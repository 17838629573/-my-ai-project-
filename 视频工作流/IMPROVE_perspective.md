# IMPROVE_perspective：透视几何（改前必读）

## 一、为什么需要这个模块

用户指出：路径不能硬编码两点坐标（如 `(474,482)→(23,732)`）。
长城在画面里是**由远及近的纵深走向**，沿它走必须**远小近大**；
若平行画面横着走，则**无大小变化**。

原代码缺失：
- `scale_map.py` 只有**单一 `px_per_m`**，无纵深维度，无法表达远小近大
- `_px.py` 的 `px_per_m(ref_px, ref_m, crop_top)` 同样是标量
- 路径生成靠手填控制点 → 改一次场景就得重写

## 二、业界依据（三个独立来源，互相印证）

### 来源1：Hoiem et al., IJCV 2008《Putting Objects in Perspective》Eq.(6)
已知一个真实高度 y_c（相机高）与地平线 y_0，可反推物体真实高：
```
y_world = y_c * (v_t - v_b) / (v_0 - v_b)
```
v_t / v_b = 物体顶部/底部像素 y（图像 y 向下为正，故 v_t < v_b）。

**关键用途：变形后即可由已知参照物反解相机高度**（不需手填）：
```
H_cam = y_world * (v_b - v_h) / (v_b - v_t)
```

### 来源2：CVPR《Single View Scene Scale Estimation Using Scale Field》
```
k(x, y_g) = (y_g - y_0) / y_c        [px per meter]
```
地面像素到地平线的垂直距离 / 相机高 = 该点 px per meter。
**scale 与"离地平线的距离"成正比**，与横向位置无关。

### 两式自洽性验证（已写入自检第4项）
```
(v_b - v_t) = y_world * (y_b - y_0) / y_c
```
两来源推导完全一致，互为交叉验证。

### 来源3：地面平面单目测距
```
Z = f * H_cam / (y_0 - y)          （零俯仰针孔模型）
```
双曲线关系：越接近地平线，深度增长越快。
反函数 `y(Z) = y_h + f*H_cam/Z` 用于**由深度生成路径点**（铁律100 的实现基础）。

### 焦距经验值
Hoiem 正文："f = 1.4 times image height is typical"。
这是模块内**唯一常数 `F_OVER_IMAGE_H = 1.4`**，改动必须换出处。

## 三、实测（本轮真跑）

输入全部为「已知事实」，无手填路径坐标：
```
参照物：僧人 1.70m，图上 200px，脚底 y=878
地平线：v_h=480（由消失点探测）
→ 反解 H_cam = 3.383 m      f = 1344 px
```

| 方向 | 结果 | 判定 |
|---|---|---|
| 横向 x:60→480, y 恒定 | 僧人恒 200.0 px | 无大小变化 ✓ |
| 纵深 y:600→878 | 60.3 → 200.0 px | 远小近大 3.3× ✓ |
| 纵深屏幕间距 | 19/28/40/65/126 px | 远处密近处疏（透视压缩）✓ |

## 四、踩过的坑

**自检第9项 FAIL 是测试数据的错，不是实现的错。**
初版测试随手写了三条线段，断言它们汇聚于 y=300，
实际交点在 455.6 —— 期望值写错。
修正为「从 VP=(400,300) 出发取斜率 k，截取 y=900→500 的线段」，
并补 `9b` 断言 VP_x 也还原正确。

**教训：写几何自检时，测试数据必须由"目标真值"反推构造，
不能凭直觉摆几条线再猜结果。**

## 六、给 AI 的提示词

> 生成路径时，禁止写出 `(x1,y1)→(x2,y2)` 这样的具体坐标。
> 必须先确定：地平线 v_h（探测）+ 相机高 H_cam（参照物反解），
> 再用 `path_along_depth(z0, z1, n, ...)` 由深度生成屏幕点。
> 若场景是横向平移而非纵深，用 `path_lateral` 并接受 scale 恒定。
> 需要"远处物体小多少"时调 `object_px_height`，不要自己乘比例。

## 七、顺带修复：gate_doc.py 门禁口径 bug（字节 vs 字符）

加完透视契约后文档门禁报 `契约总量 71183 > 70000`，
但 `wc -m` 实测只有 43,815 字符 —— 差 27,368。

**根因：`gate_doc.py` 的 `sz()` 用 `os.path.getsize()` 字节数，
而 `gate_module.py` 用 `len(src)` 字符数，两个门禁口径打架。**

中文 UTF-8 一个汉字占 3 字节，用字节数衡量中文文档会虚高约 1.6 倍，
等于把 70000 的阈值暗中压到实际约 23,000 字符 —— 阈值失去原意。

**判定：这是门禁的 bug，不是文档膨胀。**
对 LLM 而言上下文占用是字符/token，不是磁盘字节（与模块门禁口径统一）。

修复：`sz()` 改为 `len(f.read())`（UTF-8 解码后计字符）。
修复后：契约总量 43,815 / 70,000，余量 26,185。

**教训（同类第二次）：**
本项目已两次遇到"字节数 vs 字符数"误判
（第一次是 `solver_survey.py` 被误报 16,254 超限，实际 11,922 字符）。
凡是**衡量给 LLM 看的东西**，一律用字符数；
只有**衡量磁盘占用**时才用字节数（`gate_size.py` 管产物体积，那个用字节是对的）。
