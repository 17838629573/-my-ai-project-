# 开源对照与改造方向清单

建立日期：2026-10-04
用途：把外部开源项目的实现方式与我们当前实现逐条对照，标出差异，作为后续改造的施工顺序。

---

## 零、一句话结论

**十个项目里只有 AnimatedDrawings 真正对口「让人物动起来」，其余要么我们已实现，要么不适用。**
我们缺的不是"引擎"（帧号→规则、位移缩放、透视推进全都有），而是**最后一层：让位图关节弯曲的形变器**。

---

## 一、逐项目对照

### 1. AnimatedDrawings（Meta / SIGGRAPH 2023）★核心

**它怎么做**：一张人物图（不拆）+ 手动标 16 关节 + BVH 动作 + ARAP 形变。

| 环节 | 它的实现（已查证） |
|---|---|
| 网格 | scipy Delaunay + **40×40 均匀内部采样**（不是泊松盘）+ 轮廓化简 tol=0.25 + 重心过滤三角面；约 **840 顶点 / 1000–1600 面** |
| UV | **顶点归一化到 [0,1] 的原始像素坐标**（没有专门 UV 展开） |
| ARAP | **单步两阶段，非迭代**：先解全仿射求边变换 → 提取 2×2 旋转（用 **atan2，不是 SVD**）→ 把旋转施加到原始边当目标 → 再解顶点位置 |
| 控制点权重 | `w = 1000` |
| 数值稳定 | 奇异矩阵加 `1e-8·I` 扰动 |
| 越界处理 | 初始就落在三角形外的 pin **直接丢弃**（源码会 track 哪些 pin 在 mesh 内） |
| 投影分组 | frontal / sagittal / pca 三选一；**躯干常用 frontal，四肢用 pca** |
| 关节深度 | 就是投影时**被丢掉的那个轴的坐标**，用于渲染前后顺序 |

**与我们不同**：

| 项 | 我们 | 差异 |
|---|---|---|
| 三角网格 | ❌ 没有 | 我们从未三角化过人物 |
| ARAP 形变 | ❌ 没有 | **核心缺口** |
| 关节像素标注 | ❌ 没有 | puppet 阶段用过"锚点 10%"估算，被证明不可靠 |
| 关节求解 | ✅ `pose.solve` 17 关节、随 t 变、有 stance/swing | **我们有，而且更强** |
| 动作数据 | 它仓库 **7 个 BVH 里没有走路循环**（最接近的是 jumping_jacks 125帧/30fps、jumping 654帧/120fps） | 我们不需要找 BVH，`pose.solve` 自带 walk |

**关节命名对不上，必须做映射**：

```
它(16): root hip torso neck l/r_shoulder l/r_elbow l/r_hand l/r_hip l/r_knee l/r_foot
我们(17): nose l/r_eye l/r_ear l/r_shoulder l/r_elbow l/r_wrist l/r_hip l/r_knee l/r_ankle
缺口:  我们没有 root / torso / neck 单点 → 需派生（pelvis=双髋中点, neck=双肩中点，puppet 阶段已做过）
        hand≈wrist, foot≈ankle（可接受）
        头部我们有 nose/eye/ear 三点，它只有 neck → 头可整体随 neck 走
```

**已知局限（论文/issue 明示）**：
- 关节附近纹理拉伸（因为 UV=顶点位置，没有专门参数化）
- **单步 ARAP 在大角度弯曲时误差大**（它为了快牺牲了迭代）
- 无自碰撞
- 输入要求：四肢必须分离、背景必须纯白

**许可**：CC BY-NC 4.0，**禁商用**。但我们照 Sorkine&Alexa 2007 论文自己实现不受此限——算法原理是公开的。

**采纳**：✅ 照论文自己实现 `arap.py`，不抄它的代码。
**一处要改**：它用单步非迭代，我们**用迭代版**（走路循环可离线算，不怕慢，换取大角度不出错）。

### 2. Remotion（61.7k）

**它怎么做**：React 组件 + `useCurrentFrame()` 拿帧号 → 返回该帧该长什么样 → 无头 Chrome 逐帧截图 → FFmpeg 编码。
核心约定：**画面只由「帧号 + 数据」决定**，帧间无状态，所以能并行、结果完全确定。
它明确禁止 CSS 动画 / setTimeout —— 因为渲染时帧是乱序并行的，这类动画会错位闪烁。

**与我们不同**：
- 我们 `walkflow.run` 里 `t = i/fps` 逐帧算 `(x, y, scale)` —— **同一个模型，已实现**
- 我们用 OpenCV VideoWriter 直出，没有浏览器层（我们不需要 DOM）

**采纳**：❌ 不引入。已在做。
**但抄一条纪律**：帧间无状态、结果可复现——这条我们已满足，值得写进契约固定住。

---

### 3. Manim（94.5k）

**它怎么做**：`ImageMobject` + `.animate.shift() / .scale() / .rotate()`。

**搜到一条对我们极重要的原话**（它的位图限制）：
> 位图不能用 `.animate` 做形变动画，它们不是矢量无法插值变形。只应使用 FadeIn/FadeOut 以及 shift/scale 这类**不改变几何拓扑**的操作。

**这条直接证明我们走过的路是对的**：光流只能挪像素所以腿糊；位图就是不能靠位移做形变；形变必须走 ARAP 这类网格方法。

**与我们不同**：`matteflow.place` 就是位移+缩放，已实现。

**采纳**：❌ 不引入。但它的限制是"必须上 ARAP"的直接依据，值得记进 IMPROVE。

---

### 4. MoviePy / Ken Burns（14.9k）

**它怎么做**：`make_frame(t)` → `scale = 1.0 + 0.08*progress` → resize → crop 平移。慢推拉。

**与我们不同**：
- 它的缩放是**匀速线性**的（1.0→1.08）
- 我们 `walkflow` 的缩放来自 `px_per_m_lateral(y) = (y−v_h)/h`，是**透视真值**，随深度非线性收缩（实测 118.5→68.6 px/m，5.26 倍）

**采纳**：❌ 已超越。我们的更严谨。

---

### 5. DiffMorph（484）

**它怎么做**：CNN 训练 mult/add/warp 三张 map，梯度下降，公式
`result = W(source * max(0.1, 1+mult*mult_scale) + add*add_scale, warp*warp_scale)`
默认 **训练 1000 epochs**，依赖 TensorFlow 2.4。

**与我们不同**：
- 需 TF（违反纯代码约束）
- **每对图都要重新训练**，不是通用动画器
- 是"两图之间 morph"，不是循环动画

**采纳**：❌ 否。

---

### 6. vectalign（2011）

**它怎么做**：Needleman-Wunsch 序列对齐（生物信息学的蛋白/核酸比对算法）→ 把 SVG path 转点序列对齐 → 统一命令类型（Q 升 C）→ 统一起点/方向/闭合 → 输出可插值的 pathData。纯数学，很优雅。

**与我们不同**：**要求矢量**。我们是位图，没有 path。

**采纳**：❌ 否（除非改走矢量素材路线，那是另一条大路）。

---

### 7. gl-transitions（2144）

**它怎么做**：125 个 GLSL 转场，`vec4 transition(vec2 uv)` 返回 `mix(getFromColor(uv), getToColor(uv), progress)`。

**与我们不同**：转场是**片段与片段之间**的过渡，不是角色动作。

**采纳**：⚠️ 可选。做场景切换（比如远景→近景）时可套，非核心。

---

### 8. pixelsort / ASDFPixelSort（874 / 661）

像素排序，静态图渲染成流动色带。抽象艺术效果。

**采纳**：❌ 与古风写实基调冲突。

---

### 9. DepthFlow / 3d-ken-burns（你已排除，判定正确）

**它怎么做**：前者走 `transformers` 调深度估计模型（Depth Anything 类），渲染才是 GLSL；后者 PyTorch 深度网络。

**判定口诀（你给的，已验证）**：凡是"因为理解了画面深度所以立体移动"的，都带权重。

**我们不同**：我们的深度是世界坐标几何真值（Z 从 11.4m 到 60m），比估计出来的准。

**采纳**：❌ 确认排除。

---

### 10. img2obj（1667）

从一张图程序化推断几何生成 .obj，再旋转渲染。3D 化。

**采纳**：❌ 偏离 2D 工作流。

## 二、差异汇总（一眼看全）

| 能力 | 开源做法 | 我们现状 | 判定 |
|---|---|---|---|
| 帧号→规则引擎 | Remotion / Manim | ✅ walkflow 已有 | 不需引入 |
| 位图位移缩放 | Manim / MoviePy | ✅ matteflow.place 已有 | 不需引入 |
| 透视推进（非线性） | 开源普遍是线性 Ken Burns | ✅ 世界弧长，**我们更强** | 不需引入 |
| 关节求解（随 t） | BVH 文件 | ✅ pose.solve 17 关节 | 不需引入 |
| 绿幕抠 alpha | — | ✅ flood_key 已有 | 已有 |
| 关节像素标注 | char_cfg.yaml 16 点 | ❌ 缺 | **要补** |
| 三角网格 | Delaunay ~840 顶点 | ❌ 缺 | **要补** |
| ARAP 形变 | arap.py | ❌ 缺 | **核心缺口** |
| 关节→形变接线 | retarget | ❌ 缺 | **要补** |

**结论：四个要补的里，三个是 ARAP 的前置件。施工重心就是 ARAP。**

## 三、改造顺序（按依赖排，不并行）

```
Step 1  mesh.py     轮廓提取 + Delaunay 三角化 + 内部采样
                    （复用 flood_key 的 alpha，不重新抠图）
Step 2  rig.py      16 关节像素标注表 + 派生 root/torso/neck
                    （需目视校准一次，业界也认这步必须人工）
Step 3  arap.py     2×2 旋转 + cotangent 权重 + 稀疏求解
                    （用迭代版，不用它的单步版）
Step 4  retarget.py pose.solve 米制关节 → 图像像素控制点
                    （注意：它躯干用 frontal、四肢用 pca，我们可先全用 frontal 简化）
Step 5  接进 walkflow  替换"逐格贴 alpha"，改为"一张图逐帧形变 + 位移缩放"
```

Step 1–4 各自带自检，Step 5 才出片。

## 四、风险登记

| 风险 | 依据 | 应对 |
|---|---|---|
| 关节附近纹理拉伸 | 它 UV=顶点位置，官方已知局限 | 顶点密度提高；或接受（僧袍宽松，拉伸不明显） |
| 大角度弯曲出错 | 它单步非迭代的已知问题 | 我们用迭代版，且走路循环可离线算 |
| 关节标注不准 | 官方自带 fix_annotations 工具承认"自动不准" | 接受人工校准一次；但**内点标错只局部变形，不会肢体接反**（比部件拼接鲁棒） |
| 输入图要求 | 四肢必须分离、背景纯色 | 我们已有绿幕抠图，满足 |
| 走路 BVH 缺失 | 它仓库 7 个文件无走路循环 | 不影响，我们用自己的 pose.solve |
| 许可 | CC BY-NC 4.0 禁商用 | 照论文自己实现，不抄代码 |

# 附录 A：路径 · 朝向 · 缩放（补记）

## A.1 业界怎么做

### 缩放：三种方案（groebelsloot 归纳，已被多个引擎采用）

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| ① 按 Y 轴 | 屏幕越靠上缩得越小 | 极简，多数场景够用 | **不能表达"同一 y 上不同深度"**——楼梯上走不该缩小，它会缩 |
| ② walkbox 顶点插值 | 可走区域多边形每个顶点存缩放值，内部插值 | 能表达复杂房间 | 每个顶点手调，维护量大 |
| ③ alpha 图 | 另存一张只画可走区域的灰度图，**alpha 值 = 该像素的缩放系数** | 逐像素精确，Photoshop 拉个渐变就行 | 要为每场景额外做一张图 |

Visionaire / AGS 是 ①+② 的混合：**way point 存 Character size（百分比），点与点之间插值**。
官方原话：*"usually a bigger number at the bottom of the scene, a smaller number further upwards"*；
并警告 *"Adding a scale factor to too many points can lead to unexpected results"*。

SeaLeft 补了关键一条：**多层房间必须分多个缩放区**，否则二楼的人会被缩成蚂蚁。
（我们的城墙是单层，暂不需要，但这条解释了为什么业界不只用 Y 轴。）

### 速度：必须同时调三个量

groebelsloot 原话：
> You have to adjust 3 variables: **size of the actor, horizontal speed, and vertical speed**.
> If you don't adjust that speed, and the actor is half its normal size because it's far away,
> then the speed in which he walks **seems ridiculous fast**.

**这正是我们 V2 修的那个病**——只调了缩放没调推进，所以"小人在狂奔"。
我们用世界弧长解决（横向/深度 px_per_m 是两个量，比值 3.39→17.82 非常数），比业界的"手动给两个速度"更严谨。

### 朝向：8 方向 sprite

业界标准做法是**量化扇区**：
```
DIRECTIONS = ['E','SE','S','SW','W','NW','N','NE']
angle   = atan2(inputY, inputX)
sector  = round(angle / (PI/4))
facing  = DIRECTIONS[(sector+8) % 8]
```
Visionaire 是引擎**自动决定**用哪个方向动画，作者不用管。

八方向素材制作纪律（framesprite 指南）：
- 先定一张 full-body master，锁定服装/比例/持物手/相机高度/地平线
- 先出 N/E/S/W 四个正向，比对**相反方向**（持物手、披风、护肩是否漂移）
- 再出四个斜向
- **只对称的设计才能镜像**——不对称的持物/发型/Logo 镜像就错

### 深度：四种技巧（SeaLeft）

```
1 透视 Perspective    —— 平行线收敛
2 缩放 Scaling        —— 远小近大
3 深度遮罩 Depth Mask —— 每个像素存深度值，人物深度 > 像素深度就不画（可走到柱子后）
4 渲染顺序 Render Order —— 深度大的先画，近的覆盖远的
```

### 多消失点（AGS 论坛）

Gemini Rue 用**多个消失点**让消失线更接近平行：
> 好处是拿到轴测透视的优点（缩放不剧烈），又不像轴测那样假（全平行显得人工）

风险：不同物件用了不同消失线，人物走近走远时与它们的比例会对不上。

## A.2 我们实测的三种方向

用 `_ground_arc` 反投影实测（相机 v_h=480, v_x=270, h=3.366, f=1344）：

| 方向 | 屏幕轨迹 | 朝向角 | 缩放 | 判定 |
|---|---|---|---|---|
| **A 沿深度走远** | (150,876.8)→(247.2,555.4) | −73.2° | **5.26x** | ✅ |
| **B 平行屏幕横走** | (80,876.8)→(460,876.8) | 0.0° | **1.0000x** | ✅ y 变化 0.00px |
| **C 斜向** | (80,876.8)→(224.4,630.8) | −59.6° | 2.63x | ✅ |

**B 完全正确**：y 变化 0.00px、缩放比 1.0000 —— 你说的"侧轴应该平行"，几何上已经成立。

## A.3 差异与缺口

| 项 | 业界 | 我们 | 判定 |
|---|---|---|---|
| 沿深度走远收敛 | 缩放到消失点 | ✅ 5.26x，几何真值 | **我们更强**（业界是手填百分比，我们是反投影算的） |
| 平行屏幕不缩放 | 同一缩放区 | ✅ 实测 1.0000 | 已有 |
| 斜向 | 插值 | ✅ 已验证 | 已有 |
| 速度三量同步 | 手动给水平/垂直速度 | ✅ 世界弧长自动 | **我们更强** |
| **朝向** | **8 方向 sprite** | ❌ **单张位图恒朝右** | **核心缺口** |
| 缩放区（楼梯/多层） | alpha 图或多区域 | ❌ 单区域 | 城墙单层暂不需要 |
| 深度遮罩 | 逐像素深度 | ❌ 无 | 人物永远盖在背景上，无法走到墙后 |
| 渲染顺序 | 深度排序 | ❌ 无（单人场景） | 多人时需要 |
| 多消失点 | 可选技巧 | ❌ 单消失点 | 可选优化 |

## A.4 结论

**几何层我们没问题，缺的是"朝向"这一层素材维度。**

`_ground_arc` 的三种方向全对（B 的 y 变化精确到 0.00px），但这只解决了"人往哪走、缩多少"。
人物本身是哪张图，取决于朝向——而我们只有一张朝右的位图。

所以走远时人仍朝右、横走时也朝右、斜走时还朝右。**业界用 8 方向解决。**

好消息：**ARAP 上线后这条会有变化** —— 关节能弯曲意味着同一张图可以做一定程度的朝向偏转，
而不必真出 8 套素材。但**背面/正面**（N/S）是骨架投影面的问题，ARAP 也救不了，只能靠素材。

**务实取舍**：我们是"沿城墙走远"单一场景，朝向实际只需要 1~2 个（朝右走远 / 背影走远）。
建议先只补**背影一套**（走远时本就该看到后背），而不是全套 8 方向。
