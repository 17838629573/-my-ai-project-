## 三、绕过测试：发现 9 项缺陷

### P0-1 · 安装后门禁全部失效（致命）

```
$ mkdir proj/.claude && sh install.sh .
已安装到 Claude Code → .claude/skills/ + WORKFLOW.md

$ test -f scripts/enforce.py && echo 存在 || echo 不存在
✗ scripts/enforce.py 不存在!

$ python3 scripts/enforce.py gate post-step 1
python3: can't open file 'scripts/enforce.py': [Errno 2] No such file or directory
exit=2
```

**install.sh 只复制 `skills/` 和 `WORKFLOW.md`，从不复制 `scripts/`。**

后果：README 推荐的「方式二：一键安装」装完后，WORKFLOW.md 七个步骤里每一条要求的 `enforce.py` 调用全部报 exit=2，**五道硬门禁一行都跑不起来**，`validate` 也直接失效。这是首要路径，不是边缘场景。

### P0-2 · 门禁脚本可被 AI 自行改写，且自检发现不了

```
$ cat > scripts/enforce.py <<< 'print("✓ 全部通过"); sys.exit(0)'
$ python3 scripts/enforce.py check-write .env
[enforce] ✓ 全部通过
exit=0        ← 红区保护已失效

$ python3 scripts/enforce.py validate
[enforce] ✓ WORKFLOW.md 铁律完整（9 条）
[enforce] ✓ scripts/dep_check.py 存在
[enforce] ✓ scripts/enforce.py 在运行     ← 只打印"在运行"
[enforce] ✓ 全局完整性检查通过
exit=0        ← 自检全绿
```

`validate` 对 enforce.py 只做「在运行」的存在性声明，**不校验哈希、不校验内容**。AI 被门禁卡住时，最直接的解法就是改门禁本身，而这套系统对此毫无感知。

### P0-3 · 判定依据门禁形同虚设

```
$ enforce.py check-evidence 1 "测试失败,8个用例挂了3个"
[enforce] ✓ 判定依据：退出码 1 | 测试失败,8个用例挂了3个
exit=0
```

**传失败退出码照样放行。** 铁律 1 的全部意义在于「不允许 AI 用嘴判定」，但该门禁只校验参数是不是整数，完全不看数值。AI 跑挂了测试、如实上报退出码 1，门禁照样盖章通过。

### P0-4 · 铁律内容可被替换（只改文字，不改标题）

```
# 将铁律1 由「判定靠命令输出，禁止说应该没问题」
# 改为「判定可凭经验估计，无需每次跑命令」

$ enforce.py check-iron-law WORKFLOW.md
[enforce] ✓ WORKFLOW.md 铁律完整（9 条）
exit=0
```

门禁用两个条件保护铁律：① 正则匹配 `## 铁律` 标题存在；② 数 `^\d+\.` 编号 ≥9。
**只改主体文字、保留标题和编号，两项检查全部通过。**

对照组：若连标题一起改（如改成 `## 纪律（可选参考）`），门禁能正确阻断 exit=1。**所以保护的是标题，不是内容。**

### P1-5 · pre-step 门禁是死代码

```python
return 0 if ok == checks else 0  # pre-step 只警告不阻断
```

三元表达式两个分支都返回 0。前 3 项检查算完白算，**pre-step 在任何情况下都不可能阻断**。

### P1-6 · post-step 只认字符串，不认成败

```
$ echo '2026-09-29 10:00 | 步骤5 | 测试失败,卡住' > WORKLOG.md
$ enforce.py gate post-step 5
[enforce] ✓ WORKLOG 已记录步骤 5
exit=0
```

只要出现「步骤5」四字即放行，写入的是失败记录也照过。断点续作会从一个失败点继续。

### P1-7 · 授权可被 AI 自行伪造

```
$ printf '问: 可否修改 .env\n授权: 永久\n到期日: -\n' > tracks/.env.track.md
$ enforce.py check-write .env
[enforce] ✓ .env 红区文件，已有授权
exit=0
```

`.track.md` 是纯文本，无签名、无用户痕迹、无创建者校验。AI 自己写一个「到期日: -」就拿到永久授权，**红区保护一次性瓦解**。铁律 8 的授权体系建立在「AI 不会伪造授权文件」这个假前提上。

### P1-8 · CI 配置实际不在红区（与 README 声明不符）

```
$ enforce.py check-write .github/workflows/ci.yml
exit=0          ← 放行

$ enforce.py check-write requirements.txt
[enforce] ✗ 铁律5 违例：requirements.txt 属于【红区文件】
exit=1          ← 阻断
```

`RED_ZONE_PATTERNS` 中只有 `r'(^|/)ci/'`，**没有 `.github/workflows`**。README 与代码注释均声称保护 CI 配置，实际未覆盖。AI 可自由改写 GitHub Actions。

### P1-9 · auth 模式误伤严重

```
$ enforce.py check-write src/author.py
[enforce] ✗ 铁律5 违例：src/author.py 属于【红区文件】
exit=1

$ enforce.py check-write app/authors/model.py
[enforce] ✗ 铁律5 违例
exit=1
```

`r'(^|/)auth'` 无词边界，任何含 auth 子串的路径（author / authors / auth_utils）都被判红区。在正常业务项目里会造成大量误阻断。

## 四、架构层：一个前提性问题

以上九项是代码缺陷，还有一个更根本的：

```
$ echo "SECRET_KEY=leaked" > .env      # 不调用 enforce.py，直接写
退出码=0  文件存在? 是
→ enforce.py 只在 AI「主动调用」时生效
```

**整套门禁是「自觉遵守型」的。** 没有任何 hook、pre-commit、CI 强制把它挂在写文件动作上。AI 用编辑工具直接落盘，门禁根本不会被触发。

这意味着：以上所有门禁的强度，都建立在「AI 会主动调用它」这个前提上。而这个前提恰恰是被约束对象自己保证的。

## 五、防得住的部分（正面结论）

| 场景 | 结果 |
|---|---|
| `check-evidence` 传非整数（如「应该没问题」） | exit=1 ✓ 正确阻断 |
| 铁律章节标题被删除或改名 | exit=1 ✓ 正确阻断 |
| 红区文件无授权写入（AI 主动调用时） | exit=1 ✓ 正确阻断 |
| WORKLOG 无步骤记录时过门 | exit=1 ✓ 正确阻断 |
| 授权文件缺失 / 过期 / 缺到期日 / 日期格式错 | exit=1 ✓ 四种均正确阻断 |
| `dep_check.py` 缺 deps.md | exit=1 ✓ 正确报错 |
| WORKFLOW.md 引用的 12 个 skills 文件 | 全部存在 ✓（SKILL.md 引用的 deps.md 为运行时产物，正常缺失） |

授权过期处理的四种异常状态覆盖得相当细致，这部分实现质量高。

## 七、修复建议（按优先级）

**P0 — 必修**

1. **install.sh 补复制 `scripts/`**，并在安装完成后执行一次 `validate` 自证；装完跑不通就不算装完。
2. **enforce.py 自校验**：启动时比对自身与 `scripts/` 下的哈希，或把门禁挪到 AI 权限之外（Git hook / CI），使其不可被改。
3. **check-evidence 校验退出码为 0**，非 0 即阻断——这是铁律 1 的唯一意义。
4. **铁律保护改为内容哈希**，而非数编号；可把九条铁律的规范化文本存哈希常量。

**P1 — 应修**

5. 修 `return 0 if ok == checks else 0` 死代码。
6. post-step 增加状态字段校验，失败记录不得过门。
7. `.track.md` 增加用户签名或写入者校验，纯文本授权不可采信。
8. 红区补 `.github/workflows`，`auth` 模式加词边界 `\b`。
9. 在 WORKFLOW.md 中明确声明：门禁生效依赖宿主 hook 强制，否则只是自觉遵守。

## 八、给作者的一句话

这套工作流的**内核值得继续做**——省上下文、硬软规则分离、层级只读、契约图，这几条判断是准的，比多数堆提示词的方案高一个层级。

但当前版本最大的风险不是规则不够，是**门禁可以被绕过而不留痕迹**。一个能被约束对象自己关掉的门禁，在验证报告里记多少次「通过」都不算数。

建议下一步：先修 P0-1（装完即废）和 P0-2（可自废门禁），然后找一个没参与设计的人真实跑一遍完整项目。当前 README 里的「六轮测试、24 项边界场景」若为 AI 自测，其可信度不足以支撑「顶级」这个定位。
