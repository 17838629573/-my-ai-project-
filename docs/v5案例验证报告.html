案例项目

为贴近真实使用场景，选了一个与运营相关的实用工具：多平台文案合规检查器——输入一段文案，自动检查其在公众号 / 小红书 / 抖音三平台的适配性（标题长度、正文字数、话题数上限），纯 Python 标准库实现。

项目信息
维度值
项目规模中小型（5 个模块，约 150 行代码 + 4 个测试文件）
语言 / 框架Python 3 · 标准库（unittest 测试）
模块划分cli（入口）/ checker（引擎）/ parser（解析）/ platform_rules（规则）/ report（渲染）
架构分层2 层：L0 总架构师（cli / core / report）→ L1 次级架构师（checker / parser / platform_rules）
测试策略TDD：先写测试（红）→ 写实现（绿）

步骤 3：写模块（TDD 分支）

拆模块时勾选 TDD → 先写测试再写实现。测试先行，运行确认全红（符合预期）：

随后按契约实现 5 个模块，再次运行测试：

Ran 8 tests — FAILED (failures=4)  # TDD 抓到 2 个真实 bug

发现的问题 ①：parser 同一行多标签没拆分

症状：#标签1 #标签2 写在同一行时，被当成一个整体标签，导致「话题数超限」检查漏报。
根因：解析逻辑按行取整段，没有按 # 切分同行的多个标签。
修复：改用正则 #([^\s#]+) 提取一行内所有标签。

发现的问题 ②：平台规则「不支持标签」误报

症状：公众号（max_tags=0）把普通正文里的 # 符号当话题，误报「该平台不支持话题标签」，导致正常文案被判 fail。
根因：规则语义设计不合理——max_tags=0 本意是「不检查话题数」，实现却写成「有标签就报错」。
修复：改为 max_tags=0 时跳过话题检查，只在平台明确有上限时校验。

修复后测试全绿：Ran 8 tests — OK。这正是 TDD 分支的价值：先写测试暴露期望，再写实现逼出真实语义问题。

发现的问题 ③：dep_check 不识别「包内模块」写法（工作流自身 bug）

症状：代码里明明写了 from core.parser import parse，dep_check 却报「代码中未见」——图与代码一致性检查失效。
根因：dep_check 解析 import 时取 token.split(".")[0]，遇到包内模块 core.parser 只取了包名 core，匹配不到模块 parser。
影响：这是工作流脚本自身的 bug——如果项目用「包内模块」组织（Python 包 / 目录模块），依赖图验证会漏检，还可能让上层误以为下层没实现契约。
修复：import 解析改为取 token 各段候选（core.parser → {core.parser, parser}）匹配模块名。修复后复测：
模块数: 5
依赖图验证通过（0 个 warning 可人工过目）   # 全绿 ✓
