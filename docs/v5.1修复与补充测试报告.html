dep_check.py 深度修复

这是本版改动最大的文件（112 行 → 193 行）。修复过程中用真实项目逐文件核对 import，发现并确认了 3 个解析缺陷 + 2 项新能力需求：

1. 多级包内引用匹配不到（T5 假 warning 根源）

代码写 from clairvoyance.entities.context import log，旧逻辑候选只取 {token, 最后一段}，匹配不到 deps.md 的短名模块 entities.context。修复为逐级剥前缀生成全部后缀候选：

# token = "clairvoyance.entities.context" → 候选
#   clairvoyance.entities.context / entities.context / context
parts = re.split(r"[./]", token)
for i in range(len(parts)):
    cand = ".".join(parts[i:])
    if cand in modules and cand != owner:
        found[owner].add(cand)

2. from X import Y 把 Y 当模块（T5 假 error 根源，上轮误判为真 bug）

from clairvoyance.entities.context import client, config, log 中 client / config 是变量名，旧正则把 import 列表当模块路径，导致上轮报告"oracle 实际依赖 client"的 假 error（真实代码里 oracle 根本不 import client）。修复：from 语句中 X 能匹配模块 → 只依赖 X，Y 列表忽略；X 匹配不到（如 from pkg import submodule）→ Y 列表项才当候选。

# from X import Y：X 可匹配模块时，Y 是名字/属性，不参与依赖
if any(".".join(xparts[i:]) in modules for i in range(len(xparts))):
    toks.add(x)                    # 只依赖 X
else:
    # from pkg import submodule → submodule 当候选
    for item in re.split(r"[,\s]+", m.group(2).strip()):
        if item and not item.startswith("*"):
            toks.add(item)

3. 多目录概念模块归属失败（T11 多语言漏检根源）

FastAPI 模板中 deps.md 概念模块 backend.api 对应代码 backend/app/api/，旧 owner 匹配（文件名/目录名）匹配不到。修复为"路径段保序子序列 + 最后匹配位置优先"：

# 模块名段 ["backend","api"] 是文件路径段 ["backend","app","api","routes","users"] 的保序子序列
# 多个候选（backend / app.api / backend.api）选最后匹配位置最靠后的（最贴近文件的模块）
pos = _match_pos(ms, fsegs)
if pos >= 0 and pos > owner_pos:
    owner, owner_pos = m, pos

同时约定：仅出现在 -> 左侧的主模块才有代码归属权，[runtime] 契约目标（如 backend.api）不参与归属，避免假归属。

4. 括号注释与 [runtime] 运行时契约（T11 新能力）

  • (HTTP/OpenAPI) 括号内容不再被拆成"模块"（旧逻辑会产生假模块 + 假 warning）
  • 行尾 [runtime] 标记跨语言/跨进程契约（HTTP API、数据库 Schema）：跳过代码存在性验证、仍查循环依赖
  • 依赖按逗号切分（不再按空白切），frontend/client -> backend/api (HTTP/OpenAPI)[runtime] 可正确解析

5. ESM 导入支持（T11 真实发现）

TS/JS 主流写法 import { fetchApi } from "frontend/lib" 旧正则完全漏检，新增 from-import 形式匹配。已知局限：相对导入 ./helpers、路径别名 @/lib 不解析，落入 warning 兜底（不误报 error）。
