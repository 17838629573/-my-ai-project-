AI CODING WORKFLOW · 2026-09

自研工作流 v3 对比业内最佳实践

对比对象：自研「主干 + 通用模块懒加载」工作流（v3）｜对照：Spec Kit、BMAD Method、Claude Code（subagents/hooks）、Aider、Anthropic 上下文工程指南

① 最终结论：分场景，不和稀泥

总评

v3 的架构思想与 2025-2026 年业内主流最佳实践高度同频——「主干常驻 + 动作按需加载」正是 Anthropic 官方总结的 just-in-time context；「子 agent 各写各的、只回传摘要」正是 sub-agent 隔离上下文模式；「判定靠命令输出」与 Spec Kit「任务可独立验证」、Aider「跑测试迭代到通过」是同一思路。它不是野路子，而是把这些理念压缩成了极简形态。

但它本质上是「提示词纪律（软约束）的精简版」：整套体系靠 AI 自觉读、自觉遵守，没有任何运行时强制。这决定了它的可靠上限低于成熟框架。

✅ v3 更合适的场景

个人 / 小团队、中小项目、快速试错；用的是不支持 hooks/skills 的轻量 AI 工具（DeepSeek、通用聊天助手、CodeBuddy/Trae 等）。

轻、通用、零依赖、拷过去就能用——这是它对 Spec Kit / BMAD 的明确优势：那两套一个要 slash 命令生态、一个有 12 个 agent + 34 个工作流的体量。

⚠️ 成熟方案更合适的场景

团队协作、中大型产品、合规/安全要求高：用 Claude Code + hooks（硬约束，AI 没法跳过门禁）或 Spec Kit（spec/plan/tasks 持久文档 + TDD 契约测试先行）。

企业级全流程：用 BMAD Method（PRD/架构/UX 多角色 + 规模自适应规划）。这类项目里 v3 缺的规划文档层、测试先行、对抗式评审都会变成真实风险。

一句话排名：在「纯 markdown 提示词工作流」这个类别里，v3 属于上游水平，结构克制程度甚至优于多数同类；但跨类别和「软+硬约束结合」的成熟工程体系比，它是理念对齐、执行力差一层的轻量版。作者自己写的「下一步：从软约束跃迁到 hooks 代码」——方向完全正确，这也正是它和顶尖实践之间最主要的那道坎。

② 业内最好的几套在怎么做

GitHub Spec Kit

规范驱动开发（SDD）：specify（写什么/为什么，用户旅程）→ plan（技术栈/架构）→ tasks（拆成可独立实现和验证的小任务）→ implement（人变审查者）。另有 constitution（项目宪法，九条原则）和 Phase -1 门禁（简单性/反抽象/契约测试先行）。

来源：GitHub Blog · spec-driven.md

BMAD Method

AI-native 敏捷框架：12 个专家 agent（PM/架构师/开发/测试架构师/UX…）、34 个工作流、三档规模自适应规划（Quick Flow 修小 bug → BMAD 全流程 PRD+架构+UX → Enterprise 加安全/DevOps/测试策略）、just-in-time context 故事驱动开发、对抗式代码评审。

来源：bmadcodes.com · GitHub 仓库

Claude Code（subagents + hooks）

子代理各自独立上下文窗口、可限定工具权限，主代理只收摘要。Hooks 是硬约束：PreToolUse/PostToolUse 等生命周期节点挂脚本，退出码 2 直接阻断操作——「CLAUDE.md 管方向，Hooks 管纪律」，AI 没有跳过余地。

来源：Anthropic 官方文档·Subagents · CLAUDE.md/Hooks 解析

Aider + 上下文工程共识

Aider：repo map（整仓函数签名地图喂模型）、每次改动自动 git commit 可回滚、auto-lint/auto-test 循环跑到通过。Anthropic 2025 上下文工程指南：just-in-time 动态检索（只存文件路径等轻量标识）、子代理隔离、结构化笔记（NOTES.md）、压缩——核心原则「最小高信噪比 token」。

来源：Aider GitHub · Anthropic·上下文工程

④ 你的设计已被业内验证的部分

  • 懒加载 = just-in-time context：Anthropic 明确建议「只维护文件路径等轻量标识，执行时才动态加载」，v3 的「主干点名才读专项文件」是同一模式，且执行得更彻底（峰值上下文约 4.5KB）。
  • 子 agent 契约隔离 = sub-agent 架构：每个子 agent 干净上下文、只回传 1-2K 摘要，官方称该模式在复杂任务上显著优于单 agent；v3 的「只看契约块、不看别人实现」与官方「单一明确职责的聚焦子代理」建议一致。
  • 判定外置 = 可验证任务：Spec Kit 要求每个 task「可独立实现和验证，类似给 AI 的 TDD」；v3 的「grep 为 0 / 退出码 0 才算过」同理。
  • 修复环上限+中断诊断：与 Aider「auto-test 迭代到通过」+ 工程界「限重试次数防烧预算」共识一致；halt 模块的「四选项等用户选」比多数方案更显式。
  • 红黄绿文件分级：对应 Claude Code 的权限规则/hooks 阻断思想，v3 用提示词实现了它的软版本。
  • 旁路入口 = BMAD 规模自适应的朴素版：「只测试就跳步骤 5」与 BMAD「修 bug 走 Quick Flow、大项目走全流程」是同一思路。
特色亮点（别人没这么做的）：把「跨步骤复用的动作」抽成 verify/fix/check/halt 四个通用模块、步骤文件只留独有动作——这种「动作级 DRY」切法在 Spec Kit/BMAD 里都没有对应物，它们的复用靠模板和角色，v3 靠文件加载点。对「防止上下文爆炸」这个目标，这是最直接的一刀。

⑤ 真实差距与风险

差距 1：软约束是天花板 最关键

CLAUDE.md 式提示词「AI 读了会参考，但不保证每次遵守，它认为不适用就会跳过」；hooks 则是「不满足条件就阻断，没有跳过的余地」。v3 的十道门禁全是文字——AI 完全可能在第 4 轮对话后忘记读 halt、或把 quick-check 降级成「我看过了没问题」。你设计的所有精妙门禁，执行力上限是模型的自觉性。

差距 2：缺 spec/plan 持久文档层

Spec Kit 的核心资产是 spec.md / plan.md / tasks.md 三份落盘且可追溯的文档；BMAD 有 PRD/架构文档。v3 的模块契约清单是口头确认级的产物，没有要求落盘成版本化文档——长周期项目里上下文一旦压缩/重置，「当初为什么这么设计」就丢了。v3 只有 WORKLOG 事后记录，缺事前/事中的规格文档。

差距 3：测试在事后，不在事前

Spec Kit 要求 LLM「先生成定义行为的测试、获批后才写实现」、契约测试强制先行。v3 是「写完模块→检查→测试找 bug」，测试是验证手段而非设计驱动。对 bug 率要求高的项目，TDD 路线的可靠性已被大量实践证明更高。

差距 4：缺独立对抗视角

BMAD 有专门的代码评审 agent 和测试架构师（TEA），写代码的和挑毛病的不是同一个上下文。v3 的 check/test 都由同一个 AI 自写自查——「又当运动员又当裁判」，概率性偏差在这里没有冗余对冲。

差距 5：无 git 安全网

Aider 每次改动自动 commit，改坏了一键 /undo。v3 完全没提版本控制节奏——AI 精准修改（fix）一旦判断失误，没有天然回滚点。

一个小风险：极致精简本身也是双刃剑。单文件 ≤1KB 意味着每条规则都被压到一句话，新手 AI（弱模型）可能缺乏足够示例去理解「契约块到底长什么样」——Anthropic 特别强调「精选的 few-shot 示例比规则枚举更有效」。v3 目前几乎没有示例。

⑥ v3 改进清单（按性价比排序）

  1. 给关键门禁配最小硬约束 收益最高

    不必全套 hooks 化，先做两件事：① 一个 pre-commit 脚本自动跑 lint+测试，不过就阻止提交（替代 check/verify 的自觉执行）；② 红区文件路径列表交给 .gitignore 式的保护机制或 CI 检查。软约束负责「告诉 AI 该做什么」，硬约束负责「没做也跑不坏」。

  2. 步骤 2 产物落盘为 docs/低成本

    把用户确认过的模块契约清单写成 docs/spec.md（职责/接口/依赖），任务拆解写 docs/tasks.md（带勾选框）。上下文重置后 AI 读这两个文件就能无缝接续——这正是 Anthropic 说的「结构化笔记」模式，v3 现在只有事后 WORKLOG。

  3. test 模块增加「测试先行」可选档 低成本

    核心模块/公共接口：先写契约测试再实现（学 Spec Kit Article IX）；原型/一次性脚本：维持现有事后测试。给用户在步骤 1 选档位，而不是一刀切。

  4. fix 模块强制 git 节奏 低成本

    加一条铁律：「每次精准修改前确保工作区干净或先 commit，修改完成自动 commit」。一句话规则，换来 Aider 级别的回滚安全网。

  5. 评审与实现分离 中成本

    步骤 4/5 的全量检查，条件允许时派一个独立子 agent 做（它没写过代码、上下文干净、只拿契约和 diff），而不是写代码的主 agent 自查。对应 BMAD 的对抗式评审。

  6. 每个模块文件补 1 个微型示例 低成本

    比如 verify 附一段「合格验证声明」实例、split 附一个契约块实例。Anthropic 的经验：少量典型示例 > 更多规则文字。文件仍可控制在 1.5KB 内。

  7. 规划深度分档 中成本

    学 BMAD 三档：小改/原型 → 跳过步骤 2 的完整契约，一句话方案即可；正式产品 → 现有 7 步；多模块大项目 → 加 spec/plan 文档和架构评审。入口判断里加一问「这是一次性脚本还是要长期维护」。

做完 1-4 项后，v3 的定位会变成：「轻量版 Spec Kit 纪律 + Claude Code 式硬兜底」，在个人和小团队场景几乎没有短板，且依然保持「贴个文件就能用」的低门槛——这是它相对两套重框架的差异化生态位，建议守住，不要往 BMAD 那种大而全方向膨胀。
