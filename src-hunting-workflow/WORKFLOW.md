# SRC 挖洞工作流 · 主干（常驻）

> 版本 v2.1 · 十步主干 · 三条铁律 · 根因族抽象层
>
> **设计原则：规则替代思考，提问激活思考。**
> 凡是脚本能判定的，一律交给脚本；模型只做脚本做不了的事——理解意义。

---

## 三条铁律（全局常驻，仅此三条）

1. **授权范围内，最小危害**——证明可利用即可，不拖库、不改生产数据、不动真实资金
2. **不信任前端**——一切限制以改包后的服务端响应为准
3. **脚本能判定的，不动脑**——注意力留给业务理解和串联

**检索纪律（贯穿全程）**：**按根因检索，不按 CVE 检索。**
CVE 是流水号，它把同根因的东西打散了；CWE 与根因描述才是聚合键。

## P0 · 收割与校准（开工必做）

**目标**：收 15 个最近三个月的公开漏洞，反过来检验工作流。

**为什么是 15 个**：少于 10 个统计上无意义，多于 20 个校准成本会吃掉挖洞时间。

```bash
python3 src_calibrate.py load --file vulns.json --out calib.json
python3 src_variant.py gen --file vulns.json --top 8
```

**引导提问**
> 先看「工作流缺口」。
> **那些定位不到任何步骤的漏洞，为什么我的工作流看不见它？**
> 是步骤缺失，还是信号缺词？前者加步骤，后者补几个词。
>
> 再看「各步骤命中贡献」。
> **哪个命中最多？哪个是 0？**
> 命中 0 的，要么是不做的方向（删掉），要么是样本偏了（补样本）。
> 别留着既不产出又不删除的步骤——它只会稀释注意力。
>
> 最后，**这 15 个的根因有多少是同一个？**
> 三个以上同根因 = 当前周期高频模式，你的目标上大概率也有。

**纪律**：样本来源要杂——顶会、厂商公告、GHSA、社区、AI/云原生/工控各来一点。
只从一个渠道取样，校准出的覆盖率是假的。

## P1 · 情报泛化

```bash
python3 src_intel.py demo --top 10      # 情报打分
python3 src_variant.py demo --top 6     # 模式泛化（21 维）
```

**引导提问**
> **他改的参数为什么会生效？缺的是哪一道校验？** 这是根因。
> **这个根因还可能藏在哪？** 同模块其他接口、反方向操作、换方法、老版本、移动端。
> **如果防护是黑名单，等价写法有多少种？**
> **最重要：如果这么明显，为什么原作者停在这里？**
> 他很可能不是没想到，是试过没成。

## P2 · 资产测绘

```bash
python3 run.py p0 --host https://target.com
```

**引导提问**
> 哪个最值钱？标准不是"哪个好打"，是"哪个被打之后后果最严重"。
> **哪些入口是别人不会去看的？**
> 页面上能点的功能几百人测过了。真正出货的是不在页面上但确实在跑的东西——
> 老版本接口、内部路径、移动端专用域名、下线没关掉的服务。

## P3 · 越权与未授权

```bash
python3 run.py p1 --req req.txt --ids ids.txt --param orderId \
    --cookie-a "session=A" --cookie-b "session=B"
```

**引导提问**
> **这些数据本来就该公开吗？**
> 商品列表返回全部商品叫正常功能；订单详情返回别人手机号才叫越权。
> 你要回答的不是"有没有返回数据"，而是"**返回的数据属不属于我**"。
>
> 确认属于别人后：**同一批代码写的其他接口呢？管理端呢？老版本路径呢？**
> 一个接口越权是低危，同一根因的一批接口越权就是高危。
>
> **如果这么明显，为什么之前没人报？**

## P4 · 业务逻辑

**引导提问**
> **这笔钱、这张券、这个库存，服务端眼里到底是怎么算的？**
> 下单请求里带金额字段多半有问题——金额本该服务端算出来，不是从请求里读。
> **这里的"限制"是真的限制吗？** 单线程测必定正常，**必须并发**。
> **这些步骤能跳过吗？** 直接请求最后一步，看后端认不认。

---

## P5 · 注入与服务端

**引导提问**
> **转义之后还有没有还原？**
> `printf %q` 转义完，`eval printf %s` 又求值了——转义是编码决策，不是永久属性。
> 重点查：printf%q→eval、JSON 转义→shell、YAML 折叠→模板、Base64→decode→执行。
> **最终解释点看到的是什么？** 只看输入或只看输出都会漏掉中间语义变化。

## P6 · 补丁对齐

```bash
python3 src_patchdiff.py run --before <旧版> --after <新版> --out diff.json
python3 src_patchdiff.py guard --out diff.json    # 提取字段坐标
python3 src_patchdiff.py signals                  # 六类改动信号
```

**引导提问**
> **公告说的，和实际改的，对齐吗？** 不对齐 → 那道缝就是洞。
> Redis 8.6.4 声称修了，实际那个 check 只在 8.6.5——**升到 8.6.4 的用户以为安全，实际没有**。
> **修复版新增的拒绝消息说了什么？** 那条消息点名了字段、路径、条件——**它就是漏洞位置的坐标**。
> **默认值是不是变了？** 由"开"变"关"= 厂商承认原默认值不安全，**原默认值就是攻击面**。

## P7 · 信任域与内部元数据

**引导提问**
> **这个值被谁信任了？** 前端传的？第三方回调？内部服务？消息队列？
> **内部头能不能被外部覆盖？** 试 `X-Internal-*`、伪头、重复 `X-Forwarded-Host`。
> 看"最后写入生效"还是"先到优先"。
> **同一对象的两种表示，走的校验路径一样吗？** 不一样就是洞。

---

## P8 · AI / Agent 决策边界

**引导提问**
> **数据、指令、工具策略，在架构上分开了吗？**
> 模型拿到的是 token 流，分不清"要处理的数据"和"数据中藏的命令"。
> 如果工具策略只检查用户授权没授权连接器，不检查当前动作来自哪——
> **数据就自动获得了指令权限**。

## P9 · 根因族关联

```bash
python3 src_rules.py download                    # 下载规则库
python3 src_rules.py cwe --cwe CWE-347           # 按根因族拉全部案例
python3 src_rules.py vendor                      # 找跨年重复出洞的厂商
python3 src_rules.py coord --cve CVE-2024-45409  # 拿完整攻击坐标
```

**引导提问**
> **这个根因，还有哪些产品踩过？**
> 按 CWE 检索——同根因的会自动聚合，哪怕分属不同协议、不同产品、不同年份。
>
> **这个厂商，是不是在同一个坑里摔过不止一次？**
> 同组件跨年出洞且 CWE 相同 = 修复是补手法不是重构模型。**补手法的必出第三次。**
>
> **较新的那个 CVE，EPSS 是不是更高？**
> 是的话说明补丁绕过比原洞更活跃，未打补丁的实例更集中，优先级上调。

## 深挖 · 低危升级（命中任意一项后触发）

三动作：**找根因 → 横向扩展 → 纵向串联**

> **一个接口越权是低危，同一根因的一批接口越权就是高危。**
> 这是同一个洞有人报低危有人报高危的全部差别。
>
> 设止损：排查一轮无果就记 `[~]`，别为每个低危耗半天，反而挤掉出高危的时间。

## 报告 · 提交纪律

**引导提问**
> **不了解这个目标的人，照着我的步骤能复现吗？** 不能就回去补。
> **我写的是业务后果还是技术名词？**
> "存在越权漏洞"没有信息量；"任意登录用户可遍历全站订单，含手机号与收货地址，实测 N 条"才叫危害。
> **修复建议落到代码层面了吗？** "加强校验"不算。

**两条硬性纪律**：

1. **疑似 ≠ 发现。** Atmail 规则明确写"automated scanners is ineligible"，
   "scanner output only becomes reportable once you have manually confirmed it"。
   脚本产出未经人工复现，一律不许提交。
2. **同根因的多个洞要合并报。** EDUSRC 明确"多处相似漏洞"降等级。
   合并成一份按整体影响面定级，拆开报反而被降。

## 三层分工

| 层 | 谁做 | 做什么 |
|---|---|---|
| **脚本层** | 程序 | 穷举、比对、并发、版本判断——结果确定 |
| **引导层** | 提问 | 激活心智模型，指明思考方向 |
| **模型层** | 模型 | 业务理解、模式泛化、串联、创造性绕过 |

**判断标准**：这个答案能不能写成可判定的条件？能 → 脚本层。

**为什么用提问不用规则**：给模型 20 条规则，它做机械匹配；给 3 个问题，它才真正推理。
提问有叙事结构，天然抗注意力稀释；遇到清单外情况，规则不会处理，提问靠理解能迁移。

## 状态标记

| 标记 | 含义 |
|---|---|
| `[!]` | 命中，有客观差异支撑 |
| `[~]` | 观察项或假设，无客观差异，**不是发现** |
| `[x]` | 已排除，须写排除理由 |

**疑似 vs 臆测的分界线**：
疑似 = 有客观差异（两版本响应不同、换凭证返回他人数据）
臆测 = 只有推理链，无客观差异支撑 → **一律丢弃**

## 限速（必填，非可选）

| 平台 | 限速 |
|---|---|
| Atmail | ≤ 5 req/s per host，禁止无人值守扫描 |
| Kernel | ≤ 10 req/s，需带 `X-HackerOne-Research` 头 |
| OpenBugBounty | ≤ 10 req/min，登录尝试 ≤ 10/h |

**不同平台差两个数量级**，用错即违规。开工前必须按目标平台规则设定 `--delay`。
