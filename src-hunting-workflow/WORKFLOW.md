## 三条铁律（全局常驻，仅此三条）

1. **授权范围内，最小危害**——证明可利用即可，不拖库、不改生产数据、不动真实资金
2. **不信任前端**——一切限制以改包后的服务端响应为准
3. **脚本能判定的，不动脑**——注意力留给业务理解和串联

**检索纪律（贯穿全程）**：**按根因检索，不按 CVE 检索。**
CVE 是流水号，它把同根因的东西打散了；CWE 与根因描述才是聚合键。

**映射纪律**：**底层 CVE 是导航图，不是靶子。**
协议层/运行时层/框架层的漏洞本身报不了 SRC——你证明不了"某网站受 NAT 漏洞影响"。
**能提交的是映射后的应用层形态**：它在目标的代码里，在 SRC 范围内，复现得出来。

## 开工第一问（P-1，每次必答）

**动手之前先回答这一句：**

> **目标的语言 / 框架 / 运行时，近 3-5 个月是否升过级？**

不必挖、不必猜——这是客观事实，问一次就有答案。

```bash
python3 src_stack.py upgrade --lang python   # 或 java / go / js
```

**为什么是 3-5 个月**：短于 3 个月变更太少，长于 5 个月早已被别人扫过、时间窗关闭。

**没升级** → 旧版本本身就是敞口：
已知 CVE 未修 + 用着已废弃且不再收补丁的 API（CWE-477）。
Python 3.13 一次移除 19 个模块（cgi、telnetlib、crypt、pipes…），
移除理由是"长期无人维护"——**3.13 之前用它们的系统，那些模块里的问题永远不会被修**。

**升过级** → 追问：**升的是哪部分？升级过程暴露了什么？**

升级成功 ≠ 安全迁移。ESPHome CVE-2026-59178（9.8）：凭证环境变量改名无 fallback，
升级后认证与 WebSocket 登录门**全部静默禁用**，只在启动日志打 banner，`docker run -d` 看不到。

### 变更信号分级

**已硬化**：`src_stack.py upgrade` 内置分级表，按它给的强度判定，不要自己猜。

### 验收测试

**不看"服务起来了"。** 从每个能触达的网段确认五类控制仍生效：
**认证 · 授权 · 加密 · 日志 · 网络绑定**。

判据一句话：**升级后，未认证访问是否被拒绝？**

## P0 · 收割与校准（开工必做）

**目标**：收 15 个最近三个月的公开漏洞，反过来检验工作流。

**为什么是 15 个**：少于 10 个统计上无意义，多于 20 个校准成本会吃掉挖洞时间。

```bash
python3 src_calibrate.py load --file vulns.json --out calib.json
python3 src_variant.py gen --file vulns.json --top 8
```

**引导提问**
> 先看「工作流缺口」。
> **那些定位不到任何步骤的漏洞，为什么我的工作流看不见它？**
> 是步骤缺失，还是信号缺词？前者加步骤，后者补几个词。
>
> 再看「各步骤命中贡献」。
> **哪个命中最多？哪个是 0？**
> 命中 0 的，要么是不做的方向（删掉），要么是样本偏了（补样本）。
> 别留着既不产出又不删除的步骤——它只会稀释注意力。
>
> 最后，**这 15 个的根因有多少是同一个？**
> 三个以上同根因 = 当前周期高频模式，你的目标上大概率也有。

### 三项硬性规则（已硬化，跑脚本即可）

```bash
python3 src_calibrate.py load --file vulns.json --require-nonfamous
```

脚本会自动判定并拦截：

- **非知名 CVE ≥ 1/3** —— 已披露大厂 CVE 关键词密度天然高，匹配上叫自证不叫校准
- **非知名样本单独覆盖率** —— 100% 总覆盖率不再算通过，这个数才是真信号
- **零命中步骤** —— 自动列出，并按三级流程提示处置

**零命中三级处置**（第1轮补样本 → 第2轮再补 → 第3轮降级移除）。
**禁止用"属正常""样本滞后"收尾**——这类措辞会让缺陷永久留在流程里。

### 高价值情报二次源验证

**已硬化**：`python3 src_gate.py intel --epss 0.93723 --kev --cve <CVE>`
（EPSS > 0.5 或 KEV 在列时强制三层；缺一层即拦截）


**引导提问**
> **我挖的是这个应用，还是它底下的框架？**

## P13 · 运行时根因映射

```bash
python3 src_stack.py lang --lang python
python3 src_stack.py map --family api_misuse
```

**引导提问**
> **这个语言/标准库的坑，目标代码踩了吗？**
> CPython tarfile 三个月三连修（名离返 → 硬链指软链 → fallback 双调用），
> 每次堵一个具体形态。说明还有第四种。
>
> **是不是"不当的地方用了不当的代码"？**
> 这类不是缺校验，是**用错了查找方式**——正常输入下完美工作，
> 只在攻击者控制的键名下崩溃：
> `message.hasOwnProperty(f)` → 字段名 `hasOwnProperty` 遮蔽原型方法 → 崩溃
> `Object.hasOwnProperty.call(message, f)` → 才是正确写法
>
> **关键：这类必须专门构造键名才能触发**（`constructor`/`__proto__`/`toString`/`rpcCall`）。

**纪律**：运行时 CVE 本身报不了 SRC（除非目标 SRC 明确包含且版本可判定）。
能报的是**误用那一半**——它发生在应用代码里，在目标仓库里，在 SRC 范围内。

## 深挖 · 低危升级（命中任意一项后触发）

三动作：**找根因 → 横向扩展 → 纵向串联**

> **一个接口越权是低危，同一根因的一批接口越权就是高危。**
> 这是同一个洞有人报低危有人报高危的全部差别。
>
> 设止损：排查一轮无果就记 `[~]`，别为每个低危耗半天，反而挤掉出高危的时间。

| 拦截项 | 依据 |
