# 厂商改动对齐法：用「实际改了什么」精确定位漏洞

> 核心命题：**公告是说法，改动是行为。**
> 把两者逐条对齐——一致即精确定位；不一致的那道缝，就是洞。

---

## 一、为什么这个方法更强

前面我们做了两件事：读公告措辞反推、看补丁 diff 反推。但两者都有盲区：

- **公告会撒谎**（不一定恶意，可能是笔误、合并错误、分支混乱）
- **闭源看不到 diff**

而"厂商实际改了什么"是**行为证据**，不依赖它的自我陈述。

### 决定性例证：Redis 8.6.4 的 patch guard omission

Redis 8.6.4 的 release notes 声称通过 PR #15081 修复了某个问题。
但审计 8.6.4 的源码发现：**那个 duplicate-ownership check 根本不在 8.6.4 里，它只出现在 8.6.5**。

后果：**所有升到 8.6.4 的用户以为自己安全，实际没有。**

这个案例的价值不在于"Redis 有个洞"，而在于它证明了——
**公告与实现之间存在系统性偏差，而这个偏差本身就是最高价值的攻击面。**

## 二、六类改动信号

闭源环境下没有源码可 diff，但改动会在这些地方留下痕迹。逐项核对：

### 1. 版本串与构建号

修复版本号、SMR/补丁级别、内部 build 号。
例：Chrome 151.0.7922.109、OMSA 11.1.0.2、DualDAR 2026-09-01、
GitLab 18.11.11 / 19.0.8 / 19.1.6 / 19.2.4、Langflow 1.9.0、Exim 4.99.3

**纪律**：必须精确到具体版本串，不能只记"已升级"。
注意 GHES 那种**多分支并行修复**——3.17.19 / 3.18.13 / 3.19.10 / 3.20.6 / 3.21.4，
只升其中一个分支等于没升。

### 2. API 签名与参数变化

handler 签名增删、必填项变化、参数类型变化。

**最佳例证**：Langflow CVE-2026-33017
修复方式是**从 handler 签名里去掉 `data` 参数** → 打过补丁的版本在 FastAPI 校验层直接拒绝，返回 **422**。

于是非破坏性的版本指纹就出来了：
- 404 / 200 / 5xx → **脆弱**（handler 接受了 data）
- 422 → **已修**（签名不再接受 data）

这类"签名变更"是最干净的版本判别法，不需要任何破坏性操作。

### 3. 新增的拒绝消息 / 错误码 ★

修复版多出来的 `xxx is required`、`invalid xxx`、`not permitted`。

**这是信息密度最高的一类**——那条拒绝消息直接点名了字段、路径或条件，
**它本身就是漏洞位置的坐标**。

拿到之后立刻做等价变形，就是绕过测试的第一步。

### 4. 默认值变更

出厂默认由"开"变"关"、由"允许"变"拒绝"。

例：阿里云 ACK 托管节点池 `management.auto_vul_fix` 与 `auto_repair` 默认值统一变更为 `false`。

**逻辑**：默认值变更 = 厂商承认原来的默认值不安全。
**原来的那个默认值就是攻击面**——去查那些没跟着改的、或者被显式改成旧值的实例。

### 5. 依赖项版本提升

例：Adobe 要求升级 C2PA SDK（`c2pa-web ≤0.7.1` / `c2pa ≤0.80.1` → `0.8.3` / `0.85.1`）。

**逻辑**：依赖升级把根因锁到了具体解析库。顺藤摸瓜查该库的其他 CVE，
往往能找到同一根因的其他形态。

### 6. 新增/删除的配置项与文档

例：Playwright MCP 新增 `allowedHosts` 配置项。

**逻辑**：新增配置项 = 原来缺的那道检查。
**配置项的名字直接告诉你检查的是什么**（allowedHosts → 原来没校验 Host）。
配置项的可配置来源（`--allowed-hosts` 命令行、`PLAYWRIGHT_MCP_ALLOWED_HOSTNAMES` 环境变量）
也是攻击面——环境变量注入、配置文件覆盖。

## 三、自动化：src_patchdiff.py

"同一组探针，分别打在修复前后两个版本上，比对响应差异"——这是脚本能干的事。

**差异点 = 校验点。** 尤其是"修复版新增的拒绝"，那条消息就是坐标。

### 用法

```bash
# 起本地靶场（模拟修复前 :8901 / 修复后 :8902）
python3 mock_patchdiff.py &

# 对比
python3 src_patchdiff.py run \
    --before http://127.0.0.1:8901 \
    --after  http://127.0.0.1:8902 \
    --out patchdiff.json

# 提取新增校验的字段坐标
python3 src_patchdiff.py guard --out patchdiff.json

# 查看六类改动信号清单
python3 src_patchdiff.py signals
```

自定义探针文件（格式 `名称|方法|路径|头|体`）：
```
路径穿越|GET|/api/file?name=..%2f..%2fetc%2fpasswd|| 
内部头|GET|/api/items|X-Internal-Env: canary||
```

### 实测结果

本地靶场 18 个探针，定位到 **9 处新增校验**。提取出的字段坐标示例：

| 探针 | 修复后拒绝消息 | 提取到的字段/条件 |
|---|---|---|
| `/api/file?name=../..` | `invalid name: path traversal not permitted; must be under allowed_dir` | `name` `allowed_dir` `traversal` |
| `/api/items/99999999` | `invalid item_id: must be positive integer and owned by current user` | `item_id` `owned` `current user` |
| `/api/items` + `X-Internal-*` | `internal header X-Internal-*/X-Tenant-Id not allowed from client` | `X-Internal-` `X-Tenant-Id` |
| `TRACE /` | `method not allowed: TRACE is unsupported` | method 层校验 |
| `/api/orders` | `unauthorized: valid session required` | session 校验 |

**这些 token 就是下一步绕过测试的靶心**——
拿到 `name` 和 `allowed_dir`，就知道该在 `name` 上做等价变形；
拿到 `item_id` 和 `owned by current user`，就知道该测越权和类型混淆。

### 它还能发现反向信号

脚本会标出 **"拒绝消失"（lost_reject）**——修复后反而放开了的探针。
这可能是补丁缝隙、回退 bug，或者修复引入的新问题。这类反向信号常被忽略，
但价值极高。

## 四、操作 SOP：公告 ↔ 改动 逐条对齐

拿到一个漏洞，按这五步走：

**步骤 1｜提取公告的"承诺"**
把公告里所有具体的断言列出来：哪个入口、哪个字段、哪道检查、影响哪个版本区间。

**步骤 2｜收集改动证据**
按六类信号逐项去捞：版本号、API 签名、新增错误码、默认值、依赖版本、新配置项。

**步骤 3｜做对齐表**

| 公告承诺 | 实际改动 | 结论 |
|---|---|---|
| 修了 X 入口的路径校验 | 新增了 `allowed_dir` 检查 | ✅ 对齐 → 漏洞点确认为此 |
| 声称修了某检查 | 代码/行为里找不到 | ⚠️ **缝隙** → 最高价值 |
| 没提 | 却多了新配置项 | 🔍 静默修复 → 未认领的 1-day |
| 修了 A 分支 | B 分支没同步修 | 🔍 分支遗漏 |

**步骤 4｜对"缝隙"做验证**
缝隙是最值钱的产出。用 `src_patchdiff.py` 在声称已修的版本上跑探针——
如果修复版的响应和修复前一样，说明**这个版本实际没修**。

**步骤 5｜对"对齐"的部分做绕过测试**
确认了校验点之后，拿拒绝消息里的字段坐标去做等价变形。
`guard` 子命令会自动提取这些 token。

## 五、四类"不对齐"及其价值排序

| 不对齐类型 | 表现 | 价值 |
|---|---|---|
| **声称修了，实际没修** | release notes 引用了 PR，但代码/行为里没有 | ★★★★★ 整个版本的用户暴露 |
| **只修了一部分路径** | 修了 HTTP，没修 WS / 回环 / 老版本路径 | ★★★★ 换个入口就能打 |
| **静默修复（公告没提）** | 多了新配置项/新错误码，公告没写 | ★★★★ 未认领的 1-day，竞争为零 |
| **多分支修复遗漏** | 3.17 修了，3.18 没同步 | ★★★ 未升到位的实例全是活的 |

## 六、怎么嵌进工作流

在 P-1 情报前置批次里加一步：

```
P-1 情报前置
  ...
  3. 对每条情报：
     a. 提取公告承诺
     b. ★ 收集六类改动信号，做对齐表        ← 新增
     c. ★ 有缝隙 → 直接在"声称已修"的版本上验证  ← 新增
     d. 有对齐 → 用 src_patchdiff.py 提取字段坐标，做绕过测试
     e. src_variant.py 生成变体假设
```

同时，如果目标有测试环境能同时部署修复前后两个版本（很多 SRC 允许）
——**这是最理想的情况**，直接跑 `src_patchdiff.py` 就是了。

## 七、纪律

- 所有探针限于授权资产、厂商赏金范围、隔离环境
- 探针必须是无害的：只读、随机 marker、可逆
- **不要用破坏性操作来"证明"漏洞**（不删文件、不触发 RCE、不动真实资金）
- 版本判别优先用签名差异这类非破坏性指纹（如 Langflow 的 422）
- 声称已修但未修的，报告时要提供版本证据，不能只凭行为推断
