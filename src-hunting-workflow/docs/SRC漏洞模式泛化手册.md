# 漏洞模式泛化：从「一个洞」推到「一类洞」

> 核心思路：公开报告讲的是**一个点**（某个接口、某个参数、某种触发方式）。
> 但根因通常是**通用的**。把「点」抽象成「模式」，再沿维度展开，就能推导出
> 作者没写、甚至没发现的其他形态。

---

## 一、先说边界：这能做什么，不能做什么

**能做的**：把单篇报告拆解成"根因 + 触发条件"，再按泛化维度系统地列出
"这个根因还可能在哪些地方、以什么形式出现"。产出的是**可测的假设清单**。

**不能做的**：凭空编造漏洞。**推导出来的每一条都是假设，不是漏洞。**
它必须回到测试卡的判据去验证——验证不了就是 `[~]`，记排除理由，不许硬凑。

这条边界必须守住，否则你会陷入"我觉得这里应该有问题"的自我说服，
产出一批无法复现的报告，砸掉平台信誉。

---

## 二、三层提炼法

拿到一篇报告，不要只看"怎么复现"，要拆成三层：

| 层 | 问什么 | 例子（jackson-databind SSRF） |
|---|---|---|
| **触发条件层** | 作者改了什么、走了什么流程 | 提交含 `InetAddress` 字段的 JSON，反序列化时触发 DNS 解析 |
| **根因层** | 为什么会这样，缺了哪道校验 | 反序列化时未限制可解析的主机范围；上一版补丁用黑名单，没堵全 |
| **模式层** | 这个根因在哪些地方还会出现 | 同组件其他反序列化入口；同类库（fastjson/Gson/snakeyaml）；黑名单的各种等价变形 |

**多数人只读第一层，照着复现一遍就交了。价值在第二、三层。**

---

## 三、十二个泛化维度

按历史命中率排序，每个维度都有固定的"操作"和"命中判据"：

| 维度 | 做什么 | 为什么有效 |
|---|---|---|
| **同族 sibling** | 同模块其他接口、PC端/移动端/小程序端/管理端同名接口 | 一个接口有问题，同一批代码写的接口大概率都有 |
| **静默补丁 silent** | 翻 git log，找改动在校验/边界/过滤但描述平淡的 commit | 未认领的安全修复 = 未披露的 1-day，竞争为零 |
| **等价变形 encode** | URL 编码/双重编码、Unicode 归一化、大小写、`/`↔`\`、IP 进制/域名指回、协议大小写 | 黑名单几乎总能绕，这是"修复不完整"类情报的头号突破口 |
| **对称性 symmetry** | 原洞是「读」就测「写/改/删」；是「上传」就测「下载/删除/列举」 | 多数开发只校验了用户看得到的那个方向 |
| **时序 concurrency** | 并发 N 次制造超领/超卖/复用；TOCTOU 竞态 | 单线程测必定正常，必须并发。SRC 逻辑漏洞主力 |
| **信任边界 boundary** | 追问"这个值被谁信任了"——前端传值？第三方回调？内部服务？消息队列？ | 越权/伪造类漏洞的根源都是信任了不该信任的来源 |
| **串联 chain** | CORS+XSS、开放重定向+OAuth、信息泄露+密钥、SSRF+内网服务 | 两个低危拼一个高危，评级跃迁的主要方式 |
| **方法变换 method** | GET→POST/PUT/PATCH/DELETE；HEAD/OPTIONS；`X-HTTP-Method-Override` | 网关按方法做鉴权很常见，改方法常能穿透 |
| **状态机 state** | 跳过前置步骤直达最后一步；乱序；重放已完成步骤 | 前端跳转不等于后端校验 |
| **版本 version** | `/v1/` `/v2/` `/internal/` `/beta/`；接口名加 `-old`/`-bak`；直连后端端口 | 网关拦新版，老接口往往没人管 |
| **参数形态 param_shape** | 负数/0/小数/极大值/null/数组而非标量（类型混淆）/字段重复两次 | 只校验字符串的代码，传数组就绕过了 |
| **生态迁移 ecosystem** | 该组件有 → 同生态其他组件呢？该业务有 → 同行业其他家呢？ | 一次研究多次产出，适合跨目标复用 |

## 四、实战演示

**输入**：`jackson-databind: Incomplete fix for CVE-2026-54514 — SSRF still present`
（根因 = 修复不完整，防护 = 黑名单，类型 = SSRF）

**脚本推导出的 Top 6 假设**：

1. **等价变形（123分）**——黑名单没堵全，试 IP 进制、域名指回、协议大小写、DNS 重绑定
2. **静默补丁（122分）**——翻 git log 找未认领的修复，很可能还有别的洞没被公开
3. **同族（100分）**——其他反序列化入口、其他数据类型是否同样未限制
4. **对称性（85分）**——反序列化方向的洞找到了，序列化方向呢？
5. **信任边界（80分）**——谁调用了它？上游是否可控？
6. **串联（78分）**——SSRF 打到内网后，还能接什么

**输入换成**：某订单接口改 `orderId` 可读他人订单（根因 = 缺失鉴权，类型 = IDOR）

推导立刻变了，Top 变成：同族（118）→ 对称性（108）→ 方法变换（93）→ 老版本路径（90）→ 并发（82）。

**同一套维度，不同根因自动排出不同的优先级**——这就是泛化的价值，它不靠灵感，靠结构。

## 五、工具用法

```bash
# 看完整维度库
python3 src_variant.py dims

# 内置样例跑通
python3 src_variant.py demo --top 6

# 从自己的 JSON 生成假设
python3 src_variant.py gen --file vuln.json --top 12 --out variants.json
```

输入格式：

```json
{
  "title": "漏洞标题",
  "component": "组件名",
  "root_cause": "incomplete_fix",
  "defense": "blacklist",
  "vuln_class": "ssrf",
  "trigger": {"location": "body-json", "param": "字段"}
}
```

可选值：
- `root_cause`：`incomplete_fix` / `silent_patch` / `missing_authz` / `trust_client` / `blacklist` / `race` / `deserial` / `path_traversal`
- `defense`：`blacklist` / `filter` / `waf` / `regex` / `none`
- `vuln_class`：`ssrf` / `sqli` / `idor` / `authz` / `auth` / `upload` / `traversal` / `deserial` / `logic` / `payment` / `coupon` / `inventory`

脚本会根据根因和类型自动加权，输出排序后的假设清单，**每条都带操作和命中判据**。

## 六、怎么嵌进工作流

在《分批执行协议》的 **P-1 情报前置批次**里加一步：

```
P-1 情报前置
  1. 收集 24-72h 内的新披露
  2. src_intel.py 打分排序 → 取 Top 5
  3. ★ 对每条走 src_variant.py 生成变体假设   ← 新增
  4. 假设按分数排进待测队列，逐条验证
  5. 命中 → 单卡深挖；未命中 → 记 [~] + 排除理由
```

**关键纪律**：变体假设必须**先验证再报**。验证方式回到测试卡的判据——
有命中判据和排除判据，不靠"我觉得"。

---

## 七、三个必须防的坑

**1. 假设当结论**
泛化推导很爽，容易让人产生"我已经发现了好几个洞"的错觉。
没复现的就是没发现。**假设数量不写进任何报告**。

**2. 无限发散**
12 个维度 × N 条情报 = 爆炸。对策：每条情报只取 Top 5 假设，
每天总共不超过 10 条待验证，其余归档。发散要有配额。

**3. 忽略"为什么原作者没继续挖"**
作者往往不是没想到，而是**试过没成**。所以推导前先想：
如果这么明显，为什么原作者停在这里？答案常常是"有 WAF"、
"需要特定配置"、"目标侧不具备该组件"。先排除这些，再动手。

---

## 八、一句话总结

公开报告给你的是**一条鱼**，泛化推导给你的是**鱼群的位置**。
但鱼群的位置不等于鱼——还得你自己去捞，捞不到就老实记 `[~]`。
