# SRC 挖洞：自动化分层方案

> 结论先说：**机械重复的部分全部交给程序，人的注意力只花在"判据"和"串联"上。**
> 但有一条硬边界——**逻辑漏洞基本无法自动化**，程序只能帮你穷举，不能替你理解业务。

---

## 一、三层漏斗模型

```
        ┌─────────────────────────────────────┐
        │  第一层：程序穷举（毫秒级 / 千级请求）  │
        │  特征明确、动作重复、无需业务理解       │
        └──────────────┬──────────────────────┘
                       │ 产出：疑似清单（带判定理由）
                       ▼
        ┌─────────────────────────────────────┐
        │  第二层：人工复核（按测试卡判据）       │
        │  确认数据归属 / 排除误报 / 取证        │
        └──────────────┬──────────────────────┘
                       │ 产出：确认的漏洞
                       ▼
        ┌─────────────────────────────────────┐
        │  第三层：人工串联（灵感区）            │
        │  组合漏洞、业务理解、绕过思路          │
        └─────────────────────────────────────┘
```

**关键设计：程序不做最终判定。** 它只输出"疑似 + 判定理由"，最终是否成立由人按测试卡的命中/排除判据决定。这样既提速，又不会把误报直接推向平台。

---

## 二、哪些能自动化，哪些不能（硬边界）

| 环节 | 能否自动化 | 原因 |
|---|---|---|
| 子域名/端口/指纹测绘 | ✅ 完全 | 纯穷举 |
| 常见泄露路径探测 | ✅ 完全 | 特征固定 |
| 组件 CVE 版本比对 | ✅ 完全 | 版本→CVE 是查表 |
| 删凭证未授权探测 | ✅ 高 | 判据明确（响应相似度） |
| 资源 ID 越权批量验证 | ✅ 高 | 有"黄金标准"可对比 |
| 并发类（券/库存） | ✅ 高 | 动作机械，判据是次数 |
| SQL 注入 / XSS 初筛 | ⚠️ 半 | 可初筛，误报多，需人工确认 |
| 验证码爆破 | ⚠️ 半 | 可跑，但需先判断有无锁定 |
| **支付/金额逻辑** | ❌ 不能 | 必须理解业务规则，且不能真造成资金变动 |
| **优惠券叠加/退款** | ❌ 不能 | 依赖业务语义 |
| **多步流程绕过** | ❌ 不能 | 需理解状态机 |
| **SSRF 组合利用** | ❌ 不能 | 需要判断内网有什么可利用 |
| **WAF 绕过** | ❌ 不能 | 需针对规则做创造性变形 |

一句话总结：**程序擅长"有没有"，人擅长"能不能利用、有多严重"。**

## 三、工具用法（src_scout.py）

### 前置

```bash
pip install requests
```

把 Burp 里抓到的请求右键 "Copy to file" 存成 txt，脚本直接读。

### 1. leak — 信息泄露路径探测（对应 E 模块）

```bash
python3 src_scout.py leak --url https://target.com \
    --cookie "session=xxx" --threads 5 --delay 0.3
```

**判据**：状态码 200 + 与随机路径 404 基线相似度低 + 长度达阈值。
404 基线是关键——防止"所有路径都返回 200 的站点"造成全量误报。

### 2. unauth — 删凭证未授权探测（对应 A1 卡）

```bash
python3 src_scout.py unauth --file req.txt --proxy http://127.0.0.1:8080
```

**判据**：删凭证后的响应 与 带凭证响应 相似度高 + 无登录提示 + 非 401/403。
自动处理 Unicode 转义（避免把 `请先登录` 的转义形式漏判）。

### 3. idor — A/B 凭证越权批量探测（对应 A2/A3 卡）

```bash
python3 src_scout.py idor --file req.txt --param orderId \
    --ids ids_b.txt --cookie-a "session=A" --cookie-b "session=B" --delay 0.3
```

**判据（黄金标准对比法）**：
用 A 的凭证访问 B 的资源，与**B 本人访问自己的资源**的响应做相似度对比。
相似度高 = A 真的拿到了 B 的数据。这个判据误报率远低于"看状态码"。

参数替换自动覆盖：query / body-json / body-form / header / path。

### 4. diff — 任意两请求响应对比（辅助判据）

```bash
python3 src_scout.py diff --file req.txt --replace "Cookie: session=B"
```

### 通用参数

| 参数 | 说明 |
|---|---|
| `--threads` | 并发数，默认 5。**SRC 有限速时务必调低** |
| `--delay` | 每次请求间隔，默认 0.2s |
| `--sim` | 相似度阈值，默认 0.85。误报多就调高 |
| `--proxy` | 走 Burp 代理，方便看流量 |
| `--scheme` | 强制 http/https，默认按 Host 判断 |
| `--out` | 结果存 JSON，便于归档进资产库 |

## 四、与分批执行协议怎么衔接

把自动化塞进批次表，人工只需处理剩下的：

| 批次 | 原方式 | 改为 |
|---|---|---|
| P0 资产测绘 | 手工 | **程序**：子域/指纹/泄露路径 |
| P1 越权前 4 卡 | 手工逐卡 | **程序跑 idor + unauth**，人工只复核疑似 |
| P7 注入与上传 | 手工 | **程序初筛**，人工确认 |
| P9 信息泄露 | 手工 | **程序全跑** |
| P5/P6 业务逻辑 | 手工 | **仍手工**（程序帮不上） |
| P3/P4 验证码/JWT | 手工 | 半自动（先判有无锁定） |

**省下来的注意力全部投到 C 模块（业务逻辑）和"串联"上**——那才是 SRC 里真正拉开差距的地方。

## 六、自动化会带来的新问题（要防）

1. **误报噪音**：程序粗判必然有假阳性。对策是程序只出疑似，不直接提交。
2. **触发限速/风控**：SRC 平台常有速率限制。对策是默认低并发 + `--delay`。
3. **污染账号**：批量请求可能触发账号风控。对策是用小号，且控制总量。
4. **跳过理解业务**：全靠程序会让你失去对目标的业务感觉。对策是程序跑完，**人工必须过一遍功能枚举清单**，理解每个接口在做什么。
5. **日志留存**：程序跑的请求会留在 Burp 里，正好作为取证材料，记得开全量日志。

---

## 七、纪律（不变）

- 只在平台授权资产范围内跑
- 不做 DoS、不做社工、不批量拖库、不造成真实资金变动
- `--threads` 和 `--delay` 按平台规则调整
- 程序输出的疑似项，未经人工复验不算漏洞
