## 一句话总结

补上了一个**成本极低、但一直没做的环节**：

> **先认出目标是用什么成熟架构搭的，再拿该架构的已知问题去低频验证。**

认架构几乎零成本——几个响应头、一个 favicon、一条特征路径。
而成熟架构的洞被研究得最透、PoC 最多，是杠杆最高的方向。

## 升级 1：新增 P14 · 成熟架构指纹匹配 + 低频验证

```bash
python3 src_stack.py arch                    # 全部六类
python3 src_stack.py arch --cat "AI/自动化"   # 只看一类
```

### 六类架构池（脚本内置指纹 + 识别方法 + 要点）

| 类 | 成员 |
|---|---|
| 建站/CMS | WordPress、Joomla、Drupal、ThinkPHP、若依 RuoYi、织梦 |
| 后端框架 | Spring Boot、Django、Laravel、FastAPI、Express、Gin、Rails |
| AI/自动化 | Dify、n8n、Langflow、LangChain/LangGraph、FastGPT/MaxKB/RagFlow |
| 中间件网关 | Nginx、Traefik、Kong、Tomcat |
| 运维 DevOps | Jenkins、GitLab、Grafana、SonarQube、Gogs/Gitea |
| 数据缓存 | Redis、Elasticsearch、MongoDB |

每条都给了**指纹**（看什么路径/响应头）和**识别方法**（怎么确认）。

例：
- WordPress → `wp-login.php` / `wp-content/` / `readme.txt`，icon_hash 定位
- Spring Boot → `/actuator` / Whitelabel Error Page
- FastAPI → `/docs` / `/openapi.json`（文档端点未授权即暴露全部接口）
- FastGPT/MaxKB/RagFlow → 国内 SRC 高频，**多租户隔离是薄弱点**

### 三条引导提问

1. **这个站是用什么搭起来的？** 响应头、favicon icon_hash、特征路径、错误页
2. **认出来之后，版本号是多少？** 版本串是闭源/半闭源环境唯一坐标
3. **这个版本的已知问题，在目标上还在吗？**

### 差异化不在"找新洞"

成熟架构竞争最大，大家都在盯。值钱的只有两件事：

- **① 老版本没升** —— 补丁已发但目标没升
- **② 非默认配置** —— Langflow 默认未授权自动登录，
  才让 CVE-2026-5027 无需凭证即可打

**插件/扩展是主战场**：建站类框架核心修得快、插件没人管。
（ASD 一次警报列出 17 个 WordPress 插件 CVE）

## 升级 2：低频验证子步骤（P14 内）

**原则**：只读、随机 marker、可逆、**单请求**、0.2-0.5 req/s

| 顺序 | 动作 |
|---|---|
| 1 | 指纹确认（响应头 / icon_hash / 特征路径 200） |
| 2 | 版本确认（CHANGELOG / `/api/version` / 错误页） |
| 3 | **只验证已知问题在当前版本是否仍存在——不构造新 payload** |
| 4 | 命中即停，不扩展、不遍历 |

**禁止**：不扫全站路径（只打架构特征路径）、不并发、不爆破、不下载、不做破坏性验证。

**判据**：命中 = 已知问题复现出客观差异；未命中 = 版本已修 / 配置已关 / 不在范围。

### 为什么必须低频

架构类问题通常 **1-3 个请求**就能确认。批量扫既没必要，又会触发风控。

**被 WAF ban 之后，真正的深挖就做不了了**——
低频不只是合规，是**保护后续测试能力**。

## 升级 3：P-1 补四语言升级敞口对照

原来 P-1 只问"是否升级"，没有给**逐语言的对照表**。现在补上：

| 语言 | 近期关键升级 | 反向敞口 |
|---|---|---|
| **Python** | 3.13 移除 19 个模块；3.14 multiprocessing 默认改更安全 | 3.13 前用这些模块**永无补丁**；旧默认 fork 不安全 |
| **Java** | JDK 17 JEP 403 强封装；11 移出 JAXB/JAF | 迁移需 `--add-opens` **永久开口子** |
| **Go** | 1.22+ net/http 路由更严格 | 旧版通配匹配可被绕过 |
| **JS** | Node 20+ 权限模型实验性引入 | 默认无权限模型 |

**核心推理（可复用）**：

> 厂商把一个行为从 A 改成 B，通常是因为 A 不安全。
> 那么**还停留在 A 的系统就是敞口**。

这个推理方向不限于上表四行——任何语言/框架的版本变更都能套。

## 已知边界

1. **架构池的指纹是静态的**，没有实际验证过每个指纹在当前版本下是否仍有效。
   尤其是 icon_hash 值可能随版本变化。
2. **低频速率 0.2-0.5 req/s 是估计值**，未对照具体平台限速。
   实际执行时仍需以 `src_gate.py rate` 的平台上限为准（取更严格的）。
3. 架构池偏向国内 SRC 常见目标（若依、织梦、FastGPT 等），
   国际平台（HackerOne）的目标覆盖可能不足。
