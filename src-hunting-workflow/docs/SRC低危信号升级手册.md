# 低危信号升级手册：从低危挖到高危

> 核心判断：**低危漏洞的价值不在它本身，而在于它证明了"某一层的防护缺失"。**
> 而防护缺失通常是系统性的——同一套代码、同一个开发、同一套配置，不会只在一个地方松懈。

---

## 一、先校准一下这个判断

你的判断在**大多数情况下成立**，但要加两条限定，否则会陷进另一个坑：

**成立的部分**：防护缺失有"同源性"。一个接口没做鉴权，往往不是它单独忘了，而是这个服务/这个模块/这个开发写的一批接口都没做。一个地方泄露了路径，说明错误处理的配置是全局没关的。所以**低危是探针，指向的是根因**。

**不成立的部分**：有些低危确实是孤立的——比如某个静态页面的 Cookie 少了个 Secure 标记，背后什么都没有。

**所以操作原则变成**：低危不是终点，是**触发排查的开关**。但要设止损——排查一轮无果就老实记 `[~]`，不要硬凑。否则你会为每个低危耗掉半天，反而挤占了真正出高危的时间。

---

## 二、升级三动作（固定套路）

拿到一个低危，按顺序做三件事：

### 动作 1：找根因
问一句"**为什么会这样**"。
不是"这个接口没鉴权"，而是"这个接口没鉴权，说明什么防护机制不存在？"

### 动作 2：横向扩展
同一个根因，在别的地方是不是也一样？
- 同接口的**其他 HTTP 方法**（GET 能查 → PUT/DELETE 呢）
- 同模块的**其他接口**
- 同服务的**其他子域 / 老版本接口**（v1、v2）
- 管理端的**对应接口**
- **批量 / 导出接口**（危害直接放大一个量级）
- 移动端 / 小程序端（常常是另一套鉴权，更松）

### 动作 3：纵向串联
两个中低危能不能串成高危？
例：CORS 配置不当 + 任意一个 XSS = 可读取已登录用户的全量数据
例：信息泄露 → 拿到源码 → 源码里有硬编码密钥 → 接管存储桶

## 三、映射表（重点）

| 低危信号 | 背后根因 | 升级动作 | 可达级别 |
|---|---|---|---|
| **用户名/手机号可枚举** | 认证响应未统一 + 无风控 | 测密码爆破有无次数限制、验证码可爆破、找回 token 可预测 | **高危**（任意用户登录） |
| **报错页泄露路径/SQL片段/堆栈** | 错误处理未收敛、debug 未关 | 顺着泄露的 SQL 找注入点；找其他报错触发点；试 `/actuator`、`/debug` | **高危**（注入 / 源码泄露） |
| **版本号/指纹泄露** | 响应头未清理 | 直接比对 CVE，找对应组件的历史利用 | **严重**（RCE） |
| **Swagger / 接口文档暴露** | 文档无访问控制 | 文档里每个接口逐个跑 unauth + idor | **高危**（批量未授权） |
| **开放重定向** | URL 参数未做白名单 | 同一参数试 SSRF（内网、169.254.169.254）；查 OAuth 回调是否可控 | **中高危**（SSRF / 账号劫持） |
| **Cookie 缺 HttpOnly/Secure、CORS 允许 \*** | 安全配置整体松懈 | CORS 配合读用户数据；测 session 固定、token 长期有效、退出不失效 | **中危** |
| **前端 JS 硬编码密钥** | 密钥管理不规范 | 先确认这是什么密钥——OSS/COS 的 AK/SK？短信接口？支付密钥？ | **严重**（存储桶接管 / 伪造支付） |
| **单字段越权（只读到昵称）** | 该接口鉴权缺失 | 同接口其他方法、其他字段、子资源、批量接口 | **高危**（全量数据） |
| **验证码位数少/有效期长** | 验证码策略弱 | 测有无次数限制与锁定 → 可爆破 → 任意用户注册/登录 | **高危** |
| **短信接口无频率限制** | 无风控 | 配合验证码爆破或可预测 → 组合利用 | **中高危** |
| **单处信息泄露（脱敏不全）** | 脱敏逻辑不统一 | 找批量/导出接口，看能否一次拿全量 | **高危**（批量数据泄露） |
| **.git / .svn 泄露** | 部署流程不规范 | 还原源码 → 找硬编码数据库密码、内网地址、未上线接口 | **严重** |
| **上传点仅前端校验** | 校验在客户端 | 改包绕过：类型绕过、路径穿越、解析漏洞 | **高危**（getshell） |
| **目录遍历只读到一个文件** | 路径未做规范化 | 试读配置文件、私钥、数据库备份 | **高危** |
| **未授权但数据不敏感** | 该接口鉴权缺失 | 找同服务其他接口、找同源的需鉴权接口 | **中高危** |

## 四、发现一个越权后的标准扩展动作

这是命中率最高的一条路径，单独列出来：

1. **换方法**：GET 能越权 → POST/PUT/DELETE 全部试一遍
2. **换接口**：同模块所有接口套同一个参数替换手法
3. **换端点**：PC 端能越权 → 移动端 API、小程序 API、老版本 `/v1/` 分别试
4. **找批量**：有没有列表/导出接口？`pageSize` 调大能拿多少？
5. **找子资源**：主资源校验了，子资源 ID 换掉呢？
6. **找管理端**：`/admin` 下同名接口，用普通 token 打

> 一个接口越权是低危，**同一根因的一批接口越权就是高危**。这也是为什么 SRC 上同一个洞，有人报低危有人报高危——差别在于有没有做扩展。

## 五、两个反面提醒

**不要夸大危害凑评级。**
评级靠的是危害证明，不是形容词。写"可导致大量用户数据泄露"之前，先证明你真的能拿到那么多。被平台打回几次，信誉分比多一个高危值钱。

**但合并是合理且被鼓励的。**
同一根因造成的多个低危，合并成一个报告、按整体危害定级——这不是凑，这是**准确反映真实影响面**。报告里要写清楚"以下 N 个接口均存在同一问题，合计影响范围是……"。

## 六、怎么嵌进现有工作流

在《分批执行协议》的**单卡深挖模式**里加一步：

原四步：确认可利用 → 确认影响面 → 取证 → 写报告

改成：
1. **确认可利用**
2. **判定初始级别**
3. **若 ≤ 中危 → 走升级三动作**（找根因 / 横向扩展 / 纵向串联）
4. **重新判定级别**
5. 取证 → 写报告

同时把本手册的映射表加到测试卡的**排除判据**旁边：判为 `[~]` 之前，先扫一眼映射表，确认没有遗漏升级路径。
