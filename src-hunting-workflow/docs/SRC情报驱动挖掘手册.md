# SRC 情报驱动挖掘手册：从最新披露挖到新洞

> 核心判断：**老 N-day 已被挖烂，最新披露才是富矿。**
> 但真正的价值不在"拿别人的洞去打目标"，而在**看补丁怎么修的，找补丁的缝隙**。

---

## 一、先校准这个判断

你的判断成立，而且要再往前推一步。

**第一层：用别人的洞打你的目标（N-day 复现）**
新披露的漏洞，从披露到目标厂商修复之间有个**时间窗**。这个窗口期就是机会——你比厂商快，就能交。价值中等，但竞争也激烈，因为同一条情报所有人同时看到。

**第二层：从补丁里挖出新洞（真正的富矿）**
这才是最值钱的。三个入口：

1. **修复不完整（Incomplete Fix）**
   厂商修了，但没修干净。GitHub Advisory 里这类条目极多，标题常带 `Incomplete fix for CVE-XXXX`、`Bypass`、`still present`、`partially`。
   → 这说明**原漏洞点还在，只是加了层过滤**，绕过的可能性很高。

2. **静默安全补丁（Silent Patch）**
   很多开源项目修漏洞时故意用模糊的 commit message：`improve buffer check`、`fix edge case`、`refactor`、`hardening`。
   → 这类 commit 就是**没被公开认领的 1-day**，竞争几乎为零。

3. **补丁引入的新问题**
   修复代码本身可能有 bug（越界、逻辑错误、新分支未校验）。
   → 看 diff 时不只看"加了什么检查"，还要看"这个检查本身对不对"。

**第三层：从情报反推你目标的同类问题**
某组件曝出"未授权访问"，说明这类组件的**默认配置有坑**。你去查目标上同系列的其他组件、同类部署方式，往往能找到同源问题。

## 二、补丁对比（Patch Diffing）SOP

这是第二层的核心手艺，五步：

### 步骤 1：定位修复 commit

```bash
# 开源项目：直接搜修复记录
git log --grep="CVE-2026-XXXX"
git log --grep="security" --oneline
git log --grep="fix" --since="2026-09-01"

# 找到后看具体改了什么
git show <commit-hash>
```

**静默补丁怎么找**：不搜关键字，改成按**文件和函数**筛——找那些改动集中在校验/边界处理/输入过滤、但描述很平淡的 commit。

### 步骤 2：读 diff，反推漏洞类型

看 diff 时固定问三个问题：

| 观察点 | 反推 |
|---|---|
| 新增了长度/边界检查 | 原处是越界读写（OOB） |
| 新增了空指针判断 | 原处是 UAF / 空指针解引用 |
| 新增了权限/身份校验 | 原处是**未授权或越权** |
| 新增了对某字符/路径的过滤 | 原处是**注入或路径穿越** |
| 改了内存释放顺序 | 原处是 UAF |
| 新增了类型/范围校验 | 原处是整数溢出或类型混淆 |

**重点看"新增校验"**——它直接告诉你原来的洞在哪、怎么触发。

### 步骤 3：判断补丁是否完整

这是出活的关键。检查：

- 只修了触发路径 A，路径 B/C 呢？
- 只过滤了 `../`，那 `..\`、URL 编码、双重编码呢？
- 只校验了 GET，POST/PUT 呢？
- 只修了主接口，老版本 `/v1/`、移动端接口呢？
- 修复是黑名单还是白名单？**黑名单基本都能绕**。

### 步骤 4：写 PoC

在**未修复版本**上验证。Web 方向通常直接构造请求即可，不需要二进制工具。

### 步骤 5：比对你的目标

目标用的是不是受影响版本？版本在不在区间内？多数 SRC 要求提供**验证证据**，不能只报版本号。

**二进制项目**（Windows/闭源）才需要 BinDiff、Diaphora、ghidriff 这类工具。Web 方向的 SRC 基本用不上，别在这上面浪费时间。

## 三、情报源清单（分层）

### 一手源（披露最早，抢时间窗靠它）

| 源 | 说明 |
|---|---|
| **GitHub Advisory Database** | 开源组件漏洞，覆盖 npm/pip/Maven/Go/RubyGems。**重点是它带"Incomplete fix"标记** |
| **oss-security 邮件列表** | openwall.com/lists/oss-security，开源项目一手披露 |
| **Full Disclosure** | seclists.org/fulldisclosure |
| **NVD / MITRE CVE** | 权威索引，有 API 和 RSS |
| **CISA KEV 目录** | **已被在野利用**的漏洞列表——说明真能打，优先级最高 |
| **CNNVD / CNVD / CNCERT** | 国内权威，中文，含通报 |

### 二手源（带分析，帮你省时间）

| 源 | 说明 |
|---|---|
| **Exploit-DB** | 有公开 PoC 的漏洞，可直接复现 |
| **Rapid7 Blog** | 分析质量高，常带检测脚本 |
| **The Hacker News** | 快，适合扫标题 |
| **厂商公告** | MSRC、Oracle CSPU、Red Hat、GitLab、Atlassian |

### 社区源（含"不是人人能看"的部分）

| 源 | 说明 |
|---|---|
| **先知社区** xz.aliyun.com | 中文高质量，部分内容需权限 |
| **T00ls** | 邀请制，国内一线实战 |
| **补天论坛** forum.butian.net | SRC 视角，贴平台偏好 |
| **安全客 / FreeBuf** | 综合资讯 |
| **Twitter/X 安全研究者** | Project Zero、tiraniddo 等，一手披露常在这里首发 |
| **r/netsec、Hacker News** | 英文社区讨论 |

> 你说的"不是人人有资格看"——T00ls 邀请制、先知部分内容、以及 CVE ** embargo 期**（披露前只有少数人拿到详情）都属于这类。这类信息差就是时间窗。

### 自动化拉取

- **cve-search**（github.com/cve-search/cve-search）：本地 CVE 数据库 + 搜索
- **cve-monitor**：按关键词订阅推送
- **Google Alerts / Feedly**：订阅厂商公告 RSS，省得每天刷

## 四、用 src_intel.py 做优先级排序

情报太多会淹死你。脚本做的事是：**按你的技术栈过滤 + 按价值打分排序**，输出"今天该打哪几条"。

```bash
# 先验证打分逻辑（内置样本，无需网络）
python3 src_intel.py demo --top 10

# 导入你整理的 JSON 打分
python3 src_intel.py load --file advisories.json --top 15 --minscore 60
```

### 打分权重（在脚本里可改）

| 信号 | 权重 | 理由 |
|---|---|---|
| ★ 修复不完整 / 可绕过 | **+60** | 极可能是新洞，最高价值 |
| 已在野利用（KEV） | +50 | 说明真能打，不是理论漏洞 |
| 技术栈命中 | +30 | 你目标上真有这个组件 |
| 类型命中（RCE/未授权/越权） | +25 | 你想要的类型 |
| 静默安全补丁 | +25 | 1-day 富矿，竞争少 |
| 新（7 天内） | +20 | 时间窗还在 |
| 有公开 PoC | +20 | 可直接复现 |
| **无公开 PoC** | **+15** | 说明要自己写，**竞争少** |
| DoS 类 | **-40** | 多数 SRC 不算分或评级低 |
| 一年以上老洞 | -15 | 已被挖烂 |

**注意"无公开 PoC"是加分项**——这条反直觉但很重要。有 PoC 意味着所有人都能复现，你抢不过；无 PoC 意味着会的人少，你做补丁对比写出 PoC，就是独家。

### 实测排序结果

内置样本跑出来：在野利用的 GitLab 路径穿越 160 分居首，修复不完整的 jackson-databind（SSRF）150 分第二，2021 年的 log4j 被压到 60 分，DoS 类直接被过滤掉。逻辑符合预期。

### 数据格式

```json
[{
  "cve": "CVE-2026-XXXXX",
  "component": "jackson-databind",
  "title": "Incomplete fix for CVE-2026-54514 ...",
  "severity": "High",
  "published": "2026-09-28",
  "poc_public": false,
  "kev": false,
  "url": "https://..."
}]
```

在 `intel_profile.json` 里把 `stack` 改成你常遇到的组件，命中率会明显提升。

## 五、怎么嵌进现有工作流

在《分批执行协议》里**新增一个前置批次 P-1**，放在 P0 之前：

```
P-1  情报前置（每天开工前 20 分钟）
     1. 跑一遍情报源，收集 24-72 小时内的新披露
     2. src_intel.py load 打分排序
     3. 取 Top 5，逐个对照目标资产：
        - 目标用了这个组件吗？版本在区间内吗？
        - 有 PoC → 直接复现验证
        - 无 PoC → 做补丁对比，自己写 PoC
     4. 命中则直接进单卡深挖模式
     5. 无命中则照常走 P0 → P1...
```

**P-1 和常规批次的关系**：情报驱动是**机会主义**——有就插队打，没有就走常规穷举。两者不冲突，是叠加关系。

## 六、情报驱动的坑（要防）

**1. 同质化竞争**
同一条情报，几百人同时看到。谁先交谁得分，晚交就是重复。对策：抢时间窗，**优先打那些无公开 PoC 的**（你会的人少）。

**2. 版本判定不严谨**
报"目标用了受影响版本"但拿不出证据，会被打回。对策：必须提供版本证据（响应头、报错页、favicon hash、JS 库版本）。

**3. 只看情报，不做穷举**
情报驱动覆盖面窄，它只能告诉你"这个组件有问题"，不能告诉你"这个目标还有什么别的洞"。对策：**情报是加分项，不是替代品**，常规批次照走。

**4. 忽略国内源**
很多国内 SRC 的目标用的是国内组件和二次开发框架，国外情报覆盖不到。对策：CNNVD、先知、补天要一起看。

**5. 追新追到失控**
新披露每天几十条，全追就别干别的了。对策：用 `--minscore` 卡阈值，每天只打 Top 5，其余归档。

---

## 七、纪律（不变）

- 情报只是线索，**是否在授权范围内、是否真能复现**，仍需你自己验证
- 补丁对比写出的 PoC，只在授权目标上验证
- 不利用未公开（0-day）情报去打任何未授权系统
-  embargo 期内的信息不得外传
