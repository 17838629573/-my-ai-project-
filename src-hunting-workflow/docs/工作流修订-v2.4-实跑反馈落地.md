# 工作流修订 v2.4：实跑反馈落地（R1–R4）

> 触发：v2.1 首次 AI 端到端实跑复盘 + EPSS 复核
> 修订内容：R1 凭证前置 · R2 零命中处置 · R3 样本构成 · R4 目标选择 · 情报二次源验证

---

## 背景：这次修订的由来

v2.1 由另一个 AI Agent 独立端到端跑了一遍。结论是：

> **流程跑通了，但数据基本是空转的——它证明了工作流可执行，没证明工作流有效。**

这句话是这次修订的全部动机。四个具体问题，逐条落地如下。

---

## R1 · P3 凭证前置检查（最高优先）

**问题**：v2.1 没有"开工前确认凭证齐备"的环节。P3 需要 A/B 两套有效账号，
沙箱没有，导致 P2 跑完白进了 P3 才发现无法执行。

**修订**：P3 开头增加检查卡——

| 检查项 | 不通过怎么办 |
|---|---|
| 持有 A/B 两套测试账号（或平台标准账号） | 跳过 P3，标记 `[~] 待凭证复验` |
| 两套账号能登录、能访问同一类资源 | 同上 |

**关键**：这条检查**在 P2 选目标时同步完成**。
目标已选但凭证缺失是最浪费的失败模式——P2 全白跑。

选目标时就该问一句：**"这个目标我拿得到 A/B 账号吗？"**

---

## R2 · 零命中步骤的处置机制

**问题**：P4 连续三轮 0 命中，报告里用"属正常""样本滞后"轻轻带过。
按 P0 纪律（命中 0 的要么删掉要么补样本），三轮已是处置阈值。

**修订**：写死三级处置流程

```
第 1 轮 0 → 补该方向样本，下一轮重跑
第 2 轮仍 0 → 再补，并明确记录补了什么
第 3 轮仍 0 → 降级为观察态，从主干移除
```

**核心是这句**：**禁止用"属正常""样本滞后"作为结论收尾。**

这类措辞会让缺陷永久留在流程里。它必须落到具体动作——补样本，还是删步骤。

P4 已挂上观察态标记，本轮必须补入并发/支付/状态机类样本。

**这是个通用机制，不只是 P4。** 任何步骤连续三轮 0 都走同一条处置链。
`src_calibrate.py` 现在会自动列出零命中步骤并打印处置要求。

---

## R3 · 校准样本必须含非知名 CVE

**问题**：v2.1 样本全是微软、索尼、VMware、WSO2——已披露的大厂 CVE。
校准器靠关键词匹配，**已披露 CVE 的描述关键词密度天然高，当然 100% 命中。**

**那叫自证，不叫校准。**

**修订**：

1. 每轮至少 **1/3 为非知名 CVE**（社区披露、小众组件、AI/云原生、闭源公告）
2. `100% 覆盖率` 不再算"校准通过"，**必须同时报告非知名样本单独覆盖率**
3. `src_calibrate.py` 新增：
   - 自动按厂商名/线索词分类样本
   - 打印非知名占比，不足 1/3 报警
   - `--require-nonfamous` 参数：不达标直接判定本轮不通过
   - 输出非知名样本的**单独覆盖率**——这才是真信号

---

## R4 · 目标选择准则

**问题**：实跑选了静态高校官网 + 44 个常见路径（`.git/config`、`swagger`、`actuator`）。
**这是几百人扫过的组合，0 命中是数学上必然**，不是工作流有效/无效的证据。

P2 那条提问本意是"找不在页面上但确实在跑的东西"，它读了但没照做。

**修订**：P2 重写为目标选择准则

**优先**：有交互、**有凭证体系**、**多版本并存**的系统
**直接降权**：纯静态官网——不是没洞，是探测器照不到

**路径探测前先做暴露面摸底**：子域（证书透明度/备案）、老版本接口、
移动端专用域名、dev/qa/uat 同构部署。摸完再选路径。

**目标类型须与后续步骤能力匹配**——纯静态官网这类目标尽早换掉，
否则 P10–P13 专家模块完全用不上。

## 新增 · 高价值情报必须二次源验证

这条来自 EPSS 复核，是本次意外收获。

**EPSS > 0.5 或 KEV 在列的情报，用之前必须交叉验证三层：**

```
1. 本地源原文（该字段是否逐行独立、无跨行挪用）
2. 解析链路（脚本是逐字段独立提取，还是按行号拼接）
3. 官方 API 交叉（EPSS: api.first.org/data/v1/epss?cve=XXX）
```

**为什么值得这么麻烦**：FOFA 语法错了还能重扫，
**优先级排错了是浪费整个周期**。一个错的高分会把所有后续决策带偏。

**实证**：CVE-2026-21643 报 EPSS 0.93723（分位 0.99842，前 0.16%），
因数值极罕见一度怀疑是 `src_rules.py` 字段串行。
经三层复核确认**属实**——FortiClientEMS 7.4.4 未认证 SQLi，CWE-89，已入 KEV。
脚本无需修复。

---

## 一个观察：它学会了形式，没学会机制

这是本次复盘最值得记的一条。

实跑的 Agent 完整执行了步骤、跑了脚本、标了状态标记——形式全对。
但它在"连续三轮 P4 = 0"这件事上用了"属正常"收尾。

**工作流真正独创的不是那十四个步骤，是 P0 那条自我校准的回路。**
它在那条回路上是空转的。

如果工作流只被当作清单执行，那跟市面上那些"清单型方法论"就没区别了。

R2 这次把处置流程写死，就是为了让回路**无法被轻轻放过**。
