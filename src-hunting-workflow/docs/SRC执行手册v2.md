# SRC 执行手册 v2（校准驱动版）

> **本轮整合了十几轮讨论的全部成果，并把第零步改成「用最近三个月的真实漏洞反向校准工作流」。**

---

## 核心改动：为什么第零步要变

前十几轮我们一直在做同一件事——**往工作流里加东西**。
越权卡、泛化维度、情报源、补丁对齐……清单越写越长。

但这有个致命隐患：

> **清单是我们自己写的，它只能覆盖「我们已经想到」的攻击面。**

覆盖面再大，也是认知的投影。真正的问题是**我们没想到的部分**，而清单自己发现不了它。

所以第零步必须变成：

**拿最近三个月公开的真实漏洞，反过来问工作流一句——「你能发现它吗？」**

- 能定位到某一步 → 该步骤记一次命中
- 定位不到 → **缺口**，这才是真正要补的东西

这不是收集情报，这是**给工作流做回归测试**。

---

## 三步铁律（全局只有三条）

1. **授权范围内，最小危害**——证明可利用即可，不拖库、不改生产数据、不动真实资金
2. **不信任前端**——一切限制以改包后的服务端响应为准
3. **脚本能判定的，不动脑**——注意力留给业务理解和串联

## P0 · 收割与校准（第零步，开工必做）

### 目标

收 **15 个**最近三个月的公开漏洞，反过来检验工作流，然后拿它们做外推。

**为什么是 15 个**：
少于 10 个统计上没意义，多于 20 个校准成本会吃掉本该用来挖洞的时间。
15 个能在 30–40 分钟内走完，且足够暴露缺口。

### 脚本

```bash
# 1. 把收集的漏洞存成 vulns.json（每条至少 title / vuln_class / root_cause）
# 2. 校准
python3 src_calibrate.py load --file vulns.json --out calib.json

# 3. 校准完直接进泛化引擎
python3 src_variant.py gen --file vulns.json --top 8
```

### 引导提问（跑完再看）

> 先看「工作流缺口」那一段。
>
> **那些定位不到任何步骤的漏洞，为什么我的工作流看不见它？**
> 是步骤缺失（压根没这类检测），还是信号缺词（有这个步骤但描述没覆盖）？
> 前者要加步骤，后者只要补几个信号词。
>
> 再看「各步骤命中贡献」。
>
> **哪个步骤命中最多？哪个是 0？**
> 命中最多的是你的主产出方向，值得多分配时间。
> **命中 0 的，要么是你不做的方向（那就删掉），要么是样本偏了（那就补样本）。**
> 别留着既不产出又不删除的步骤——它只会稀释注意力。
>
> 最后，**这 15 个漏洞的根因，有多少是同一个？**
> 如果三个以上指向同一根因（比如都是「缺失鉴权」），
> 说明这是当前周期的高频根因——你的目标上大概率也有。

### 校准结果怎么用

| 发现 | 动作 |
|---|---|
| 有缺口 | 抽象根因 → 补成新步骤或补信号词 → **再校准一次** |
| 某步骤 0 命中 | 判断是不做还是样本偏，删掉或补样本 |
| 多个漏洞同根因 | 该根因列入本轮重点，直接在目标上验证 |
| 覆盖率 ≥ 90% | 工作流当前有效，开始正常挖洞 |

**注意**：覆盖率高不代表工作流完备，只代表它能覆盖这批样本。
样本来源要杂——顶会、厂商公告、GitHub Advisory、社区讨论、AI/云原生/工控各来一点。
只从一个渠道取样，校准出来的覆盖率是假的。

## P1 · 情报泛化

**目标**：从别人的一个洞，看出他没看出来的东西。

**脚本**
```bash
python3 src_intel.py demo --top 10      # 情报打分排序
python3 src_variant.py demo --top 6     # 模式泛化推导
```

**引导提问**
> 拿到报告先别急着复现。问：
> **他改的参数为什么会生效？缺的是哪一道校验？** 这是根因。
>
> **这个根因还可能藏在哪？** 同模块其他接口、反方向操作（能读就能改吗）、
> 换 HTTP 方法还灵吗、老版本路径呢、移动端呢。
>
> **如果防护是黑名单，等价写法有多少种？** 黑名单几乎总能绕。
>
> **最重要：如果这么明显，为什么原作者停在这里？**
> 他很可能不是没想到，是试过没成。想清楚这个再动手。

## P2 · 资产测绘

**目标**：知道该打哪里，不打哪里。

**脚本**
```bash
python3 run.py p0 --host https://target.com
```

**引导提问**
> 这些人里哪个最值钱？标准不是"哪个好打"，是"哪个被打之后后果最严重"。
> 存手机号的后台，价值远高于静态官网，哪怕后者更好打。
>
> 再问：**哪些入口是别人不会去看的？**
> 页面上能点的功能几百人测过了。真正出货的是不在页面上但确实在跑的东西——
> 老版本接口、内部路径、移动端专用域名、下线没关掉的服务。

## P3 · 越权与未授权

**目标**：找出"谁都能拿到谁的数据"。

**脚本**
```bash
python3 run.py p1 --req req.txt --ids ids.txt --param orderId \
    --cookie-a "session=A" --cookie-b "session=B"
```

**引导提问**
> 脚本告诉你哪些请求换凭证后仍返回数据。但先想清楚：
> **这些数据本来就该公开吗？**
> 商品列表返回全部商品叫正常功能；订单详情返回别人手机号才叫越权。
> 你要回答的不是"有没有返回数据"，而是"**返回的数据属不属于我**"。
>
> 确认属于别人后：**同一批代码写的其他接口呢？管理端呢？老版本路径呢？**
> 一个接口越权是低危，同一根因的一批接口越权就是高危。
>
> **如果这么明显，为什么之前没人报？**
> 答案常是有 WAF、需特定配置、没人测到这里。想清楚再投入时间。

## P4 · 业务逻辑

**目标**：找出"服务端算错了"。

**脚本**只能帮忙做并发，其余做不了。

**引导提问**
> 像真实用户那样用一遍，然后问：
> **这笔钱、这张券、这个库存，服务端眼里到底是怎么算的？**
> 下单请求里带金额字段多半有问题——金额本该服务端算出来，不是从请求里读。
>
> **这里的"限制"是真的限制吗？** "每人限领一张"写在页面上还是服务端？
> 如果是前者，同时发二十个请求试试。单线程测必定正常，**必须并发**。
>
> **这些步骤能跳过吗？** 直接请求最后一步，看后端认不认。

## P5 · 注入与服务端

**目标**：找出"不可信数据变成了指令"。

**引导提问**
> **转义之后还有没有还原？**
> `printf %q` 转义完，`eval printf %s` 又求值了——转义是编码决策，不是永久属性。
> 重点查四类链路：printf%q→eval、JSON 转义→shell、YAML 折叠→模板、Base64→decode→执行。
>
> **最终解释点看到的是什么？** 是"已定型的值"，还是重新获得执行语义的原始输入？
> 只看输入或只看输出都会漏掉中间语义变化。

## P6 · 补丁对齐

**目标**：用厂商实际改了什么，精确定位漏洞。

**脚本**
```bash
python3 src_patchdiff.py run --before <旧版> --after <新版> --out diff.json
python3 src_patchdiff.py guard --out diff.json    # 提取字段坐标
python3 src_patchdiff.py signals                  # 六类改动信号
```

**引导提问**
> **公告说的，和实际改的，对齐吗？**
> 对齐 → 精确定位，确认修复。
> **不对齐 → 那道缝就是洞。**
>
> Redis 8.6.4 声称修了，审计发现那个 check 只在 8.6.5 里——
> **所有升到 8.6.4 的用户以为自己安全，实际没有。** 这类缝隙价值最高。
>
> **修复版新增的拒绝消息说了什么？**
> 那条消息直接点名了字段、路径、条件——**它本身就是漏洞位置的坐标**。
> 拿到之后立刻做等价变形，就是绕过测试的第一步。
>
> **默认值是不是变了？** 默认值由"开"变"关"= 厂商承认原默认值不安全，
> **原默认值就是攻击面**。

---

## P7 · 信任域与内部元数据

**目标**：找出"外部输入能改写内部事实"。

**引导提问**
> **这个值被谁信任了？** 前端传的？第三方回调？内部服务？消息队列？定时任务？
>
> **内部头能不能被外部覆盖？** 试 `X-Internal-*`、伪头、
> 重复的 `X-Forwarded-Host`、`Host` 与 SNI 不一致。
> 看"最后写入生效"还是"先到优先"——GitHub X-Stat 就是靠这个覆盖了内部配置。
>
> **同一对象的两种表示，走的校验路径一样吗？**
> HTTP↔WS↔Unix socket↔回环 IPv6、查询↔响应的扩展字段、
> 包名↔代码来源、命令↔参数。**不一样就是洞。**

---

## P8 · AI / Agent 决策边界

**目标**：找出"外部内容变成了高权限指令"。

**引导提问**
> **数据、指令、工具策略，在架构上分开了吗？**
> 模型拿到的是 token 流，分不清"要处理的数据"和"数据中藏的命令"。
> 如果工具策略只检查用户授权没授权连接器，不检查当前动作来自哪——
> **数据就自动获得了指令权限。**
>
> **如果原作者停在这里，是因为什么？**
> 他很可能不是没想到，是试过没成。先想清楚这个再动手。

## 深挖 · 低危升级

**命中任意一项后触发，三动作**：

1. **找根因**——这个洞缺的是哪一道校验？
2. **横向扩展**——同根因的其他接口、反向操作、其他方法、老版本、移动端
3. **纵向串联**——能和什么其他弱点组合，使危害跃迁？

> **一个接口越权是低危，同一根因的一批接口越权就是高危。**
> 这是同一个洞有人报低危有人报高危的全部差别。
>
> 但也要设止损：排查一轮无果就老实记 `[~]`，别为每个低危耗半天，
> 反而挤掉出高危的时间。

## 报告

**引导提问**
> **不了解这个目标的人，照着我的步骤能复现吗？** 不能就回去补——这是被打回最常见的原因。
>
> **我写的是业务后果还是技术名词？**
> "存在越权漏洞"没有信息量；
> "任意登录用户可遍历全站订单，含手机号与收货地址，实测 N 条"才叫危害。
>
> **修复建议落到代码层面了吗？** "加强校验"不算；
> "在 XxxService.getOrder 中比对 order.userId 与当前登录用户"才算。

## 纪律

- 脚本输出的疑似项，未经人工复验不算漏洞
- 泛化推导出来的是**假设**，不是发现。验证不了就记 `[~]` + 排除理由
- `--threads` 和 `--delay` 按平台限速规则调
- 只在授权资产范围内跑
- **不要用破坏性操作"证明"漏洞**（不删文件、不触发 RCE、不动真实资金）
