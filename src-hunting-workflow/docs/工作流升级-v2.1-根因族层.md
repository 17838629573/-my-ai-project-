# 工作流升级 v2.1：规则库挖掘层的并入

> 触发：CWE-347 根因族挖掘实证
> 升级内容：新增 P9 步骤 + 4 个泛化维度 + 1 个工具 + 校准样本扩充

---

## 一句话总结

这次挖掘证明了一件事：**工作流缺的不是步骤，是"根因族"这一层抽象。**

我们原来按漏洞类型分类（越权/注入/逻辑），按 CVE 检索情报。
但实证显示——**GitLab SAML 2024 和 2025、UpdraftPlus UDRPC 2026，
三个完全不同的协议和产品，是同一个根因**。

按类型或协议都串不起来它们，只有按根因能。

---

## 升级 1：新增 P9 步骤「根因族关联」

插入在 P8 之后：

**脚本**
```bash
python3 src_rules.py download                  # 下载规则库（约 10MB）
python3 src_rules.py cwe --cwe CWE-347         # 按根因族拉全部案例
python3 src_rules.py vendor                    # 找跨年重复出洞的厂商
python3 src_rules.py coord --cve CVE-2024-45409  # 拿完整攻击坐标
```

**引导提问**
> **这个根因，还有哪些产品踩过？**
> 按 CWE 检索，不按 CVE 检索——同根因的会自动聚合，
> 哪怕它们分属不同协议、不同产品、不同年份。
>
> **这个厂商，是不是在同一个坑里摔过不止一次？**
> 同组件跨年出洞且 CWE 相同，说明修复是**补手法**不是**重构校验模型**。
> 补手法的必出第三次。
>
> **较新的那个 CVE，EPSS 是不是更高？**
> 是的话说明**补丁绕过比原洞更活跃**——未打补丁的实例更集中，优先级上调。

## 升级 2：泛化引擎新增 4 个维度（12 → 21 维）

| 维度 | 分 | 实证依据 |
|---|---|---|
| `sig_separation` 签名/校验对象与取值对象分离 | **95** | CWE-347 三例：删签名、CDATA 注入、客户端指定 key_name |
| `vendor_recurrence` 同厂商跨年复发 | 92 | GitLab 2024→2025，EPSS 0.107→0.206 翻倍 |
| `rule_coord` 规则库坐标提取 | 90 | 公告说"存在绕过"，规则给到字节级构造 |
| `conditional_guard` 条件校验 vs 强制校验 | 88 | `if(sig){verify()}` vs `if(!sig){reject()}` |

**`sig_separation` 拿到 95 分（与不变量冲突并列最高）**，因为它是目前唯一被三个跨协议案例实证的维度。

实测排序（GitLab CVE-2025-25291）：
```
122  静默补丁
115  不变量冲突
108  同族
103  边界一致性
 95  ★ 签名/校验对象分离   ← 新增
```

## 升级 3：新增工具 `src_rules.py`

四个命令，核心是**把规则库当知识源读，不是拿来跑扫描**：

```bash
download   下载 nuclei-templates（codeload 可达，实测 7 秒 9.5MB）
cwe        按根因族聚合 —— 跨协议同根因自动聚类
vendor     同厂商跨年分布 —— 修复不彻底信号
coord      提取单条规则的完整攻击坐标
patterns   高频根因族速查表
```

`coord` 能提取出的东西比公告详细一个量级：

```
CVE-2026-10795
  CWE      : CWE-347  加密签名验证不当
  标签     : vkev（已知在野利用）
  FOFA     : body="/wp-content/plugins/updraftplus"
  Shodan   : http.html:"updraftplus"
  参数     : key_name / udrpc_message / format / CT_B64 / RSA_LEN ...
  硬编码常量: AES key 与 IV 全零
```

**实测对 1807 个规则跑 `vendor`，立刻识别出跨年复发**：
apache（2000/2016/2020）、microsoft（2000/2019/2020）、
jenkins（2016/2017 两次反序列化）、sudo（2019/2021）。

Jenkins 那组很典型——**2016 和 2017 连续两次 Java 反序列化，CWE 从 90 变成 502**。

## 升级 4：校准样本扩充（15 → 18）

加入 CWE-347 三例后重跑校准：

| 步骤 | 命中 |
|---|---|
| P3 越权与未授权 | 8/18 |
| P5 注入与服务端 | 6/18 |
| **P9 根因族关联** | **6/18** ← 新步骤立刻成为第二产出源 |
| P6 补丁对齐 | 3/18 |
| P7 信任域 | 3/18 |
| P8 AI 边界 | 3/18 |
| P2 测绘 | 2/18 |
| P4 业务逻辑 | **0/18** |

覆盖率 93% → 94%。

**两个信号值得注意**：

1. **P9 一加入就是 6/18**，仅次于 P3。说明"根因族"这个抽象确实补上了真缺口。
2. **P4 仍然是 0**。连续两轮样本都偏服务端漏洞。
   **这不是工作流的问题，是取样的问题**——再不补逻辑漏洞样本，P4 该考虑从流程里拿掉。

## 升级 5：一条新的工作流铁律

原来三条铁律之外，加一条**检索纪律**：

> **按根因检索，不按 CVE 检索。**

CVE 编号是流水号，它把同根因的东西打散了。
CWE / 根因描述才是聚合键。

这条适用于：
- 规则库检索（`src_rules.py cwe`）
- 历史情报回溯（同组件跨年）
- 泛化引擎的维度匹配

## 下一步要解决的

**P4 连续两轮 0 命中。** 两个可能：
1. 样本偏了 → 补逻辑漏洞样本再校准一次
2. 真的不做这个方向 → 从流程里删掉，别占注意力

**建议**：找 5 个并发/支付/状态机类的真实漏洞补进样本，跑第三次校准。
如果还是 0，就说明这个方向确实不做，删掉它比留着强。

这正好呼应 P0 那条引导提问：**命中 0 的，要么是不做的方向（删掉），要么是样本偏了（补样本）。**
