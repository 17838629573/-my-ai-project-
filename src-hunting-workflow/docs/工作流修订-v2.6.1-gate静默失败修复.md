# 工作流修订 v2.6.1：src_gate 静默失败修复 + 冒烟测试纪律

> 触发：v2.6 实跑报告发现 check 命令 2 处 bug
> 性质：**我在修 bug 时发现了第 3 个、也是最严重的一个**

---

## 一句话总结

它报的 2 个 bug 是真的，但**真正的问题不是那 2 个，是它们被静默吞掉了**——
`check` 跑完输出「[OK] 全部通过」，实际上两个闸门根本没执行。

**这是工作流里最忌讳的失败模式：静默失败。**
ESPHome CVE-2026-59178（9.8）就是它——升级后认证全部失效，
只在启动日志打 banner，`docker run -d` 看不到。

我们的工作流自己犯了同一个错。

---

## 它报的 2 个 bug

| # | 位置 | 缺陷 |
|---|---|---|
| 1 | check 子解析器 | 缺 `--add`，`gate_quota` 读 `a.add` → AttributeError |
| 2 | check 的 `--rate` | `dest="rate_ok"` 但 `gate_preflight` 读 `a.rate` → AttributeError |

已修复：`--add` 补齐，`dest` 改回 `rate`。

---

## 我修的时候发现的第 3 个 bug（最严重）

```python
except Exception as e:
    print(f"   (跳过: {e})"      # ← 静默吞掉
    ...
print(" [OK] 全部通过" if rc == 0 ...)   # ← 然后谎报通过
```

**实测**（v2.6.1 修复前）：
```
──── 配额 ────
   (跳过: 'Namespace' object has no attribute 'add')
──── 开工前置 ────
   (跳过: 'Namespace' object has no attribute 'rate')
======================================================================
 [OK] 全部通过          ← 两个闸门没跑，却说通过
```

**修复**：异常不再吞，记为 `errored`，退出码 2，明确输出：

```
 [!!] 2 个闸门执行出错，无法判定——不得当作通过
```

**原则写进代码注释**：闸门执行出错 ≠ 通过。宁可报错，不许谎报。

## 一个值得记住的规律

| 版本 | 谁发现的 | 什么 bug |
|---|---|---|
| v2.4 | 外部 Agent | 2 处运行时崩溃 |
| v2.6 | 外部 Agent | 2 处运行时崩溃 |
| v2.6.1 | **我自己**（修 bug 时发现） | 1 处静默失败 |

前两轮都是**崩溃型**——会抛异常，别人一跑就发现。
这一轮是**静默型**——不抛异常，只是悄悄给出错误结论。

**崩溃型 bug 好抓，静默型 bug 要靠主动设计防御。**

所以新增的纪律不止是"跑一遍"，而是：
**任何 catch-all 的 except，都必须把失败显式暴露出来，不许吞。**
