# 工作流升级 v2.2：底层根因映射层

> 触发：发现"声明边界 ≠ 实际处理边界"这一根因从协议层一路投影到应用层
> 升级内容：新增 P10–P13 四步 + 泛化引擎 21→24 维 + 新工具 `src_stack.py`

---

## 一句话总结

这次不是加步骤，是**加了一个抽象层**。

前面几轮我们都在应用层打转。这一轮发现：**同一个根因会在协议层、运行时层、应用层各出现一次**，而且形态可映射。这意味着底层 CVE 可以当**导航图**用——虽然它本身报不了 SRC。

---

## 核心发现：一条根因，三层投影

把所有挖到的案例按根因重排，浮现出一条贯穿三层的线：

| 层 | 案例 | 声明的 | 实际的 |
|---|---|---|---|
| 协议 | GoBGP CVE-2026-49837 | CapLen=0 | 读了后续 4 字节作 AS 号 |
| 协议 | Unbound CVE-2026-44690 | RRSIG.Labels | 实际 label 数不符仍接受 |
| 协议 | NatJack | 表项已关闭 | 仍在内存，可被复用注入 |
| 协议 | REBIRTHDAY | 聚合键含 ECS | 无 ECS 响应也算有效匹配 |
| 运行时 | CPython tarfile ×3 | 解析后路径在目的地内 | 中间路径组件在外 |
| 运行时 | OpenJDK DataView | offset 限定窗口 | 用绝对索引，忽略 offset |
| 运行时 | CPython zipfile | 分块读取内存限制 | 用攻击者控制的大小预分配 |
| 应用 | GitLab SAML | 签名覆盖的内容 | 实际取的 NameID |
| 应用 | Traefik StripPrefix | 匹配到的路径 | 实际执行的路径 |
| 应用 | Kestra | 后缀匹配白名单 | 路径可操纵绕过 |

**这不是巧合，是同一个设计错误在不同抽象层的投影。**

`invariant_conflict`（95 分）现在有 10+ 个跨层实例，是全库最强的根因。

## 升级 1：新增 P10–P13 四步

| 步 | 一句话 | 工具 |
|---|---|---|
| **P10** | 框架自身攻击面（挖框架而非应用） | `src_stack.py frame` |
| **P11** | 多 Agent 信任边界（confused deputy） | 头变异 / 委托链测试 |
| **P12** | 协议层根因映射（自下而上） | `src_stack.py proto` |
| **P13** | 运行时根因映射（语言/标准库） | `src_stack.py lang` |

四步共用同一个核心动作：**底层 CVE → 抽根因 → 映射应用层 → 在目标验证**。

## 升级 2：泛化引擎 21 → 24 维

| 维度 | 分 | 实证 |
|---|---|---|
| `declared_boundary` 声明边界≠实际边界 | **92** | 10+ 跨层实例 |
| `repeated_patch` 同模块短周期连环修复 | 90 | CPython tarfile 三连、GitLab SAML 两连 |
| `api_misuse` 不当 API/查找路径误用 | 85 | protobufjs、OpenJDK DataView |

### `api_misuse` 是全新的一类

它跟已有维度都不一样：

- 已有维度查的是「**缺了校验**」
- `api_misuse` 查的是「**用了错误的查找方式**」

```js
// 漏洞写法：字段名 hasOwnProperty 会遮蔽原型方法
if (message.hasOwnProperty(fieldName))
// 修复写法
if (Object.hasOwnProperty.call(message, fieldName))
```

这类洞**正常输入下完美工作，代码审查看不出问题，只在攻击者控制的键名下崩溃**。

特征：必须专门构造键名（`hasOwnProperty`、`constructor`、`__proto__`、`rpcCall`）才能触发。


## 升级 4：一条新的重要纪律

> **底层 CVE 是导航图，不是靶子。**

协议层、运行时层、框架层的漏洞本身报不了 SRC——你证明不了"某网站受 NAT 漏洞影响"。

**能提交的是映射后的应用层形态**：它在目标的代码里，在 SRC 范围内，复现得出来。

这条分界线不写死的话，会产出一批必然被打回的报告。

## 三个值得记住的实证

### CPython tarfile：三个月三连修

| CVE | 时间 | 形态 |
|---|---|---|
| 19672 | 8月 | 成员名 `../evil/../dest/file` 离返 |
| 82049 | 9月 | 硬链接指向符号链接（8.4 HIGH） |
| 87910 | 9月 | fallback 提取时 filter 被调用两次 |

**典型"补手法不重构"**——每次堵一个具体形态。19672 那句描述最说明问题：*"包含检查用了解析后的路径，但中间路径组件没查"*。

### MCP：厂商明确拒绝修复

Anthropic 回应：*"这是 stdio MCP 服务器工作的明确部分，我们相信这个设计确实代表了安全的默认值"*

10 个官方 SDK 全中，1.5 亿下载，20 万实例。**不是 bug，是设计。**

信号优先级因此重排：**厂商拒绝修复 > 静默补丁 > 修复不完整 > 公开 CVE**。
前两类几乎零竞争，因为根本不会有人来修，或者没人知道修过。

### WordPress：攻击面在插件不在核心

今年两个 9 分+（CVE-2026-87902 模板路径遍历 9.2、CVE-2026-63030 REST batch RCE 9.8）。

但澳大利亚 ASD 的警报更说明问题：一场全球大规模利用活动列了 **17 个插件 CVE**，全是未授权上传/RCE/SSRF/反序列化。**核心修得快，插件没人管。**

## 注意力纪律不能破

四步新增后总数到了 14 步。但**每步仍然只有三样东西**：一句话目标 + 一条脚本 + 一段引导提问。

**同时生效的规则仍然只有 3 条铁律。**

新四步不是常驻的——它们是**按需调取的专家模块**：
- 目标是 AI/Agent 类 → 调 P10、P11
- 目标有协议解析/网络组件 → 调 P12
- 做源码审计 → 调 P13
- 常规 Web → P10–P13 全部跳过

**不要一次全读。** 这是这套工作流从一开始就定下的纪律。

## 已知边界

1. **新四步的命中率完全未实测**。24 维的权重里，`declared_boundary` 和 `api_misuse` 的分数是靠实例数量推的，没有真实验证数据。
2. **框架层竞争最激烈**。跟"静默补丁零竞争"正好相反——框架 CVE 是公开舞台，比手速。差异化不靠知道得早，靠看到别人没看的关联。
3. **P4 仍然是 0 命中**，连续两轮了。这个老问题还没解决。
