# 工作流升级 v2.3：版本升级敞口（开工第一问）

> 触发：发现「升级成功 ≠ 安全迁移」——ESPHome CVE-2026-59178（CVSS 9.8）
> 升级内容：新增 P-1 前置检查 + 泛化引擎 24→26 维 + `src_stack.py upgrade`

---

## 一句话总结

这次加的是**唯一一个不用挖就有答案**的检查项。

前面所有步骤都要探、要猜、要验证。P-1 不用——
**"近 3-5 个月有没有升过级"是纯客观事实，问一次就有答案。**

而且答案的两个分支都直接指向敞口：

- **没升级** → 旧版本本身就是敞口
- **升过级** → 升级过程本身可能已经制造了敞口

---

## 核心实证：ESPHome CVE-2026-59178（CVSS 9.8）

环境变量从 `USERNAME`/`PASSWORD` 改名为 `ESPHOME_USERNAME`/`ESPHOME_PASSWORD`，
**旧名被移除且没有 fallback**。

升级后凭证解析为空 → `using_password = false`
→ REST 认证中间件 + WebSocket 登录门**全部静默禁用**
→ dashboard 对任何能访问端口的人开放。

三个细节让它成为教科书案例：

1. **只在启动日志打 banner**，`docker run -d` 根本看不到 —— 静默暴露
2. 改动标为 breaking change，**但没写进 2026.6.0 changelog**，运维没有迁移信号
3. 修复方式是**恢复兼容而非 fail closed**（1.0.12 重新接受旧名，仅当两者都设置时）
   ——因为优先级是"升级前有保护的，升级后必须仍有保护"

**一句话：成功启动不等于安全迁移。**

## 升级 1：新增 P-1 前置检查（开工第一问）

放在 P0 之前，每次必答：

> **目标的语言 / 框架 / 运行时，近 3-5 个月是否升过级？**

```bash
python3 src_stack.py upgrade --lang python   # 或 java / go / js
```

**为什么是 3-5 个月**：短于 3 个月变更太少，长于 5 个月早已被别人扫过、时间窗关闭。

---

## 升级 2：变更信号分级（防误报的关键）

**不是所有变更都意味着旧版有洞。** 必须分层，否则会大量误报：

| 强度 | 信号 | 为什么 |
|---|---|---|
| **强** | 描述含 security / unsafe / safer / harden | 官方已定性为安全相关 |
| **强** | **默认行为变更** | 旧默认被判定为不安全 → 未升级的全体暴露 |
| **强** | **移除或重命名配置项 / 凭证项** | 迁移断裂高危 |
| 中 | 移除无人维护的模块（dead batteries） | 无补丁可领，但未必可利用 |
| 弱 | 纯功能新增 / 性能改进 | 与安全无关，不要据此推断旧版有洞 |

举例：Python 3.14 把 multiprocessing 默认 start method 从 fork 改为更安全的方式
（gh-84559）——**这是强信号**，说明旧默认被判定为不安全。
而 t-strings 这类纯功能新增，不该拿去推断旧版有洞。

## 升级 3：泛化引擎 24 → 26 维

| 维度 | 分 | 一句话 |
|---|---|---|
| `upgrade_regression` | **90** | 升级后安全控制静默消失（迁移断裂） |
| `migration_exemption` | **80** | 为兼容而开的永久豁免 |

### `upgrade_regression` 是全新的一类

已有 25 个维度都在查"**缺了什么校验**"，这个查的是
"**原本有的控制，在升级后消失了**"。

判据：对比升级前后**五类控制**——认证、授权、加密、日志、网络绑定。
任何一类消失或降级、且无显式报错 = 命中。

### `migration_exemption` 查的是"开回去的门"

Java 迁移最典型：JEP 403 强封装 `java.*` 内部 API **本来是加固**，
但为了让老代码跑起来，运维会加 `--add-opens` / `--add-exports`。

**这些是编译期没有、运行期永久存在的豁免**——
而且只在启动脚本里，代码审查根本看不见。

同类：`--illegal-access`、legacy fallback 开关、兼容层、
未下线的 `/api/v1/`（缺 v2 才有的鉴权，OWASP API9:2023）。

## 升级 4：升级类目标的验收测试

**不要只看"服务起来了"。**

从**每个能触达的网络段**确认五类控制仍然生效：

```
认证 · 授权 · 加密 · 日志 · 网络绑定
```

判据一句话：**升级后，未认证访问是否被拒绝？**

这个测试便宜到离谱——发一个不带凭证的请求就行。
但它能拦住 ESPHome 那一整类洞。

## 升级 5：`src_stack.py upgrade`

```bash
python3 src_stack.py upgrade                # 全部语言概览
python3 src_stack.py upgrade --lang python  # 指定语言
```

输出三块：变更信号分级表 + 该语言的关键变更清单 + 验收测试要求。

### 收录的关键变更

**Python**
- 3.13 PEP 594 移除 19 个 stdlib 模块（cgi、telnetlib、crypt、pipes…）
  → 移除理由是长期无人维护，**3.13 之前用它们的系统永无补丁**
- 3.14 multiprocessing 默认 start method 改更安全（gh-84559）→ 强信号
- 3.14 注解默认延迟求值（PEP 649/749）→ **静默失败**，不报 ImportError
  而是拿到 ForwardRef
- 3.13.11 是"加急发布修回归" → 升级过程中暴露的活标本

**Java**
- JDK 17 JEP 403 强封装 → 加固项，但迁移需 --add-opens
- JDK 17 `--illegal-access` 作废 → 只能逐个 --add-opens
- JDK 11 JAXB/JAF 移出 JDK → 常见临时解法引入老依赖

## 为什么这次升级特别划算

三个理由：

1. **零成本**：不用发包、不用凭证、不用源码。问一句就知道。
2. **命中率高**：升级必定留下痕迹（changelog、release notes、启动脚本），
   不像逻辑漏洞要猜。
3. **竞争低**：大家都在追新 CVE，很少有人回头查"升级本身制造了什么"。

而且它天然适合 AI——**版本对比是确定性工作，正是脚本该干的**。

## 已知边界

1. `upgrade_regression` 目前只有 ESPHome 一个硬实证，
   Python 3.13.11 那个算半个。给 90 分是靠机制强度推的，不是靠实例数量。
2. 变更信号分级表是归纳出来的，没有经过大量样本验证——
   **"强信号"里可能仍有相当比例的误报**，需要实战校准。
3. Java 的 `--add-opens` 那类豁免在很多环境里是必要的正常操作，
   不能直接判为漏洞，要看它开的是哪个包、范围有多大。
