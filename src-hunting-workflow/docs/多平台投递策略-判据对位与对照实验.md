# 多平台投递策略 —— 判据对位与对照实验方法

> 本文件为**方法论**，全部目标信息已抽象为占位符。
> 核心命题：**同一批产出，按平台判据分配到不同渠道，并用反馈反向标定各平台松紧度。**

---

## 一、为什么不能把所有产出投同一个平台

不同平台的**判据维度根本不同**：

| 平台 | 它看什么 | 它不看什么 |
|---|---|---|
| **SRC 类**（高校/行业/厂商） | **你拿到了什么**（真实数据、凭据、文件） | 版本号、理论影响 |
| **CNVD 类**（国家级收录） | **这个漏洞影响多少产品/版本**（通用性） | 单实例的数据敏感度 |
| **CNNVD 类** | 漏洞细节完整度 | 是否独家 |

**同一个产出在不同平台会得到相反评价**，这不是平台水平差异，是定位差异。

**典型错配**：把"某实例运行版本 X，命中公开 CVE"投给 SRC 类平台——
- SRC 视角：互联网已公开的漏洞 + 无法提供利用方法 → **忽略项**
- CNVD 视角：通用型产品漏洞的受影响实例 → **正对口**

---

## 二、判据对位表（核心）

| 产出类型 | 首投 | 次投 | 不要投 |
|---|---|---|---|
| **未授权访问 / 越权**（有完整证明链，非通用） | SRC 类 | CNNVD | — |
| **组件版本命中公开 CVE**（无利用验证） | **CNVD** | CNNVD | SRC 类（会判忽略/降级） |
| **低危信息泄露**（路径回显、版本串、栈泄露） | **厂商渠道** | CNNVD | SRC 类（常判忽略） |
| **已公开 CVE 的新受影响实例** | CNVD（实例通报表） | — | SRC 类 |
| **可获取真实敏感数据** | SRC 类（最高优先级） | — | 勿投公开渠道 |

---

## 三、红线：一稿多投

> **同一条漏洞提交到 A 平台后又提交到 B 平台 → 多数平台判"忽略"。**

**这条极易被误解。**

- ❌ 违规：把"统计接口未授权"这条同时投 SRC 和 CNVD
- ✅ 合规：**三个不同的独立漏洞，各投一个平台**

判断标准：两条是否**同一系统、同一根因**。
同一系统的多个漏洞点应**打包**；不同系统的相同漏洞类型应**分开**。
按"系统"切分，而不是按"漏洞个数"切分。

---

## 四、三平台对照实验（获取平台真实松紧度）

### 4.1 实验设计

把一批产出按"系统"切成 **N 个独立条目**，每个条目锁定一个平台，**在同一时间窗内投递**。

### 4.2 必须控制的变量

| 变量 | 要求 | 不控制的后果 |
|---|---|---|
| **时间窗** | 一周内投完 | 平台松紧随时间波动，时间拉开则无对照意义 |
| **详略口径** | 三份用同样的证据密度与撰写深度 | A 详 B 略，则 B 被拒时无法区分"平台严"还是"写得差" |
| **措辞红线** | 三份统一执行 | 一份夸大被拒，污染整体信号 |
| **条目独立性** | 三条确为不同系统不同根因 | 触发一稿多投 |

### 4.3 判词记录表（实验的核心产出）

| 平台 | 条目 | 提交日 | 初审结果 | 最终定级 | **判词原文（逐字）** | 结论 |
|---|---|---|---|---|---|---|
| | | | | | | |
| | | | | | | |
| | | | | | | |

**判词原文必须逐字记录。** 以下短语是最有价值的信号：
- "无明显敏感信息内容" → 该平台卡数据敏感度
- "通用型降级" → 该平台卡通用性
- "无法提供利用方法" → 该平台卡证明深度
- "已收录" → 该条重复，非质量问题

### 4.4 信号解读（避免误读）

| 反馈 | 正确解读 | 常见误读 |
|---|---|---|
| 平台收了 A | A 类产出在该平台有出路 | "这个平台松" |
| 平台拒了 A | A 类的**某个维度**被卡（看判词才知道是哪个） | "这个平台严" |
| 平台拒了 C（低危） | 可能只是 C 本身价值低 | "平台严"，进而错误放弃该平台 |

**关键：被拒时要看判词定位被卡的维度，不要笼统归因于平台松紧。**

## 五、平台特定规则（投递前必查，且会变）

以下为**截至记录时点**的规则，投递前必须重新核实：

### 5.1 SRC 类（以教育行业 SRC 为例）

| 规则 | 影响 |
|---|---|
| 只收已备案的 root 域名，IP/端口不收 | 资产范围限制 |
| **已公开的漏洞 → 忽略** | 版本命中型勿投 |
| **扫描器结果无法提供利用方法 → 忽略** | 必须附手工证明链 |
| **已有他人提交过 → 忽略** | 投递前查重 |
| **无链接/截图/利用方法 → 忽略** | 截图是硬要求 |
| **通用型漏洞（无有意义组合）→ 降级** | 版本命中型会被降 |
| 提交后 N 个工作日未修复 → **漏洞公开** | 保密风险，含路径参数的报告要谨慎 |

### 5.2 CNVD 类

| 规则 | 影响 |
|---|---|
| 收通用型产品/应用漏洞（含中间件） | 版本命中型正对口 |
| 需提供**分析过程**（PoC 非强制） | 响应基线、形态分流证据就是分析过程 |
| 通用型按**通用型级别**评分 | 跨机构通用是加分项，不是减分项 |
| 通常无直接现金奖励，出原创漏洞证书 | 预期管理 |

### 5.3 CNNVD

- 国家级，要求**详细细节**
- 可补充提交已收录漏洞的更多信息

### 5.4 厂商渠道

- 对自家产品的配置类问题接受度高
- 通常无奖金，但响应快、修复直接

## 六、投递前自查清单

- ☐ 每条只投一个平台（无一稿多投）
- ☐ 按"系统"切分条目，同系统的多个点已打包
- ☐ 已按判据对位表选择平台（而非默认全投 SRC）
- ☐ 已核实该平台最新规则（规则会变，勿用旧认知）
- ☐ 【需补充】占位符已全部替换为真实证据
- ☐ 截图已附，含可辨识时间戳
- ☐ 措辞红线已校验（见下）
- ☐ 已确认测试行为的授权范围

---

## 七、措辞红线（三份报告统一执行）

| 红线 | 错误写法 | 正确写法 |
|---|---|---|
| 鉴权状态 | "已确认无鉴权" | "**未观察到鉴权拦截**" |
| 推断 vs 实锤 | 混在一起写 | 分开标注，推断单独声明 |
| 潜在影响 | 写成已发生事实 | 标"潜在"，并声明未验证 |
| 数据获取 | 暗示拿到了敏感数据 | 未拿到就明写"未获取" |
| CVE 危害 | 按 CVSS 分数描述 | 按**实际危害**描述（注意 CVSS 9.6 可能是 ANSI 注入而非 RCE） |

**违反红线的后果**：不是被打回，是**损伤账号信誉**，影响后续所有投递。

---

## 八、定级预期管理（重要）

投递前应对每条建立**降级预期**：

| 产出类型 | 自评 | 平台可能给 | 是否接受 |
|---|---|---|---|
| 未授权访问（有证明链、非通用） | 中危 | 中危或低危 | 接受 |
| 版本命中（无利用验证） | 中危 | **低危或忽略** | 接受，本就该投 CNVD |
| 信息泄露 | 低危 | 低危或忽略 | 接受 |

**不要为了保住自评级别而夸大。** 夸大一旦被复核查出，损失的是账号信誉，而账号信誉决定后续所有投递的通过率。
