# 闭源公告反推十例：用公告措辞定位缺失的那一道校验

## 摘要

这十例共同证明：闭源公告的价值不在“它承认了什么漏洞”，而在它被迫把“原本应当执行、却没有执行”的约束写成一句话。凡是公告同时出现**特定入口/协议 + 攻击者可控对象 + 安全敏感动作**，缺失的通常不是笼统的“输入校验”，而是某一道可枚举的防线：路径规范化和落点白名单、消息字段与命令参数的语义边界、服务身份与本地 IPC 的信任域、批量写入的目标范围、配置/状态机的状态切换、签名覆盖范围、对象级鉴权、审计日志的不可逆性，以及网络出口的目标范围。修复版本则是闭源环境唯一可靠的指纹坐标；日期和补丁串必须同时记录，不能只记“已升级”。

本报告的验证请求全部为**无害探针**：以只读、随机 marker、固定边界和可逆副作用为上限，且只适用于自有资产、书面授权范围或厂商隔离测试环境。对在野利用或已公开可直接利用的细节，仅保留原理与检测逻辑。事实与公告原文、版本信息列为一层；其余均为待验证外推，不得直接作为赏金结论。

## 案例 1：GitHub Enterprise Server 的 `X-GitHub-Request-Id` 路径穿越（CVE-2026-17556）

### 公告原文摘录

1. **GitHub 官方发布说明（3.17.19，2026-08-05）**：发布说明把该问题列为 HIGH，并说明“a path traversal vulnerability allowed an unauthenticated attacker to delete the user storage directory on the GitHub Enterprise Server instance, including Git LFS objects, release assets, attachments, and avatars, via the unsanitized X-GitHub-Request-Id request header”；该问题在启用 private mode 时仍可工作。修复版包括 3.17.19、3.18.13、3.19.10、3.20.6、3.21.4。[1]
2. **NVD/CVE 记录**：这是公开记录中的官方分类与时间锚点。[1]

### 措辞反推

原文最有信息量的是两个限定词：**“unsanitized”**和**“X-GitHub-Request-Id”**。它不是泛泛的“未过滤请求头”，而是这个特定头的值进入了文件系统路径构造。公告又提到“deferred cleanup routine recursively removed the traversed target”，说明缺失不止一层：第一层是入口未拒绝异常分隔符；第二层是外部字符串被拼成缓冲目录名；第三层是延迟清理只拿已保存的“内部路径”继续操作，却没有在真正落盘或删除前重新规范化并核对允许根。由此应把假设锁定在**上传缓冲生命周期的目录命名与清理阶段**，而不是普通 API 参数。这里尤其要区分：请求头本身只是攻击者输入，真正的安全属性是“最终规范路径必须位于上传缓冲白名单目录之下”。

### 组件定位信息

- **定位**：GitHub Enterprise Server 是半闭源企业平台，属于集中式 Web/后端服务，攻击面在网络可达的管理/API 入口。
- **版本区间**：官方修复版为 3.17.19、3.18.13、3.19.10、3.20.6、3.21.4；公告明确说明低于这些版本的 3.17/3.18/3.19/3.20/3.21 分支均受影响。应逐分支读取发行说明，不能只升级其中一个分支。
- **架构提示**：因为 private mode 开启仍受影响，说明它不是由常规认证门禁阻断的漏洞。

### 外推假设（待验证）

- **同族入口**：不只测根路径，同一头可能作用于其他上传、附件、Webhook、LFS 或缓存清理链路；但不得连续测试删除动作。
- **入口变形**：改为 `X-Github-Request-Id`、`X-GITHUB-REQUEST-ID`、多次同名头、折叠头、含空格/制表符变体，观察哪一条进入日志/路径。
- **归一化边界**：补丁可能只检查 `..`；若未做 percent-decoding 后再规范化，可能仍有 URL 编码、超长 UTF-8、反向斜杠或 NUL 截断差异。这里仅为代码审计或厂商隔离环境的待验证项。
- **串联**：若头值影响缓冲目录，可与并发上传、重传、取消操作组合，观察清理任务是否处理同一目录。危害跃迁需要真实删除能力，赏金报告必须保留请求 ID、时间戳和只读指纹，不通过删文件证明。

### 可构造的验证请求

```http
GET / HTTP/1.1
Host: ghes-test.example.local
User-Agent: SRC-Canary/1.0
Accept: */*
X-GitHub-Request-Id: safe-canary-001
```

请求必须发给厂商赏金范围或自有测试实例，并以低频率发送一次；`safe-canary-001` 是可追溯的只读 marker，不是遍历载荷。同步抓取响应头、应用日志、上传缓冲目录清单。

### 命中判据

命中是“客观且最小”的：应用日志/可访问调试信息出现 `safe-canary-001`；或响应头回显该 marker；或在授权隔离环境中能证明该 marker 被作为目录/文件名处理。若存在请求 ID 回显端点，以回显中 marker 的字节形态作为附加证据。没有遍历字符，因此本探针不构成任意文件删除证明。

### 排除判据

- 响应未携带任何请求 ID，且授权日志中没有 marker；
- 应用网关/反向代理 返回 4xx，未到达后端；
- 版本属于上述任一完整修复分支；
- 仅在客户端代理、浏览器历史或外部 WAF 日志中出现 marker，后端无法关联；
- 使用真实 `../` 或尝试删除目录的请求一律不作为本报告的合法验证步骤。

## 案例 2：GitHub Enterprise Server Manage API 的未认证出站请求（CVE-2026-18730）

### 公告原文摘录

1. **官方发布说明（3.21.5，2026-09-01）**：该问题被列为 HIGH，说明“an unauthenticated attacker could cause a GitHub Enterprise Server instance to send crafted outbound requests to an attacker-controlled host via an unauthenticated Manage API endpoint that parsed an attacker-supplied cluster configuration”；攻击者若可截获出站请求，可捕获可重放的管理 bearer token，高可用部署不受影响。[2]
2. 官方还确认该漏洞通过 GitHub Bug Bounty 报告。[2]

### 措辞反推

“unauthenticated endpoint”+“parsed an attacker-supplied cluster configuration”两句把边界划在 Manage API 的入口，而非普通用户 API。进一步，“send crafted outbound requests to an attacker-controlled host”说明组件把外部配置中的主机名/URL 直接转化为服务端 HTTP 客户端目标；“gateway-to-agent requests whose HMAC authenticated only a timestamp, not the request path or body”则说明第二道失效是签名完整性范围：只保证消息的新鲜度，不保证请求内容未被替换。缺失的是：**服务端出口 URL 的用途授权、Manage 入口的对象/拓扑状态检查，以及 HMAC 覆盖域从“何时”扩展到“谁向何处发什么”。**

### 组件定位信息

- **定位**：GHES Manage API 属于内部管理/运维控制面；正常运行拓扑和高可用拓扑的暴露面不同。
- **版本区间**：官方公告发布于 2026-09-01 的 3.21.5；3.17.19、3.18.13、3.19.10、3.20.6、3.21.4 也被列为相关修复版本。3.22 之前的版本均处于风险窗口。[2]
- **关键边界**：HA 部署不受该漏洞影响，说明拓扑条件是赏金报告必须首先确认的前置事实。

### 外推假设（待验证）

- **同族入口**：管理面中解析集群成员、节点、备份、迁移或复制配置的其他字段，也可能决定服务端出站目标；但不得盲目 fuzz 管理面。
- **协议与解析变形**：目标字段可能对 `http://` 与 `https://`、IP 与域名、IPv6、大小写 scheme、末尾斜杠、重复 `//`、IDN、重定向地址有不同处理。
- **串联**：若配置还控制 agent 地址、证书或共享密钥，出站请求可能把内部 token/元数据交给中间人；只有在能够合法观察网络流量且存在重放窗口时才是成立条件。

### 可构造的验证请求

本例应在拥有 GHES 测试实例和可控 DNS/HTTP 审计域名的授权环境中进行；只让服务器访问审计域名，不尝试捕获生产 token。

```http
GET /manage/api/v0/canary-test HTTP/1.1
Host: ghes-manage-test.example.local
User-Agent: SRC-Canary/1.0
Accept: application/json
```

请求路径只是占位，真实端点必须由授权方提供；请求体仅提交明确标记为测试用途的集群配置字段，目标设置为 `https://ghes-outbound-canary.example.org/`。审计端只确认“服务端请求到达”，不保存或重放收到的任何认证材料。

### 命中判据

唯一可接受的命中是：在隔离审计域名上收到来自 GHES 实例 IP 的 HTTPS 请求，且时间戳、TLS SNI、Host 与提交配置一致；同时实例返回不依赖审计域名内容的统一“配置已接受/后台处理”响应。重复两次请求应能稳定复现，且停服或禁用相关 Manage API 后请求不再发出。

### 排除判据

- 实例处于 HA 拓扑且公告明确排除；
- 防火墙/代理直接拒绝出站，不能证明应用逻辑放行；
- 审计域名未收到请求；
- 收到请求但来源不是 GHES，或目标主机并非配置所指定的域名；
- 测试实例已安装 3.21.5 或相应修复分支；
- 捕获、存储或重放任何生产 bearer token。

## 案例 3：GitHub Enterprise Server 绕过外部 IdP 的本地注册（CVE-2026-6736）

### 公告原文摘录

1. **官方发布说明（3.20.2，2026-05-07）**：该问题为 MEDIUM，说明“an attacker could create a local user account on a GitHub Enterprise Server instance configured with an external authentication provider, bypassing the identity provider entirely”；signup endpoint 未正确执行外部认证限制，允许绕过 IdP 创建账户并建立会话，新账户仅拥有实例默认基础权限。[3]
2. 官方将修复纳入 3.20.2 的 Security fixes。[3]

### 措辞反推

公告强调“configured with an external authentication provider”和“bypassing the identity provider entirely”，这并非简单的认证绕过，而是**身份来源策略与注册状态机不一致**。可推断：实例存在允许本地账户/自助注册的遗留入口，但该入口只检查“是否允许公开访问”，没有在外部 IdP 模式下重新计算“是否允许本地自助注册”；登录/注册成功后的会话建立又只依赖账户是否存在，未把身份来源作为策略属性。所以缺的是：全局认证模式 → 端点策略的映射、对象级账户来源策略、注册成功后的默认权限最小化，以及审计事件与身份来源绑定。

### 组件定位信息

- **定位**：属于企业身份/认证后端；攻击面在 signup 端点，只有启用外部 IdP 的配置才满足前置条件。
- **版本区间**：3.21 之前的版本受影响；官方修复版为 3.20.2、3.19.6、3.18.9、3.17.15、3.16.18。[3]
- **测试要求**：不能拿普通自托管账号模式的实例套用；必须先证明目标使用 SAML/OIDC，并确认允许/禁止本地用户创建的预期策略。

### 外推假设（待验证）

- **同族入口**：除了普通 signup，注册确认、邀请兑换、OAuth 应用用户创建、LDAP/SAML 账户关联，可能共用同一策略决策点；是否共享必须逐个读取响应，不批量提交。
- **状态与字段变形**：若 IdP 策略按请求参数、返回 URL 或“provider”字段选择，可能存在空值、未知 provider、大小写、重复字段；但仅发唯一测试账户，不枚举他人邮箱。
- **串联**：新账户默认基础权限若可与公开仓库、Actions/Runner 权限、OAuth App 或现有组织邀请组合，权限边界可能从“普通成员”跃迁为工作负载执行面；报告需证明组合配置确实存在。

### 可构造的验证请求

```http
POST /join HTTP/1.1
Host: ghes-idp-test.example.local
Content-Type: application/json
User-Agent: SRC-Canary/1.0

{"username":"signedup-canary-<RAND>","email":"<a mailbox you control>"}
```

`<RAND>` 用于唯一性，`<a mailbox you control>` 必须属于测试者本人。若系统需要 CSRF token，从同一会话合法读取后附入；不得使用他人邮箱、手机、邀请链接或批量注册。若公告并未确认 `/join` 路径，本报告不声称该路径存在，应按实例实际页面抓取。

### 命中判据

收到 200/302 并生成可登录会话，或返回“用户名已存在/邮箱已注册”之外的创建成功提示，同时该账户在实例管理员界面显示为本地身份且能进入受保护页面。最重要的是与策略矛盾：外部 IdP 模式明确禁止本地自助注册，却出现新的本地账户。以管理审计日志中“创建者/身份来源”字段为强证据。

### 排除判据

- 实例不是外部 IdP 模式；
- 配置本身允许本地账户自助注册；
- 响应为 403/404 且不创建账户；
- 账户未生成会话；
- 仅收到邮箱验证邮件但未形成账户；
- 唯一性报错属于注册流程正常工作，不能据此判定绕过。

## 案例 4：JetBrains GoLand 项目配置中的外部控制字段（CVE-2026-53915）

### 公告原文摘录

1. **阿里云漏洞库/公告摘要（披露时间 2026-06-19）**：JetBrains GoLand 是闭源商业 Go IDE；受影响版本包括所有早于 2026.1.3 的发布版本。公告称项目配置加载逻辑已收紧，并对外部控制项执行合法性校验、阻断其进入底层执行链路；公开资料未披露具体 commit 或源码 diff。[4]
2. 摘要将缺陷描述为项目配置中由外部控制的文件路径、文件名或脚本/命令字段缺少有效性校验与可信度评估。[4]

### 措辞反推

关键不是“配置会被解析”，而是配置来自**项目根目录 `.idea`**，却被当作当前用户的受信执行上下文。推断路径是：项目打开 → 自动加载 `.idea/workspace.xml`、`runConfigurations/*.xml` → 某个字符串字段被理解为可执行命令/脚本路径 → 解析或执行前没有校验字段是否来自可信来源、是否为项目内资源、是否需用户确认。缺失的是：**执行上下文的来源绑定、自动加载与主动执行的分层、项目外路径白名单，以及对未知/升级配置格式的显式确认。**它属于序列化/配置解析层向执行层的跨界信任问题，而不是一般 XML 解析漏洞。

### 组件定位信息

- **定位**：桌面客户端/开发工具链；攻击面要求受害者主动打开项目，属于本地攻击面，代码在用户会话内运行。
- **版本区间**：所有早于 2026.1.3 的版本受影响；修复边界为 2026.1.3。[4]
- **测试建议**：以干净低权限虚拟机打开项目，记录进程树和首次运行提示；不应在承载真实密钥的主机测试。

### 外推假设（待验证）

- **同族入口**：`workspace.xml`、`misc.xml`、`runConfigurations`、`deployment/debug`、工具链、外部工具、终端及 pre-commit 钩子配置都可能是“外部文件即命令”的候选。
- **信任边界**：即使无法直接执行，配置若控制下载地址、环境变量、代理、证书或远程解释器，也可能形成二阶风险。
- **格式变形**：旧版配置兼容路径、未知属性、相对/绝对路径、UNC/SMB 路径、符号链接、URL 与文件路径混用、XML 外部实体与编码，都可能改变解析器最终交给执行器的字符串。
- **串联**：能写项目文件的人可把恶意 `.idea` 提交进仓库；一旦受害者克隆并打开，就从仓库写入者跃迁为本地代码执行。

### 可构造的验证请求

桌面端没有 HTTP 请求，验证对象是可复现的恶意项目骨架：

```text
goland-canary/
├── main.go
└── .idea/
    └── runConfigurations/
        └── canary.xml
```

`canary.xml` 中只放置 `safe-canary-<RAND>` 作为路径/脚本字段；在隔离低权限账户下打开 `goland-canary` 项目。记录是否出现“运行/调试配置自动导入”提示、是否有解释器调用、进程名或配置 UI 预填 marker。

### 命中判据

首次打开项目即出现对 marker 的执行/解释/路径解析意图；或在配置导入弹窗前没有提示；或进程监视器发现 GoLand 访问 marker 命名对象。若补丁版本显示明确的“外部配置执行需确认”提示，而旧版本直接导入，则构成版本行为差异证据。

### 排除判据

- 版本为 2026.1.3 或更新；
- 项目未打开前没有访问 marker；
- 只有在用户主动点击“运行/编辑配置”后才处理字段，说明触发链需要超出公告条件的交互；
- marker 仅被作为普通显示文本，没有进入执行、路径解析或子进程；
- 配置被拒绝导入但没有具体错误证据。

## 案例 5：Power Automate for Desktop Java 同步服务的本地提权（CVE-2026-77897）

### 公告原文摘录

1. **Microsoft Learn 公告（2026-08，中文官方支持页）**：安装受影响版本 Power Automate 桌面的计算机可能允许本地 Windows 用户以提升权限执行代码；受影响范围是 2.54 至 2.68。[5]
2. 同一页面明确：“如果禁用 Power Automate Java 同步服务，则不会受到影响”；修复版本包括 2.68.260.26243、2.67.153.26243、2.66.169.26243；2.69 及更高版本没有漏洞。[5]

### 措辞反推

Microsoft 给出的唯一缓解措施是停止 `PADJavaSyncService`，这是闭源公告中少见的“服务级定位”。结合“本地 Windows 用户”和“提升权限”，可反推缺失校验位于**常驻服务的本地 IPC 入口，而非网页或远程 RPC**：低权限调用者能向 Java 同步服务提交对象/消息，服务以较高权限执行，却没有完成服务身份检查、消息来源证明、调用者权限继承限制，或目标对象作用域检查。公告没有给出协议细节，因此不能断言是命名管道、COM、socket 还是共享内存；只能断言“服务存在且可被本地调用”是必要前提。

### 组件定位信息

- **定位**：Windows 桌面自动化客户端；攻击面是本地常驻服务，低权限用户到高权限服务的边界。
- **版本区间**：受影响范围为 Power Automate 桌面版 2.54–2.68；修复版本为 2.66.169.26243、2.67.153.26243、2.68.260.26243，2.69+ 不受影响。[5]
- **可操作坐标**：`services.msc` 中的“Power Automate Java 同步服务”（服务名 `PADJavaSyncService`）。

### 外推假设（待验证）

- **同族入口**：Java 元素发现、同步、缓存刷新、运行时对象读取等操作可能共享同一 RPC 分派器。
- **边界变形**：即便调用者低权限，若服务把“来自本机”误当作“来自当前用户或可信自动化流”，可能缺少调用者 SID 与对象所有者的二次绑定。
- **串联**：若服务能加载 Java 类/库或写入同步缓存，又依赖环境中可控的 JRE/JDK，则可形成从本地低权限到服务账户权限的跃迁。

### 可构造的验证请求

在测试虚拟机中以普通用户执行：

```powershell
Get-Service -Name PADJavaSyncService | Select-Object Name,Status,StartType
```

随后只向已发现的本地端点发送一个包含 `safe-canary-<RAND>` 对象名的**只读列举/ping**消息；若端点使用命名管道，先读取安全描述符：

```powershell
Get-Acl '\\.\pipe\<PIPE>' | Format-List
```

不向端点发送动态库路径、命令行、脚本内容或文件写入指令。以服务身份/进程监视器记录是否有目标进程处理 marker。

### 命中判据

服务进程读取 marker、返回该 marker 对应的对象/错误信息，或事件日志出现 marker；且以本地管理员身份停止服务后，同一请求失败。停止服务能够完全阻断攻击链，正好与官方缓解一致，构成版本/服务行为差异证据。

### 排除判据

- 已安装 2.69+；
- 服务不存在、未安装或未运行；
- 当前用户没有访问端点所需的 DACL；
- 只观察到客户端自身逻辑处理 marker，服务端无响应；
- 服务处理 marker 但始终在调用者权限下运行，且无法跨越权限边界；
- 任何写入磁盘、加载库、调用 `CreateProcess` 的请求都不属于本验证步骤。

## 案例 6：Xiiaozet LK100W 的 Web 管理命令注入与认证缺失（CVE-2026-78037 等）

### 公告原文摘录

1. **CISA ICS 公告 ICSA-26-239-01（2026-08-27）**：受影响版本为 LK100W <2.1.240；CVE-2026-78037 是“OS command injection through its web-based management interface”，已认证攻击者可以高权限执行任意操作系统命令；CVE-2026-78239 暴露了一个无需认证即可调用的关键管理功能；CVE-2026-76943 在管理服务的认证弱点可绕过预期访问控制并获得命令执行能力。[6]
2. 修复建议为升级到 2.1.240。[6]

### 措辞反推

三个 CVE 构成一条完整链路。CVE-2026-78037 表明 Web 管理输入进入了 OS 命令构造，说明缺的是**参数化/白名单、shell 元字符拒绝、参数边界而非字符串过滤**；CVE-2026-78239 说明某些关键功能没有认证门禁；CVE-2026-76943 则说明主入口与管理服务的访问控制策略不同步。组合含义是：认证不是统一拦截器，而是分散在各服务/路由中重复实现，导致某一内部服务或 RPC 方法漏掉了“身份、权限、功能开关”三件套。测试时只能从公告承认的 Web 管理面出发，不能假定未公开的内部端点存在。

### 组件定位信息

- **定位**：工业设备 Web 管理面/固件；攻击面在网络可达的 HTTP 管理接口。
- **版本区间**：CISA 给出的边界是 LK100W <2.1.240，三个 CVE 共享该范围；修复版为 2.1.240。[6]
- **测试要求**：仅在厂商测试设备/赏金隔离网段操作；不得影响生产 PLC、网关或下游控制对象。

### 外推假设（待验证）

- **同族接口**：同模块 GET/POST、创建/修改/删除、导入/导出、备份/恢复、日志/诊断、证书、DNS、时间同步，都可能复用同一参数拼装逻辑。
- **入口变形**：管理端与设备端、v1/legacy 路径、JSON 与 form 编码、同名参数重复出现、参数从 query 移到 body，都可能绕过只检查一个位置的校验。
- **等价变形（待代码审计）**：若真实参数进入 shell，黑名单过滤可能存在 `&`/`|` 之外的等价写法、空格替代、变量展开、命令替换、编码、参数分割；本报告不提供可直接利用 payload。
- **串联**：未认证管理功能 + 命令注入可从网络可达跃迁为设备完全控制，进而影响串行/工业控制链路；检测上应重点监控设备外连、管理服务子进程和配置漂移。

### 可构造的验证请求

在授权的管理员会话中，对公告所确认的 Web 管理面提交只读名称字段：

```http
POST /admin/config/safe-endpoint HTTP/1.1
Host: 192.0.2.10
Cookie: <authorized session cookie>
Content-Type: application/json
User-Agent: SRC-Canary/1.0

{"name":"canary-<RAND>","description":"src-verification"}
```

`<RAND>` 只用于追踪。不要向 shell 命令、诊断命令、备份脚本名、文件名、证书字段插入元字符；不要使用 ping、DNS、time 等可能成为执行载体的探测值。

### 命中判据

只有以下一种低风险证据成立：响应/管理日志将 marker 原样回显并进入命令执行上下文。更稳妥的做法是只观察**字段校验行为**：提交过长、特殊字符、空值、重复字段时是否产生不同的模式校验/编码响应；若某响应明确显示“命令执行失败/参数非法”，说明该字段进入了命令构造，应立即停止并报告。

### 排除判据

- 固件为 2.1.240+；
- 无法建立授权管理会话，且公告未确认目标功能无认证；
- 响应只回显 HTML/JSON，未显示 marker 被解释为命令；
- 错误由前端 JavaScript 产生，后端未处理；
- 设备日志无 marker、服务子进程无 marker；
- 任何命令执行、设备重启、配置写回请求均不是本探针的目标。

## 案例 7：EnOcean SmartServer IoT 的 LON IP-852 消息解析（CVE-2026-20761）

### 公告原文摘录

1. **CISA ICS 公告 ICSA-26-050-01（2026-02-19）**：受影响设备为 EnOcean SmartServer IoT ≤4.60.009；CVE-2026-20761 为“remote attackers, in the LON IP-852 management messages, to send specially crafted IP-852 messages resulting in arbitrary OS command execution on the device”。[7]
2. CVE-2026-22885 为越界读取；修复版本为 SmartServer 4.6 Update 2（v4.60.023）或更高。[7]

### 措辞反推

“specially crafted IP-852 messages”是协议级线索：解析器先按 LON/IP-852 帧结构读取长度、类型、字段，之后某个字段被转交给特权操作。缺失的校验应在**解析层**：声明长度与实际缓冲区、字段枚举与未知类型、消息序号与状态、消息来源与认证、消息语义与执行权限之间没有保持不变量。公告把命令执行与越界读分开编号，说明同一个入口可能同时有内存安全问题和语义授权问题；后者才是可通过网络稳定利用的前置风险。

### 组件定位信息

- **定位**：工业 IoT 边缘平台/固件，管理面接受 LON IP-852 协议；属于网络协议解析与设备控制的交界。
- **版本区间**：CISA 列出的受影响版本为 ≤4.60.009；修复版本为 4.60.023+。[7]
- **测试边界**：需要在完全隔离的工控测试床复现；不得向生产 LON 网络、路由器或控制器发送测试帧。

### 外推假设（待验证）

- **同族入口**：不同 IP-852 消息类型、配置/状态切换、设备发现、路由与转发消息可能共享解析器。
- **协议变形**：长度字段边界、整数符号、最大帧长、分片重组、重复/乱序消息、未知消息类型、保留位、校验和绕过都是可观察假设；不能直接把它们转化为攻击包。
- **串联**：若越界读可泄露内存、命令执行可从管理面获得 root，工控语义层的危害会由“服务崩溃”跃迁为物理过程操控；应以设备日志、服务重启、进程崩溃作为安全告警指标。

### 可构造的验证请求

在隔离测试床中，由同一管理网络向监听 IP-852 的目标端口发送仅含随机 marker 的合法框架占位：

```text
IP-852 marker frame（仅结构示意，授权测试床使用）
00 01 02 03 <marker 4-byte> ... padding to declared length
```

具体协议版本、magic、校验和由测试床合法捕获的真实报文复制而来；不发布完整可用利用帧。同步记录设备管理日志、服务进程和端口响应。

### 命中判据

设备在授权测试床的调试/报文日志中识别并处理 marker 消息编号；或管理面返回对应错误；或连续重复特定边界长度时服务出现可恢复的异常。若服务异常，必须记录 core dump/事件日志、请求时间戳并立即重启恢复。

### 排除判据

- 固件为 4.60.023+；
- 报文未到达 IP-852 监听端口；
- 日志只显示协议握手，未处理 marker 字段；
- 响应由中间网关生成；
- 仅 TCP 连接成功，不等于消息被解析；
- 任何试图将 marker 替换为命令或观察物理输出的步骤均超出无害探针范围。

## 案例 8：Content Credentials / C2PA SDK 提取阶段的任意文件写入（CVE-2026-34657）

### 公告原文摘录

1. **Adobe 安全公告 APSB26-61（2026-06-09）**：受影响产品为 `Content Credentials JS SDK @contentauth/c2pa-web@0.7.1 and earlier` 与 `Rust SDK c2pa-v0.80.1 and earlier`；修复版本分别为 `@contentauth/c2pa-web@0.8.3` 与 `c2pa-v0.85.1`。[8]
2. **NVD/CVE 记录**：该缺陷是“Improper Limitation of a Pathname to a Restricted Directory (CWE-22)”，可导致任意文件系统写入；利用条件是“victim must extract a maliciously crafted file”。[9]

### 措辞反推

“extract a maliciously crafted file”说明动作发生在**客户端解压/提取阶段**；“write to unauthorized files or directories outside of intended restrictions”说明防护不是“检查字符串是否含 `..`”，而是**最终规范路径必须位于目标目录白名单之下**。推断流程为：读取 archive/manifest entry name → 可能解码或规范化一次 → 拼接到提取目录 → 打开文件写入；补丁应把校验移到打开前，对绝对路径、`.`、`..`、符号链接、大小写、编码、长 UTF-8 都重新规范化，再比较允许根。因 SDK 跨 Windows、macOS、Linux、iOS、Android，路径语义和保留名也是平台差异点。

### 组件定位信息

- **定位**：内容凭证/证明嵌入与解析 SDK；攻击面在客户端或服务器端处理不可信媒体/凭证文件。
- **版本区间**：JS SDK ≤0.7.1，Rust SDK ≤0.80.1 受影响；修复版为 JS 0.8.3、Rust 0.85.1。[8][9]
- **平台差异**：同一 entry 名称在不同 OS 和归档解析库中的规范化结果可能不同，需在目标平台分别测试。

### 外推假设（待验证）

- **同族入口**：提取、解压、临时目录创建、缩略图/asset 写出、manifest 资源缓存、签名状态写入，都可能需要统一的目标路径策略。
- **等价变形（代码审计）**：`..`、绝对路径、`/` 与 `\`、dotted name、Unicode 规范化、重复斜杠、URL 编码、NUL、结尾点/空格、交替数据流；补丁若只做一次校验，后续 symlink 或规范化可能改变落点。
- **串联**：不可信文件被解析后写入应用配置、脚本目录、凭证缓存或动态加载路径，可从文件写入跃迁为代码执行；运行时必须以低权限沙箱、禁止符号链接跟随、写入后二次校验。

### 可构造的验证请求

在隔离 VM 中构造一个**不包含任何目录穿越片段**的 marker 档案：

```text
c2pa-canary.zip
└── safe-canary-<RAND>.bin
```

由目标 SDK/应用按正常流程“提取/打开”该文件，观察提取输出目录。marker 文件名只含字母数字和连字符。可另构造一份包含符号链接 `canary-link -> /tmp/allowed/` 的档案，但只在允许 symlink 的授权测试目录内指向同样由测试者控制的允许目录；不指向系统路径。

### 命中判据

SDK 将文件写到预期提取根之外，或符号链接使提取流程跟随到允许目录外的真实目标；进程监视器记录打开/写入路径。若补丁版本只在最终写入前重新规范化，则旧版应复现偏差而新版不发生，形成版本差异证据。

### 排除判据

- JS SDK 为 0.8.3+ 或 Rust SDK 为 0.85.1+；
- 文件只进入允许提取目录；
- 链接目标仍在白名单内；
- 写入由底层归档库而非 C2PA SDK 触发；
- 应用未真正“提取”，仅解析内存字节；
- 使用真实系统路径、覆盖系统文件或替换可执行文件不属于本报告探针。

## 案例 9：Adobe ColdFusion RDS 文件 I/O 的受限目录检查缺失（CVE-2026-48282）

### 公告原文摘录

1. **Adobe 安全公告 APSB26-68（2026-07）**：影响范围为 Adobe ColdFusion 2025 ≤ Update 10，以及 2023 系列低于对应补丁的版本；公告页面要求读取官方补丁下载地址确认准确构建串。[10]
2. **第三方安全通告**：利用条件包括 RDS 功能已启用（默认未启用）且 RDS 的身份验证功能被禁用；公开复现请求使用了 `/CFIDE/main/ide.cfm?ACTION=FILEIO` 的 `Content-Type: application/octet-stream` 请求。[10]

### 措辞反推

公告确认这是 RDS/ide 文件 I/O 入口，而不是任意 CFML 页面问题。可推断：当 RDS 开启且认证关闭时，攻击者可直接进入文件管理路径；接口对请求中的文件名/路径缺少**规范化后的受限目录检查、对象级会话/身份绑定，以及上传落点白名单**。进一步反推修复不只应“加强过滤”，而应把 RDS 的认证、授权、路径范围、文件类型与写权限统一在文件 I/O handler 之前。第三方页面给出的 HTTP 结构可作为受控测试中的入口坐标，但不应把第三方复现内容直接当成完整利用。

### 组件定位信息

- **定位**：企业 Java Web 中间件；RDS/ide 端点位于管理/开发面。
- **版本区间**：Adobe ColdFusion 2025 ≤ Update 10，以及 2023 低于对应补丁版本受影响；准确修复构建必须以 Adobe 官方公告页面为准。[10]
- **测试条件**：仅测试自有授权实例；先确认 RDS 状态与补丁构建，不主动关闭生产实例认证。

### 外推假设（待验证）

- **同族入口**：文件浏览、读取、上传、删除、重命名、目录列举、项目同步、调试、数据源配置，可能共用 ide/RDS 分派器。
- **入口变形**：`/CFIDE/main/ide.cfm`、`/CFIDE/remote/` 的不同 action、旧版路径、大小写、分号/参数重复，均可能落到同一文件 I/O handler；必须以 404/405/403 和实际功能响应区分。
- **串联**：未认证 RDS + 文件写/读可将管理面扩展为代码部署或配置篡改；监控 RDS 端点、异常文件落点、管理日志和 CFML 编译目录是关键。

### 可构造的验证请求

在 RDS 已确认开启且处于授权隔离环境的实例中，只发送标识请求，不发送可执行文件内容：

```http
POST /CFIDE/main/ide.cfm?ACTION=FILEIO HTTP/1.1
Host: cf-test.example.local
Content-Type: application/octet-stream
User-Agent: SRC-Canary/1.0
Content-Length: 15

safe-canary-001
```

请求必须位于明确的赏金范围；若厂商公告不授权测试该端点，应停止。观察响应是否承认 ACTION、是否进入文件 I/O、是否产生可读的调试/错误标识；不读取任意文件，也不写入 webroot。

### 命中判据

应用返回非通用 404，且响应体或日志显示已进入文件 I/O handler；或认证关闭的管理端点可访问。若 ACTION 被拒绝、返回 403、需要有效 RDS 会话，则说明该版本/配置不满足条件。命中仅证明入口暴露，不证明任意文件读写。

### 排除判据

- ColdFusion 已安装公告指定 Update 10 之后的准确构建；
- RDS 未启用；
- RDS 启用且认证强制有效；
- 响应为 404/403/405，且日志没有文件 I/O 处理证据；
- 错误由 WAF/反向代理产生；
- 使用真实路径、读取敏感文件或上传 JSP/CFM 不属于本报告探针。

## 案例 10：Apache ActiveMQ Jolokia 管理操作导致远程代码执行（CVE-2026-34197）

### 公告原文摘录

1. **CNNVD/CNNVD-202604-1392**：攻击者可通过 ActiveMQ 的 Jolokia API 调用管理操作，诱使代理获取远程配置文件并执行任意系统命令；影响范围为 5.19.4 之前版本和 6.0.0 至 6.2.3 之前版本。[11]
2. **第三方风险通告（2026-04-07）**：漏洞可利用 `Jolokia API` 调用 `addNetworkConnector` 操作，利用 `vm://` 传输加载远程 Spring XML 配置文件；公开资料还给出 POC 与受影响资产统计。[11]

### 措辞反推

公告把问题限定在“Jolokia API 调用管理操作”，并指向 `addNetworkConnector` 与 `vm://` 传输。由此反推，缺陷不在 Jolokia 本身必然开放，而在**管理操作的可调用集没有被最小化**：允许通过 HTTP 管理面动态添加网络连接器，又允许 `vm://` 传输从远程 URL 加载配置对象。缺失的是：动态管理操作白名单、调用者权限/角色、传输协议许可、远程资源配置来源、对象反序列化/XML 处理上下文，以及连接器创建后的生命周期约束。第三方材料已出现公开可利用 POC，因此本报告只构造“管理 API 是否暴露”的最小指纹，不发送 `addNetworkConnector` 或外部 XML URL。

### 组件定位信息

- **定位**：企业消息中间件/服务；攻击面在 Jolokia JMX-over-HTTP 管理 API。
- **版本区间**：Apache ActiveMQ 5.19.4 之前版本，以及 6.0.0 至 6.2.3 之前版本受影响。[11]
- **部署差异**：默认是否暴露 Jolokia、是否要求认证、网络分段都会改变可利用性；赏金报告必须同时记录版本和配置。

### 外推假设（待验证）

- **同族入口**：所有 Jolokia 可写 MBean、动态连接器/transport/ broker policy 配置，都应被视为高权限管理面；但只测试只读列举。
- **入口变形**：不同 web 应用前缀、JMX 域、HTTP 方法与 content-type、跨上下文路径、管理端与代理端可能共用或分离。
- **串联**：Jolokia 写权限 + 动态连接器/远程配置加载可把“消息队列管理”跃迁为中间件主机代码执行；检测应关注异常连接器创建、外部 XML 下载、JVM 类加载和子进程。

### 可构造的验证请求

仅向授权测试实例发送只读 Jolokia 列举请求：

```http
GET /api/jolokia/list HTTP/1.1
Host: amq-test.example.local
Accept: application/json
User-Agent: SRC-Canary/1.0
```

若实例把 Jolokia 部署在别的前缀，应按部署文档调整。请求不带认证材料、不创建连接器、不引用 `vm://`、不访问外部 URL。

### 命中判据

未经授权或仅低权限即可取得 MBean 列表；响应中包含 `org.apache.activemq` 的管理对象；或管理 API 返回 200 而非 401/403。重复请求结果稳定，并在启用认证/网络隔离后不可访问。命中仅证明管理 API 暴露或权限过宽，不构成 RCE 证明。

### 排除判据

- ActiveMQ 为 5.19.4+ 或 6.2.3+；
- Jolokia 路径不存在或返回 404；
- 需要有效管理员凭证；
- 仅列出本地 MBean 但无法调用写操作；
- 代理网络策略明确禁止动态连接器；
- 任何 `addNetworkConnector`、`vm://`、外部 XML 下载请求都不属于本报告验证步骤。

## 跨案例归纳：把公告措辞翻译成缺失校验

### 可复用的“措辞 → 根因”对照表

| 公告高频句式 | 真正指出的缺失防线 | 立即生成的测试问题 | 推荐证据形态 |
|---|---|---|---|
| “unsanitized <请求头>” | 外部头值不得成为内部路径/文件名；写前重新规范化 | 头值是否进入日志/路径？是否有最终落点白名单？ | 请求 ID + 后端日志 + 版本差异 |
| “attacker-supplied <配置/URL>” | 服务端出口目标应由用途策略决定，不能照搬用户输入 | 谁批准了出站？是否限制 scheme/主机/路径/重定向？ | DNS/HTTP 审计记录 + 拓扑限制 |
| “did not properly enforce <策略>” | 策略需绑定到端点、动作、身份来源和对象 | 策略在哪一层计算？是否有默认拒绝？ | 策略配置 + 会话/审计日志 |
| “specially crafted <协议> message” | 解析长度/类型/状态/来源/权限不变式 | 边界值是否一致？未知类型是否拒绝？ | 报文日志 + 服务行为 + 崩溃转储（隔离） |
| “through its web management interface” | 管理面输入进入命令/文件/执行上下文 | 参数边界、鉴权、写前落点是否独立检查？ | 参数回显/模式校验，不做破坏测试 |
| “must <解析/打开/提取> a crafted file” | 处理不可信输入前需建立安全上下文 | 来源是否可信？是否沙箱？是否写入白名单目录？ | marker 文件 + 提取路径日志 |
| “bypassing <身份组件>” | 身份来源是对象/会话的不可变属性，不是入口标签 | 登录后是否仍按来源检查？会话能否切换来源？ | 身份来源审计 + 权限边界 |
| “service exposes <功能> without authentication” | 每个 RPC/方法都需认证、授权、功能开关 | 服务间信任是否替代了用户/调用者身份？ | 停服前后对比 + ACL |
| “only authenticated <时间戳>” | 完整性保护范围需覆盖路径、方法、关键参数和重放窗口 | HMAC/签名覆盖哪些字段？有效期多久？ | 出站请求审计 + 协议规范 |
| “can be reached over the network” | 网络暴露面不等于安全入口；需最小权限与网络分段 | 是否允许匿名？管理面是否误绑定公网？ | 端口/路由扫描 + 认证矩阵 |

**规律一：公告动词决定测试动作。**“delete/cause to send/create account/execute”描述的是安全敏感动作，测试却不能重复动作本身；应改为观察动作是否可到达、参数是否被内部使用、权限边界是否改变。这样既能写报告，也不会越过合规边界。

**规律二：公告名词决定对象。**`X-GitHub-Request-Id`、`cluster configuration`、`.idea`、Jolokia API 都不是泛化提示，而是闭源环境下的“内部变量名”。把它们做成版本差异测试中的追踪 marker，比盲目 fuzz 参数名更有信息量。

**规律三：公告副词决定前置条件。**“unauthenticated”“local”“with user interaction”“when external authentication is enabled”“HA deployments were not affected”都是命中条件。缺少这些事实，即使观察到相似现象也不能声称同一漏洞。

**规律四：补丁建议本身就是反推材料。**Microsoft 说停 Java 同步服务、Adobe 说升级 SDK、CISA 说升级固件，分别把根因锁定到服务、解析库和固件版本。版本字符串、服务名、模块名、公告日期应作为闭源环境的第一组资产指纹。

**规律五：公告不说的部分才是对手要猜的。**GitHub 公开了请求头和清理生命周期，ColdFusion 公开了入口但要求读准确补丁构建，ActiveMQ 已有公开 POC 因此只能做最小指纹，工业协议往往不公开报文细节。对后两类应停止在“版本/入口/可达性”，把具体利用留给授权代码审计或厂商隔离环境。

## 合规与验证纪律

1. 本报告仅服务于授权资产、厂商赏金范围或隔离测试环境；任何未授权目标均不发送请求。
2. 所有 marker 均为随机、唯一、可逆、只读字符串；不使用命令替换、路径穿越、外部脚本或生产敏感数据。
3. 对 CVE-2026-17556 不发送遍历值；对 CVE-2026-18730 不捕获或重放 token；对 CVE-2026-34197 不调用 `addNetworkConnector` 或 `vm://`；对 CVE-2026-20761 不在生产工控网络发送协议帧；对 CVE-2026-34657 不写入系统路径；对 CVE-2026-78037 系列不进行命令执行。
4. 对无法从公开公告确认的路径、协议、服务名、报文结构，统一标注“待验证”；不得把待验证外推写成已确认根因。
5. 每个案例至少保留：公告原文、CVE/公告链接、披露日期、受影响版本、修复版本、测试请求、时间戳、响应/日志、排除条件。只有形成可重复的版本差异，才适合作为 SRC 报告。
