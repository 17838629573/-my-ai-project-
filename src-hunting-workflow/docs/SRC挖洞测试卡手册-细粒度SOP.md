# SRC 挖洞测试卡手册（细粒度 SOP）

## 为什么需要"卡片级"颗粒度

粗粒度的工作流长这样：**"测一下越权"**。
问题是——测哪个接口？改哪个参数？改成什么值？返回什么算中？返回什么算没中？

没有这四个答案，就会出现两种失控：
- **漏扫**：只测了列表页的 ID，没测导出接口、批量接口、子资源接口
- **误扫**：把"返回自己的数据"当成越权提交，或者把正常的分页参数当漏洞

所以每张卡固定五要素：

| 要素 | 作用 |
|---|---|
| **操作** | 具体到改哪个字段、改成什么值 |
| **命中判据** | 响应满足什么条件才算中（可客观判定） |
| **排除判据** | 满足什么条件明确判定为没中 |
| **易错点** | 这一步最容易搞错/漏掉的地方 |
| **记录** | 必须留下的证据字段 |

> 纪律：每测完一张卡，必须填状态 `[ ]/[~]/[?]/[!]`。**`[~]` 也要写一句排除理由**，否则等于没测。

# 模块 A：越权与未授权（SRC 产出占比最高，优先打）

## A1 删凭证未授权访问
- **操作**：拦截任意业务接口请求 → 整个删除 `Cookie` / `Authorization` 头 → 重放
- **进阶**：换成空值、换成过期 token、换成任意用户的 token
- **命中判据**：仍返回 HTTP 200 且 body 含业务数据（非"请先登录"）
- **排除判据**：401/403 且 body 无数据
- **易错点**：
  - 只测 GET，忘了 POST/PUT/DELETE 同样要试
  - 只测主域名，API 子域往往是另一套鉴权
  - 网关鉴权但后端服务直连可达（试直接访问内网 IP/端口）
- **记录**：接口路径、无凭证响应截图、返回数据样例（脱敏）

## A2 水平越权 — 资源 ID 替换
- **操作**：两个账号 A/B 各建一条数据 → 用 A 的凭证请求 A 的数据，把请求中的资源 ID 换成 B 的
- **ID 出现的位置要全部试遍**：URL path、query 参数、POST body、JSON 字段、Header、Cookie 值
- **命中判据**：A 拿到了 B 的数据（含手机号、地址、订单内容等）
- **排除判据**：返回 403，或返回空/自己的数据
- **易错点**：
  - 只改一个位置的 ID。很多系统 path 和 body 里都有 ID，只改一处会被服务端用另一处校验
  - ID 是加密/哈希的，就先找"ID 从哪里来"——列表接口、返回包、前端 JS 里往往有明文或其他用户的 ID
  - 只测读，忘了改（PUT）和删（DELETE）
- **记录**：两个账号标识、两个 ID、替换位置、响应对比截图

## A3 水平越权 — 批量/列表接口
- **操作**：A 凭证调用列表接口 → 改分页参数（`pageSize` 调大、`page` 越界）→ 看是否返回他人数据
- **进阶**：列表接口带筛选条件（如 `userId`、`status`）→ 改成他人/全部
- **命中判据**：响应中出现非 A 的数据
- **排除判据**：始终只返回 A 自己的数据
- **易错点**：这类接口危害更大（一次拿全量），但常被忽略，因为"看起来只是在查自己的列表"
- **记录**：接口、参数值、返回条数、数据归属证明

## A4 间接引用越权
- **操作**：不直接改 ID，而是改"间接标识"——手机号、邮箱、订单号、昵称、身份证号
- **场景**：查订单时不传 orderId，传 `phone`；查用户时不传 uid，传 `email`
- **命中判据**：用别人的手机号查到了别人的订单/资料
- **易错点**：这是 A2 测不到时的备用路径，很多人测完 A2 就收工了
- **记录**：间接字段名、取值、响应

## A5 创建型越权（归属可指定）
- **操作**：用 A 的身份创建资源（下单、发评论、建地址、发优惠券）→ 在请求包里加/改归属字段（`userId`、`ownerId`、`belongTo`）
- **命中判据**：资源被创建到 B 名下
- **易错点**：前端没有这个字段不代表后端不接受——**手工加字段**进去试
- **记录**：请求包（含新增字段）、创建结果归属

## A6 垂直越权 — 角色字段与路径
- **操作**：
  1. 请求包中加/改角色字段：`role`、`userType`、`isAdmin`、`level`
  2. 直接访问管理路径：`/admin`、`/manage`、`/api/admin/...`
  3. 把普通用户 token 放到管理接口上
- **命中判据**：普通用户执行了管理操作或拿到了管理数据
- **排除判据**：403 且无数据
- **易错点**：管理路径不一定在页面上，要去 JS 文件、`sitemap`、Swagger 文档里找
- **记录**：路径/字段、普通账号标识、操作结果

## A7 子资源越权（二级对象）
- **操作**：主资源归属 A，但子资源 ID 属于 B。例：A 的项目下，用 B 的文件 ID 去下载
- **命中判据**：跨主体访问成功
- **易错点**：主资源校验了，子资源没校验——这类漏判极常见
- **记录**：主资源 ID、子资源 ID、响应

## A8 多步流程越权
- **操作**：多步流程（如订单创建→确认→支付）中，在某一步替换 ID
- **命中判据**：前后步骤的归属校验不一致，某一步可跨用户
- **易错点**：单步测都正常，但步骤间校验不一致
- **记录**：流程图式记录哪一步失守

# 模块 B：认证与凭证（验证码/找回密码）

## B1 验证码爆破
- **操作**：重放发送验证码请求 → 用 0000-9999（4位）或 000000-999999（6位）遍历
- **命中判据**：某次验证成功
- **排除判据**：错误次数限制、锁定、验证码有效期极短（<1分钟）且无法重发
- **易错点**：
  - **先看有没有次数限制再爆破**，有锁定就换思路（B2/B3）
  - 验证码有效期：先测能否反复发送刷新，决定了能否长跑
- **记录**：是否有限制、限制阈值、爆破结果

## B2 验证码复用 / 不失效
- **操作**：用同一个验证码连续提交两次；或验证成功后再次使用该验证码
- **命中判据**：第二次仍通过
- **易错点**：这是爆破被限时的**替代路径**，务必测
- **记录**：验证码值（脱敏）、两次请求与响应

## B3 验证码与手机号不一致
- **操作**：给手机号 138xxxx 发验证码 → 在验证请求里把手机号改成 139xxxx
- **命中判据**：验证通过（等于可验证任意手机号）
- **变体**：响应包里直接返回验证码；验证码放在 URL/Set-Cookie 里
- **易错点**：**一定去看发送验证码的响应包内容**，很多厂商直接把码放在返回里
- **记录**：发送手机号、验证手机号、响应包截图

## B4 密码找回 — 流程跳过
- **操作**：找回流程多步（验证身份→设新密码）→ 直接请求最后一步，跳过前置步骤
- **命中判据**：未经验证即可设置新密码
- **易错点**：前端跳转不等于后端校验，用 Burp 直接构造最终请求
- **记录**：跳过的步骤、最终请求包

## B5 密码找回 — Token 问题
- **操作**：取回 token → 测试：可复用？永不过期？可预测（时间戳/自增/手机号 MD5）？能用于改他人账号？
- **命中判据**：任一成立即中
- **易错点**：把 token 中的用户标识改掉，看能否重置他人密码——这是**高危**
- **记录**：token 样本（脱敏）、测试结果

## B6 用户名/手机号枚举
- **操作**：登录/注册/找回页输入已存在与不存在的账号，对比响应差异（错误文案、响应时间、HTTP 码）
- **命中判据**：可区分存在与否
- **注意**：多数 SRC 定级为低危/信息泄露，单独提交价值有限，但可配合其他漏洞提升评级
- **记录**：两种响应的对比截图

## B7 会话失效
- **操作**：退出登录后，用旧 token/Cookie 重放业务请求
- **命中判据**：仍可访问
- **变体**：修改密码后，其他设备的会话是否失效
- **记录**：旧 token、重放响应

## B8 JWT 问题
- **操作**：拿到 JWT → jwt.io 解码 → 测试：
  1. `alg` 改为 `none`，去掉签名
  2. 弱密钥暴力破解（常见：secret、123456、公司名）
  3. 改 `exp` 延长有效期
  4. 改 payload 中的用户标识/角色
- **命中判据**：篡改后的 token 被服务端接受
- **记录**：原始 token（脱敏）、篡改方式、响应

# 模块 C：业务逻辑（支付/优惠券/并发）

> 铁律：**只做最小危害验证**。不要真完成支付、不要真改生产订单、不要刷真实库存。用测试环境或小额/自有账号。

## C1 金额篡改
- **操作**：下单请求中改 `price`/`amount`/`totalFee`/`discount`
- **命中判据**：服务端按篡改后的金额生成订单
- **排除判据**：服务端重新计算，忽略前端传值
- **易错点**：
  - 前端改了没用→改请求包
  - 单价改不动→改数量、改运费、改优惠金额、改积分抵扣
  - 改不动→试**负数**、**小数**、**超大数**（整数溢出）
- **记录**：原始金额、篡改值、服务端生成的订单金额

## C2 数量与边界值
- **操作**：数量改 `0`、`-1`、`0.001`、极大值
- **命中判据**：订单金额异常、库存异常、可 0 元下单
- **记录**：数量值、服务端响应、订单结果

## C3 优惠券/积分并发
- **操作**：限领 1 张的优惠券 → Burp Intruder 并发 20 个请求同时领取
- **命中判据**：领到多张
- **变体**：重复使用同一张券（并发下单）、退款后券是否回收
- **易错点**：单线程测必定正常，**必须并发**
- **记录**：并发数、成功次数、截图

## C4 库存与超卖
- **操作**：库存 1 件的商品，并发下单
- **命中判据**：生成多笔订单
- **注意**：电商类 SRC 通常认可，但要在测试环境，避免影响真实用户
- **记录**：库存数、订单数

## C5 支付回调伪造
- **操作**：下单后不支付，直接构造"支付成功"的回调请求发给业务接口
- **命中判据**：订单状态被改为已支付
- **进阶**：回调中改订单号/金额，看是否校验
- **记录**：回调接口、构造的请求、订单状态变化

## C6 退款/提现
- **操作**：退款金额改大、重复提交退款、退款数量超过购买数量、提现并发
- **命中判据**：可超额退款/重复退款
- **注意**：**高危且敏感**，只在规则允许范围内做最小验证，不得造成真实资金变动
- **记录**：操作与响应（不实际造成损失）

## C7 流程顺序绕过
- **操作**：不按顺序走——跳过购物车直接下单、未付款直接发货、未完成前置任务直接领奖
- **命中判据**：状态机校验缺失
- **记录**：跳过的步骤、直接请求的接口

# 模块 D：注入与服务端（自动化 + 手工结合）

## D1 SQL 注入
- **覆盖位置**：URL 参数、POST body、Header（UA/X-Forwarded-For）、Cookie、JSON 字段
- **手法**：单引号报错、`AND 1=1/1=2` 差异、时间盲注、ORDER BY 注入、二次注入（存入后在其他功能点触发）
- **命中判据**：报错回显 / 响应差异 / 时间延迟可复现
- **易错点**：
  - 只测 GET 参数，漏掉 JSON/Header
  - 有 WAF 就放弃——先试编码、注释、分块传输等基础绕过
  - 忘了**二次注入**（注册时注入，查询时触发）
- **记录**：注入点、payload、响应证据（不拖库，证明可读即可）

## D2 SSRF
- **覆盖位置**：所有接受 URL 的参数——图片/头像远程加载、Webhook、导出、代理、PDF 生成、图片处理
- **命中判据**：目标服务器发起了你控制的请求（用 DNS 外带平台验证）
- **进阶**：探测内网、云元数据（169.254.169.254）、file:// 读文件
- **记录**：参数、外带请求日志

## D3 文件上传
- **操作顺序**：
  1. 改后缀 → 2. 改 Content-Type → 3. 改 Magic Number → 4. 双后缀/大小写/空格/点/`::$DATA` → 5. 解析漏洞（.php.jpg、.phtml）→ 6. 二次渲染绕过（图片马）→ 7. 路径穿越（`../`）
- **命中判据**：文件可被解析执行，或写入非预期目录
- **记录**：文件名、绕过方式、访问 URL（证明可解析）

## D4 模板注入 SSTI
- **位置**：邮件模板、页面渲染、导出模板、错误页
- **payload**：`{{7*7}}`、`${7*7}`、`<%= 7*7 %>` 分别试，看是否输出 49
- **记录**：输入点、payload、渲染结果

## D5 组件 CVE
- **操作**：从指纹（响应头、报错页、`/favicon.ico` hash、页面特征、JS 库版本）判断组件与版本 → 比对 CVE
- **重点组件**：Shiro、Fastjson、Log4j2、Struts2、WebLogic、Jenkins、ThinkPHP、Spring 系列
- **命中判据**：版本在受影响区间（多数 SRC 要求提供验证证据，不能只报版本号）
- **记录**：版本证据截图、验证方式

# 模块 E：信息泄露（低成本，顺手捡）

- [ ] `/actuator`、`/env`、`/metrics`、`/heapdump`（Spring Boot）
- [ ] `/.git/`、`/.svn/`、`/.DS_Store`、`/WEB-INF/`
- [ ] Swagger：`/swagger-ui.html`、`/api-docs`、`/v2/api-docs`
- [ ] 备份文件：`www.zip`、`bak.rar`、`.sql`、`域名.tar.gz`
- [ ] 报错页泄露堆栈、SQL 语句、绝对路径
- [ ] 前端 JS 中的硬编码密钥（AK/SK、API Key、内网地址）
- [ ] 云存储 bucket 未授权列举
- [ ] 日志/监控接口（Kibana、Prometheus、Druid）未授权

# 收尾自查（每题必须能答"是"才提交）

1. 我能用**最小危害**方式稳定复现吗？
2. 我记录的请求包是否**脱敏**了（域名、真实账号、Cookie 可按平台要求保留必要部分）？
3. 危害描述说的是**业务后果**（能读到多少用户的数据/能造成什么损失），而不只是技术名词吗？
4. 修复建议落到**代码/配置**层面了吗？
5. 这个洞是否在平台**授权范围**内？有没有触碰禁止项（DoS、社工、真实资金变动）？
6. 新人照着我的步骤能复现吗？
