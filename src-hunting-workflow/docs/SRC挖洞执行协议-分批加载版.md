# SRC 挖洞执行协议（分批加载版）

> 核心思想：**规则总数很多，但同时生效的必须很少。**
> 全局只常驻 5 条铁律，其余按"批次"临时加载，每批 ≤4 张卡。

---

## 一、注意力预算规则（这套协议的地基）

| 约束 | 具体值 | 原因 |
|---|---|---|
| 全局常驻铁律 | ≤5 条 | 永远生效，不占额外注意力 |
| 单批卡片数 | ≤4 张 | 超过 4 张，判据开始互相干扰 |
| 单批状态字段 | ≤5 个 | 够用即可 |
| 同时推进的批次 | 1 个 | 不允许并行 |
| 出现疑似/命中 | 立即暂停推进 | 转入单卡深挖模式 |

**暂停规则（最重要的一条）**：
一批里只要出现 `[?]` 或 `[!]`，**停止加载下一批**，转入单卡深挖。
此时全局只剩：5 条铁律 + 这一张卡。注意力全部压在一个点上。

---

## 二、全局铁律（永远生效，5 条，不随批次变）

1. **最小危害**：只证明可利用，不拖库、不改生产数据、不造成真实资金变动。
2. **不信任前端**：一律用 Burp 改包验证，前端的限制不算限制。
3. **授权范围内**：只测平台清单内的资产，不碰禁测项（DoS、社工、批量拖库）。
4. **每张卡必须留状态**：`[ ]`未测 / `[~]`排除 / `[?]`疑似 / `[!]`命中。`[~]` 必须写一句排除理由，否则视为未测。
5. **一批一结**：跑完一批，回传状态表，等确认后再开下一批。

---

## 三、批次调度表（按此顺序推进）

| 批次 | 卡片内容 | 卡数 | 优先级 |
|---|---|---|---|
| **P0** | 开工前置（见下） | 6 项动作 | 必须 |
| **P1** | A1 删凭证 · A2 ID 替换 · A3 批量接口 · A4 间接引用 | 4 | 高 |
| **P2** | A5 创建型越权 · A6 垂直越权 · A7 子资源 · A8 多步流程 | 4 | 高 |
| **P3** | B1 验证码爆破 · B2 复用 · B3 手机号不一致 · B4 找回跳步 | 4 | 高 |
| **P4** | B5 找回 token · B6 枚举 · B7 会话失效 · B8 JWT | 4 | 中 |
| **P5** | C1 金额篡改 · C2 数量边界 · C3 券并发 | 3 | 中 |
| **P6** | C4 超卖 · C5 回调伪造 · C6 退款提现 · C7 流程跳过 | 4 | 中 |
| **P7** | D1 SQL 注入 · D2 SSRF · D3 文件上传 | 3 | 中 |
| **P8** | D4 SSTI · D5 组件 CVE | 2 | 低 |
| **P9** | E 信息泄露清单（顺手捡） | 1 组 | 低 |

**卡片的详细操作、命中判据、排除判据、易错点，从《测试卡手册》中按批次号调取，不要一次全读。**

---

## 四、P0 开工前置（6 个纯动作，不涉及判断）

1. 核对目标在平台授权资产清单内
2. 确认该平台禁测项与速率限制
3. 独立浏览器 profile + 新建 Burp 项目（开全量日志）
4. 准备 ≥2 个测试小号（A/B，用于越权对比）
5. 建目录：截图 / 请求包 / 笔记，带时间戳命名
6. 画资产清单：子域名、API 域、后台入口、技术栈指纹

> P0 完成标志：能说出"我要测的资产有几项、最值钱的是哪一个"。

---

## 五、批次交接格式（固定格式，减少沟通损耗）

### 我每批结束回传给你：

```
批次：P1
A1 删凭证      [~] 全部 401，网关统一鉴权
A2 ID 替换     [!] /api/order/detail 改 orderId 可读他人订单
A3 批量接口    [ ] 未测（因 A2 命中，暂停推进）
A4 间接引用    [ ] 未测

下一步建议：转单卡深挖 A2，确认影响面与取证
```

### 你回传给我的最小信息：

- 要继续：`继续 P1` 或 `转深挖 A2`
- 要我分析：贴**脱敏**的请求包 + 响应包 + 一句话说明你观察到的异常
- 要换方向：`跳到 P5`

---

## 六、单卡深挖模式（命中/疑似后进入）

触发条件：任一卡出现 `[?]` 或 `[!]`。

此时只做四件事，做完一件再下一件：

1. **确认可利用**：换账号、换数据、重放 ≥2 次，证明稳定
2. **确认影响面**：涉及多少个接口？多少用户/数据？是单点还是全线？
3. **取证**：请求包 + 响应包 + 界面截图，三样齐全，敏感项打码
4. **写报告**：标题 / 影响范围 / 复现步骤 / PoC / 危害证明 / 修复建议

深挖期间**不加载任何其他卡片的规则**。

---

## 七、收尾自查（提交前 6 问，逐条答"是"）

1. 能用最小危害方式稳定复现吗？
2. 请求包脱敏了吗？
3. 危害写的是业务后果（能读到多少数据/造成什么损失），不是只写技术名词吗？
4. 修复建议落到代码/配置层面了吗？
5. 在授权范围内、没碰禁测项吗？
6. 新人照着步骤能复现吗？

---

## 八、这套协议怎么防"漏扫"和"误扫"

| 问题 | 本协议的对策 |
|---|---|
| 漏扫 | 批次表强制逐批推进，每卡留状态，无状态=未测 |
| 误扫 | 每卡有**排除判据**，不明确命中就记 `[~]`，不臆断 |
| 注意力稀释 | 同时生效规则 ≤5 铁律 + ≤4 卡 |
| 重复劳动 | `[~]` 强制写排除理由 |
| 半途而废 | 一批一结，不允许跳批（除非你主动指定） |
| 命中后贪多 | 出现 `[?]/[!]` 立即暂停推进，先吃透这一个 |
