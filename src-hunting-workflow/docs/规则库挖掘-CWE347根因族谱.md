# 规则库挖掘实证：CWE-347 根因族谱

> 数据源：nuclei-templates（社区最大公开检测规则库，1351 个模板）
> 方法：**不跑扫描器，把规则库当知识源**——检测规则把漏洞完整坐标都写出来了

---

## 为什么规则库比公告值钱

前面我们说过"检测规则是最值钱的碎片"。这次实证了。

一个公告会告诉你"存在认证绕过"。
一个检测规则会告诉你**精确到字节的攻击构造**——看 CVE-2026-10795 的规则：

```
KEY_NAME = "0.central.updraftplus.com"
AES-128-CBC 密钥 = <MD5>
IV             = <MD5>
消息格式 = RSA_LEN(3位hex) + RSA_B64 + CT_LEN(16位hex) + CT_B64
载荷命令 = {"command":"users.get_users", ...}
探测路径 = /wp-content/plugins/updraftplus/readme.txt
FOFA 语法 = body="/wp-content/plugins/updraftplus"
标签 = vkev（已知在野利用）
```

**一个"防御用"的规则，等于把漏洞的完整坐标给了你。**
这比任何 CVE 公告、任何技术分析都详细。

---

## 核心发现：CWE-347 根因族

规则库里 CWE-347（加密签名验证不当）共 3 例：

| CVE | 产品 | 年份 | CVSS | EPSS |
|---|---|---|---|---|
| CVE-2024-45409 | **GitLab** SAML | 2024 | 9.8 | 0.10684 |
| CVE-2025-25291 | **GitLab** SAML | 2025 | 9.3 | 0.20586 |
| CVE-2026-10795 | UpdraftPlus UDRPC | 2026 | 8.1 | 0.03635 |

**三个完全不同的技术栈、完全不同的协议，同一个 CWE。**

这正是我们工作流的核心命题：

> **高价值漏洞不源于某个危险函数，而源于系统在某个状态转换处没有重新验证。**
> 按漏洞类型泛化从一开始就走偏了，要按根因泛化。

## 深度拆解：GitLab 的两次 SAML 绕过

这是本轮**最有价值的一组数据**——同一个组件、连续两年、同一根因。

### CVE-2024-45409（CVSS 9.8）

规则的攻击逻辑（Python 片段）：

```python
response_signature = root.find('./ds:Signature', namespaces)
if response_signature is not None:
    root.remove(response_signature)      # ← 直接删掉签名节点

nameid = root.find('.//saml:NameID', namespaces)
if nameid is not None:
    nameid.text = username               # ← 改成想冒充的人

attribute_values = root.findall('.//saml:AttributeValue', namespaces)
for attr_value in attribute_values:
    attr_value.text = username
```

**根因**：解析器接受"没有签名"的断言。
校验逻辑写成"如果有签名就验证"，而不是"没有签名就拒绝"。

**这是条件校验 vs 强制校验的经典差异**——
代码写的是 `if (sig) { verify(sig) }`，而正确写法是 `if (!sig) { reject() }`。

### CVE-2025-25291（CVSS 9.3）—— 这是补丁绕过

规则的攻击构造：

```python
saml_resp_mod = prefix + saml_resp_mod[:-17].decode() + "<![CDATA[-->" + ...
saml_resp_mod = re.sub(r'(<saml:NameID[^>]*>)[^<]+(</saml:NameID>)',
                       rf'\1{username}\2', saml_resp_mod)
```

**用了 CDATA 注入**。这说明：

- 2024 年的修复**堵住了"删掉签名节点"这条路**
- 但**没有堵住"让签名验证和取值看到不同内容"这条路**

**这就是典型的 Incomplete Fix**——我们工作流里权重最高的信号（+60）。

### 数据佐证：EPSS 翻倍

| | EPSS | 含义 |
|---|---|---|
| CVE-2024-45409 | 0.10684 | 约 10.7% 分位 |
| CVE-2025-25291 | **0.20586** | **约 20.6%，翻倍** |

补丁绕过版本的**在野利用概率是原版的两倍**。
这符合直觉——绕过手法公开后，未打补丁的实例更集中、攻击更高效。

## 三层拆解

**触发条件层**：提交 SAML 断言 / UDRPC 消息。

**根因层**：**签名验证与实际取值，看到的对象不是同一个。**

三个案例三种形态：

| 案例 | 形态 |
|---|---|
| GitLab 2024 | 删掉签名节点 → 校验看不到签名，取值照常 |
| GitLab 2025 | CDATA 注入 → 校验看到一个结构，取值看到另一个 |
| UpdraftPlus | 客户端提供 `key_name` → 服务端信任它并据此选密钥 |

**模式层**：**不变量冲突**——
「用于验证的对象」与「被使用的对象」应当是不可变的同一个，
但三者都在中间环节发生了分离。

这对应我们泛化引擎里基础分 95 的 `invariant_conflict` 维度（全库最高）。

## 外推假设（待验证）

按我们工作流的维度展开，**均为假设，不是发现**：

### 1. 同族（最高优先）

GitLab SAML 两年连出两次。**第三次是否存在？**

- **依据**：同一组件、同一根因连续复现，说明修复是"补具体手法"而非"重构校验模型"
- **验证方向**：2025 补丁之后，是否还有第三种让"验证对象 ≠ 取值对象"的构造
- **候选手法**（按不变量冲突维度列举）：
  - XML 注释包裹
  - 命名空间前缀变体
  - 实体引用 / 外部实体
  - 属性顺序与重复属性（最后写入生效 vs 先到优先）
  - 编码差异（UTF-16 / 双重编码）
  - 换行与空白注入
- **命中判据**：签名验证通过但取到的 NameID 与签名覆盖内容不一致
- **排除判据**：所有变体均被拒绝，或验证与取值已改为同一规范化对象

### 2. 对称性

- UpdraftPlus 的 `users.get_users` 只是**其中一个 RPC command**。
- **其他 command 是否同样无鉴权？** 规则里给的只是探测用的最小载荷。
- **命中判据**：换 command 名后服务端仍执行
- **排除判据**：command 白名单或按 command 分级鉴权

### 3. 信任域反转

UpdraftPlus 的 `key_name` 由**客户端提供**，服务端据此选择解密密钥。

- **这是最典型的信任域反转**——密钥选择本该由服务端根据会话/租户决定
- **外推**：所有"客户端提供标识符 → 服务端据此选密钥/配置"的架构都要查
- **具体测试**：`key_name` 换成其他值，看服务端是否接受、是否有校验
- **命中判据**：任意 `key_name` 均被接受且能走通流程

### 4. 入口一致性

GitLab SAML 的修复是否覆盖了全部入口？

- SAML 通常有多个端点（SSO / ACS / SLO / metadata）
- **只修一个端点 = 换端点打**
- **命中判据**：某端点仍接受无签名/篡改断言

## 对工作流的两处验证

### 验证 1：静默补丁/补丁不完整是最高价值信号

GitLab 2025 那个 CVE **就是 2024 补丁的绕过**——活标本。
我们给 `incomplete_fix` 打的 +60 最高权重，被这组数据证明了。

**推论**：看到某个组件出了 CWE-347 类漏洞，**立刻去查它同组件的历史 CVE**，
看修复是补手法还是重构模型。补手法的必出第二次。

### 验证 2：根因族 > 漏洞类型

三个案例按漏洞类型分属于：认证绕过、认证绕过、认证绕过（看着是同一类）。
但按**协议**分是：SAML、SAML、私有 RPC（完全不同）。

**真正把它们串起来的是根因（签名验证与取值对象分离），不是类型也不是协议。**

这说明我们"模式层泛化"的设计是对的，
而按 CWE 类型或按协议分类都会漏掉这个关联。

## 可复制的方法

**规则库的正确用法不是跑扫描，是当知识源读。**

```bash
# 按根因族检索（比按 CVE 编号检索有价值得多）
grep -rl "CWE-347" --include="*.yaml" nuclei-templates-main/

# 按攻击手法检索
grep -rl -iE "auth-bypass" --include="*.yaml" .

# 看某个产品的全部历史
ls nuclei-templates-main/code/cves/2026/
```

**要点**：
1. **按 CWE 检索，不按 CVE 检索**——同根因的会聚到一起
2. **看同一 vendor 的跨年分布**——连续出洞 = 修复不彻底
3. **对比 EPSS 变化**——升高的说明在野利用加剧，优先级上调
4. **读 code 块的构造逻辑**，不只是 http 块——根因藏在构造里
