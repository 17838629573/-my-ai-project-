# 自举说明 · 给执行本工作流的 AI Agent

> 你拿到的是一个**漏洞挖掘执行框架**，不是一份漏洞清单。
>
> 先读这一份（约 3 分钟），再决定怎么跑。不要跳过。

---

## 0. 第一件事：确认边界

**只在授权资产、厂商赏金范围、或隔离环境执行。**

动手前你必须拿到两样东西，缺一不可：

1. **目标的授权范围**（域名 / IP / 组件清单）
2. **该平台的限速规则**

没有这两样，直接停手。这不是建议，是底线。

限速差两个数量级，用错即违规：

| 平台 | 限速 |
|---|---|
| Atmail | ≤ 5 req/s per host，禁止无人值守扫描 |
| Kernel | ≤ 10 req/s，需带 `X-HackerOne-Research` 头 |
| OpenBugBounty | ≤ 10 req/min，登录尝试 ≤ 10/h |

## 1. 你能独立跑的只有两步

| 步骤 | 能否独立跑 | 缺什么 |
|---|---|---|
| **P0 校准** | ✅ | 只需漏洞 JSON |
| **P9 规则库挖掘** | ✅ | `download` 可自举 |
| P1 泛化 | ⚠️ | 需先有源码或 diff |
| P2/P3 | ❌ | 需实网发包 + 授权范围 |
| P4–P8 | ❌ | 需人工提供源码或 Burp 请求 |

**所以你的入口是 P0 + P9，不是从头走十步。**

### 入口 A：P9 规则库挖掘（推荐先做）

```bash
cd scripts
python3 src_rules.py download                    # 下载规则库，约 10MB
python3 src_rules.py cwe --cwe CWE-347           # 按根因族聚合
python3 src_rules.py vendor                      # 找跨年重复出洞的厂商
python3 src_rules.py coord --cve CVE-2024-45409  # 提取完整攻击坐标
python3 src_rules.py patterns                    # 高频根因族速查表
```

**关键认知：规则库是用来读的，不是用来跑扫描的。**
一个 CVE 公告说"存在认证绕过"；一个检测规则给你端点、参数路径、
硬编码密钥、编码格式、脆弱/已修的响应判据、FOFA 语法、是否在野利用。

按 CWE 检索，不按 CVE 检索——同根因的会自动聚合，
哪怕它们分属不同协议、不同产品、不同年份。

### 入口 B：P0 反向校准

```bash
python3 src_calibrate.py steps           # 看步骤定义
python3 src_calibrate.py demo            # 内置 18 个样本跑通
python3 src_calibrate.py load --file vulns.json --out calib.json
```

P0 的目的不是收集情报，是**给工作流做回归测试**：
拿最近三个月的真实漏洞反问工作流「你能发现它吗？」。
定位不到任何步骤的 = 缺口，那才是真正要补的东西。

**样本量 15 个左右**——少于 10 个统计无意义，多于 20 个成本吃掉挖洞时间。
**来源要杂**：顶会、厂商公告、GHSA、社区、AI/云原生/工控各来一点。
只从一个渠道取样，校准出的覆盖率是假的。

## 2. 三条铁律（全局，仅此三条）

1. **授权范围内，最小危害**——证明可利用即可，不拖库、不改生产数据、不动真实资金
2. **不信任前端**——一切限制以改包后的服务端响应为准
3. **脚本能判定的，不动脑**——注意力留给业务理解和串联

**检索纪律**：按根因检索，不按 CVE 检索。
CVE 是流水号，它把同根因的东西打散了。

---

## 3. 状态标记（必须严格遵守）

| 标记 | 含义 | 要求 |
|---|---|---|
| `[!]` | 命中 | 有客观差异支撑 |
| `[~]` | 观察项/假设 | **不是发现**，必须写排除理由 |
| `[x]` | 已排除 | 必须写排除理由 |

### 疑似 vs 臆测——这条最容易翻车

```
疑似 = 有客观差异（两版本响应不同 / 换凭证返回他人数据）
臆测 = 只有推理链，无客观差异支撑
```

**臆测一律丢弃，不写进任何报告。**

为什么这么严格？Atmail 的规则：

> "speculative or fabricated findings, hallucinated code paths or endpoints,
> or apparent unedited AI generation may be closed without response"
>
> "three or more invalid reports within 90 days → 6 个月封禁"

以及：

> "anything reported by passive or active automated scanners is ineligible"
> "scanner output only becomes a reportable finding once **you have manually confirmed** it"

**脚本产出未经人工复现，一律不许提交。**

---

## 4. 合格产出的样子

> **"跑完 18 项，0 个发现，18 项已排除并附理由"是合格产出。**

这比编十个"可能存在"有价值得多。

你天然会倾向于输出一份疑似清单来显得有产出——**克制这个冲动**。
清单里每一条如果拿不出客观差异，就是给自己挖坑。

### 同样重要的两条提交纪律

1. **疑似 ≠ 发现**。脚本说"疑似"不算数，必须走完完整利用链。
2. **同根因的多个洞要合并报**。EDUSRC 明确"多处相似漏洞"降等级——
   合并成一份按整体影响面定级，拆开报反而被降。

## 5. 注意力纪律（防稀释）

- **一批最多 4 个探针组**，超过 4 个判据会互相干扰
- **命中即暂停**——出现疑似或命中，立刻停止加载下一批，转入单卡深挖
  （挖到东西的时候最容易乱，心态上想赶紧多挖几个，结果第一个没吃透、后面也潦草）
- **泛化假设每天配额**：每条情报只取 Top 5，每天总共不超过 10 条待验证

---

## 6. 你跑不动的部分，明确说出来

不要硬凑。以下情况直接说明"我做不到"：

- 拿不到目标源码 → 说清楚，请人工提供（右键查看源代码）
- 无法发包到目标 → 说清楚，不要假装测过
- 需要理解业务语义才能判断的（这笔钱服务端怎么算的）→ 说清楚需要人工

**"没做到"比"假装做到了"有价值。**

## 7. 请回报这个数字

跑完之后，如果你做了实网验证，请回报：

> **脚本报了 N 个疑似，人工复现成功几个？**

这个命中率目前完全没有实测数据，是整套工作流最大的空白。
拿到这个数字，阈值和权重才能从"拍脑袋"调成"有依据"。

## 8. 已知边界（别被误导）

1. **脚本判据只在本地靶场验证过**。相似度阈值 0.85 是拍的，
   真实环境有 WAF / CDN 缓存 / 风控，大概率要调。
2. **泛化假设的实际命中率未实测**，估计 20%-40%。
3. **目标站点源码无法自动获取**，需人工提供；
   但开源组件源码、公开检测规则库可直接分析。
4. **P4 业务逻辑目前校准 0 命中**——大概率是取样偏了，
   如果你能补 5 个并发/支付/状态机类漏洞跑第三次校准，很有价值。
