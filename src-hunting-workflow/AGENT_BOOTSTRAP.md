# 自举说明 · 给执行本工作流的 AI Agent

> 你拿到的是一个**漏洞挖掘执行框架**，不是一份漏洞清单。
>
> **每个 Agent 的工具权限不同，起点就不同。**
> 先花 2 分钟测清自己的能力边界，再决定从哪一步进。不要照抄别家的路径。

---

## 0. 第一件事：测你的能力边界

**不要假设你和写这份文档的 Agent 有一样的权限。** 它的沙盒抓不到目标站点，
你的可能能抓、能看源码、能跑脚本——也可能都不能。先测。

| 能力 | 怎么测 | 测完记下来 |
|---|---|---|
| **能发包到目标吗** | `curl -I https://目标域名` | 能 / 不能 |
| **能看到源码吗** | `view-source:` 或抓 `<script>` / form 属性 | 能 / 只有渲染后文本 |
| **能搜网页吗** | 搜索接口是否可用 | 能 / 不能 |
| **能下载 GitHub 吗** | `curl -I https://codeload.github.com` | 能 / 不能 |
| **能跑 Python 脚本吗** | `python3 scripts/src_rules.py patterns` | 能 / 不能 |
| **能装依赖吗** | `pip install requests` | 能 / 不能 |

**测完按下面的矩阵选路径。别走你走不了的路，也别浪费你独有的能力。**

## 0.5 开工第一问（不管你走哪条路径，先答这一句）

> **目标的语言 / 框架 / 运行时，近 3-5 个月是否升过级？**

这是唯一一个**不用挖就有答案**的前置检查——纯客观事实，问一次就完事。

```bash
python3 scripts/src_stack.py upgrade --lang python   # 或 java / go / js
```

- **没升级** → 旧版本本身就是敞口：已知 CVE 未修 + 废弃 API 不再收补丁
- **升过级** → 追问：**升的是哪部分？升级过程暴露了什么？**

**升级成功 ≠ 安全迁移。** ESPHome CVE-2026-59178（CVSS 9.8）：
环境变量改名后无 fallback，升级后认证中间件与 WebSocket 登录门**全部静默禁用**，
只在启动日志打 banner，`docker run -d` 看不到。

**变更信号分级**（防误报）：
- 强：描述含 security/unsafe/safer/harden；默认行为变更；移除或重命名配置项/凭证项
- 中：移除无人维护的模块
- 弱：纯功能新增/性能改进 → **不要据此推断旧版有洞**

**升级类目标必须做验收测试**：从每个能触达的网络段确认
**认证·授权·加密·日志·网络绑定** 五类控制仍生效。
判据一句话：**升级后，未认证访问是否被拒绝？**

## 1. 按能力选入口

### 路径 A：能发包 + 能看源码（最强）

**你能跑完整链路。** 这是本工作流设计时的理想假设。

```
P2 测绘 → P3 越权 → P4 逻辑 → P5 注入 → P6 补丁对齐 → P7 信任域
```

- 源码给你 API 端点、硬编码密钥、内部头、状态机
- 发包给你真实响应差异——**这才是判据**

**但你的风险不是做不到，是做过头。** 详见第 5 节（这节是为你写的）。

### 路径 B：只能看源码，不能发包

**你能做静态分析，产出假设，但无法验证。**

```
P1 泛化 → P5 源码审计 → P7 内部头分析 → 产出假设清单
```

- 你的产出是**假设**，不是发现
- 每一条必须写清「命中判据 + 排除判据」，交给能发包的人验证
- 不要写"可能存在 XXX"——写"改哪个字段、改成什么值、看到什么算中"

### 路径 C：只能搜网页 / 只能下 GitHub

**你做情报层，产出方向。**

```
P0 校准 → P9 规则库挖掘 → P1 情报打分
```

```bash
python3 scripts/src_rules.py download
python3 scripts/src_rules.py cwe --cwe CWE-347
python3 scripts/src_rules.py vendor
python3 src_calibrate.py load --file vulns.json
```

**关键认知：规则库是用来读的，不是用来跑扫描的。**
公告说"存在认证绕过"；检测规则给你端点、参数路径、硬编码密钥、
编码格式、脆弱/已修的响应判据、FOFA 语法、是否在野利用标签。

按 CWE 检索，不按 CVE 检索——同根因的会自动聚合，
哪怕分属不同协议、不同产品、不同年份。

### 路径 D：都不能

**你做方法论维护。**

- 用内置样本跑 `src_calibrate.py demo` 验证工作流逻辑
- 扩充校准样本（收集近三月漏洞 JSON）
- 修正判据与权重

这也有价值——**校准器发现工作流缺口，是这套东西唯一的自进化机制。**

## 2. 三条铁律（全局，仅此三条）

1. **授权范围内，最小危害**——证明可利用即可，不拖库、不改生产数据、不动真实资金
2. **不信任前端**——一切限制以改包后的服务端响应为准
3. **脚本能判定的，不动脑**——注意力留给业务理解和串联

**检索纪律**：按根因检索，不按 CVE 检索。
CVE 是流水号，它把同根因的东西打散了；CWE 与根因描述才是聚合键。

---

## 3. 动手前必须拿到的两样东西

**缺一不可，没有就停手。** 这不是建议，是底线。

1. **目标的授权范围**（域名 / IP / 组件清单）
2. **该平台的限速规则**

限速差两个数量级，用错即违规：

| 平台 | 限速 |
|---|---|
| Atmail | ≤ 5 req/s per host，**禁止无人值守扫描** |
| Kernel | ≤ 10 req/s，需带 `X-HackerOne-Research` 头 |
| OpenBugBounty | ≤ 10 req/min，登录尝试 ≤ 10/h |

## 4. 状态标记（必须严格遵守）

| 标记 | 含义 | 要求 |
|---|---|---|
| `[!]` | 命中 | 有客观差异支撑 |
| `[~]` | 观察项/假设 | **不是发现**，必须写排除理由 |
| `[x]` | 已排除 | 必须写排除理由 |

### 疑似 vs 臆测——这条最容易翻车

```
疑似 = 有客观差异（两版本响应不同 / 换凭证返回他人数据）
臆测 = 只有推理链，无客观差异支撑
```

**臆测一律丢弃，不写进任何报告。**

为什么这么严？Atmail 的规则：

> "speculative or fabricated findings, hallucinated code paths or endpoints,
> or apparent unedited AI generation may be closed without response"
>
> "three or more invalid reports within 90 days → 6 个月封禁"

以及：

> "anything reported by passive or active automated scanners is ineligible"
> "scanner output only becomes a reportable finding once **you have manually confirmed** it"

**脚本产出未经人工复现，一律不许提交。**

## 5. 可执行 Agent 的特有风险（路径 A 必读）

**你的问题不是做不到，是做过头。** 四个最容易失控的地方：

### 5.1 批量扫描

> 不要对着目标全站扫。SRC 规则里"unattended scanners"普遍被禁。
> 每次动手前问：**这一批请求是有目标的验证，还是盲目的穷举？**

### 5.2 破坏性验证

**禁止用破坏性操作"证明"漏洞。** 具体：

- 不删文件、不改生产数据、不动真实资金
- RCE 只做 `id` / `echo 随机串` 这类无害验证
- 越权只读取最小必要数据，拿到就停，不继续遍历

### 5.3 限速失控

`--delay` 不是可选优化项，是**开工前必填项**。
写完脚本先跑一次单请求，确认速率再放开。

### 5.4 拿真实用户数据

> 如果漏洞意外暴露了他人数据：**立即停止，不继续枚举，不保存副本，24 小时内上报。**

## 6. 合格产出的样子

> **"跑完 18 项，0 个发现，18 项已排除并附理由"是合格产出。**

这比编十个"可能存在"有价值得多。

你天然会倾向于输出一份疑似清单来显得有产出——**克制这个冲动**。
清单里每一条如果拿不出客观差异，就是给自己挖坑。

### 两条提交纪律

1. **疑似 ≠ 发现**。脚本说"疑似"不算数，必须走完完整利用链。
2. **同根因的多个洞要合并报**。EDUSRC 明确"多处相似漏洞"降等级——
   合并成一份按整体影响面定级，拆开报反而被降。

---

## 7. 注意力纪律（防稀释）

- **一批最多 4 个探针组**，超过 4 个判据会互相干扰
- **命中即暂停**——出现疑似或命中，立刻停止加载下一批，转入单卡深挖
  （挖到东西的时候最容易乱，想赶紧多挖几个，结果第一个没吃透、后面也潦草）
- **泛化假设每天配额**：每条情报只取 Top 5，每天总共不超过 10 条待验证

---

## 8. 跑不动的部分，明确说出来

不要硬凑。以下情况直接说明"我做不到"：

- 拿不到目标源码 → 说清楚，请人工提供
- 无法发包到目标 → 说清楚，不要假装测过
- 需要理解业务语义才能判断（这笔钱服务端怎么算的）→ 说清楚需要人工

**"没做到"比"假装做到了"有价值。**

## 9. 请回报这个数字

跑完后如果你做了实网验证，请回报：

> **脚本报了 N 个疑似，人工复现成功几个？**

这个命中率目前完全没有实测数据，是整套工作流最大的空白。
拿到这个数字，阈值和权重才能从"拍脑袋"调成"有依据"。

同时请回报：
- 你走的是哪条路径（A/B/C/D）
- 卡在哪一步
- 哪条引导提问让你不知道该怎么答

**卡住的地方就是文档写得不清楚的地方**，这比作者自己检查有效得多。

---

## 10. 已知边界（别被误导）

1. **脚本判据只在本地靶场验证过**。相似度阈值 0.85 是拍的，
   真实环境有 WAF / CDN 缓存 / 风控，大概率要调。
2. **泛化假设的实际命中率未实测**，估计 20%-40%。
3. **P4 业务逻辑目前校准 0 命中**——大概率是取样偏了。
   如果你能补 5 个并发/支付/状态机类漏洞跑第三次校准，很有价值。
