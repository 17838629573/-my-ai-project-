# 拆模块（架构师层级）

输入：步骤 1 确认的需求、规模与拆分层数（或待重构 / 导入的既有项目）。
产物：分层契约图（`deps.md`，供 `scripts/dep_check.py` 校验）+ 契约清单，摆给用户勾选。

1. 该调研的先搜成熟方案（铁律 4），报用户批准。
2. **按职责切分**：一个模块只干一件事；底层（工具 / 数据）与上层（业务 / 界面）分开。
3. **按架构师层级递归**（读 `skills/architect/SKILL.md`）：总架构师定顶层 → 次级架构师逐层拆 → 末层代码 AI 直接写。给 N 层 → 拆到 N 层；"拆到不能拆" → 递归到每模块职责单一。
4. **层间纪律**：上层对下层只读，禁止改下层；下层不符契约 → 上层只改自己契约使其更精准，下层重做。
5. **定依赖方向**：只准上层依赖下层；有环就重切到无环。
6. **写契约块**：每模块五项 = 职责 / 谁能调用 / 依赖谁 / 公开接口（签名+参数+返回）/ 改接口须同步查哪些文件。
7. **标文件分级**：红 / 黄 / 绿（铁律 5）。
8. 依赖落 `deps.md`：每行 `模块 -> 它依赖的模块`，逗号分隔；**模块名用代码实际 import 路径**（如 `app.api` 对应 `backend/app/api/`），dep_check 才能归属到文件；每个架构师只维护自己那层行，层间用 `# L0` / `# L1`… 注释分隔。跨语言 / 跨进程依赖（HTTP API、数据库 Schema）行尾标 `[runtime]`，括号写说明，如 `frontend/client -> backend/api (HTTP/OpenAPI)[runtime]`——dep_check 跳过其代码存在性验证、仍查循环依赖。
9. **输出全局契约图** = 各层汇总（`deps.md` 全文），交用户留档，供以后改架构定位到层。
10. 契约图 + 分层契约清单摆给用户勾选；**顺带问：是否用 TDD？**（勾 → 步骤 3 先写测试再写实现；不勾 → 写代码→测试找 bug）。

过门：用户确认 + 契约五项齐全 + 无环 + 契约图与代码对应（dep_check 过）。需用户批准的决定，按 `skills/track/SKILL.md` 落 `.track.md`。

> 契约块示例：`user_auth` — 职责：校验账号密码、签发 token；谁能调用：login_route、register_route；依赖：db、crypto；接口：`issue_token(uid:str)->str`、`verify(pwd:str,h:str)->bool`；改接口同步查：login_route.py、register_route.py、tests/test_auth.py。
