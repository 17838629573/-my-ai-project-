# 卡住协议

## 能力不足
1. 逐项探测：命令能跑？工具在？服务通？搜到的内容相关可信？
2. 有降级路径 → 用降级继续，验证声明里写明降级原因，不许假装通过。
3. 无降级或搜索无果 / 不可信 → 向用户索要：「我需要 [能力]，用于 [步骤]，请提供」；禁止基于猜测续做。

禁止：硬造假结果、假装已具备、静默跳过。

## 时间预算（防悬空态）
不许停在"既没成也没败"的悬空态——用户不监督也要有断点。此为**硬原则**；但"多久算超时"是**建议值、留余量**，不机械卡秒。
- 只算外部操作耗时（命令 / 构建 / 测试 / 网络 / I/O），思考时长不计。
- 参考上限：纯思考输出 ~60 秒（在产出可放宽）；有外部 I/O 的步骤，跑前估操作耗时 ×3（×3 是余量系数，估不准往宽估）。
- 接近上限先软告警；明显超时仍无产出 → 停下汇报。仍有效推进可继续并说明。超时是"卡死信号"，不是"任务判死"。
- 循环 5 轮：一次「fix → verify」算一轮，连续约 5 轮仍不过建议停下；同类失败指同一根因反复（定义见 `ERRORS.md`）。

## 必须停下
① 时间明显超出（无 I/O ~60s / 有 I/O 估时×3 左右）② 修复验证循环约超 5 轮 ③ 能力要不到且无降级 ④ 两项要求互相矛盾。

停下后输出诊断，四项缺一不可：
- **卡在哪步** · **已试过什么** · **缺什么**
- **四个选项**：放宽约束 / 绕过此步 / 提供能力 / 终止

## 写失败库
每次触发，追加一条到 `ERRORS.md`：步骤 / 失败类型 / 原因 / 走了哪分支 / 结果。同类失败约 3 次（建议值）或流程完不成 → 交用户裁定固化或删改。

> 示例：卡步骤 3 写 payment.py；已试：单测 8 passed，集成报 ImportError: crypto 未装；缺：装 crypto 权限；选项：放宽(换 hashlib) / 绕过(标 TODO) / 提供(帮装) / 终止 → 已写 ERRORS.md 等用户选。

等用户选择，禁止继续硬跑。
